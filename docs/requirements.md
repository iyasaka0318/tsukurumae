# ハードウェア開発支援 Skill 要件整理

（2026-10-06 時点の原要件。Skill の改善時はここと照らし合わせる）

## 1. 実現したいこと
- Codex、Claude Code、Cursor 等の既存 AI エージェントに読み込ませて使う、ハードウェア開発支援用の Skill。
- 新しい AI モデルや独自エージェント基盤を作るのではない。`i-have-adhd` や `yomiyasu` のように、既存 AI に行動方針・思考手順・チェック項目を与える「便利ツール」。
- 対象：ドローン、倒立振子、ロボット、組込みシステム、センサ装置、3D プリントを伴う試作、電装を含む個人開発、その他小規模ハードウェア開発。
- 最初から完全な汎用品でなくてよい。自分のドローン・倒立振子開発を実例に改善していく。

## 2. 作りたい理由
AI は早い段階で部品選定・CAD・コード生成へ進んでしまう。ユーザー自身が「何を決めなければならないか」を認識していないため、後から重要条件が判明して大量の手戻りが起きる。

実例:
- **IMU**：「安い方がいい」から MPU-6050 が候補になったが、本来の要求は「価格を抑えたいが、研究用途として必要十分な性能は確保したい」。研究内容まで考えると ICM-42688 系が適切だった。→ 局所的な条件ではなく「最終目的に対して十分か」まで確認すべき。
- **CAD**：型番は伝えていたが、Pico 2 か Pico 2 WH か、ピンヘッダーの有無と向き、ジャンパ線かはんだ付けか、IMU 側のヘッダー、USB アクセス、バッテリーケーブルの方向、ケーブルを挿した状態の高さ、固定方法などを確認しないまま CAD が進み、「ヘッダーがあるのでこの向きでは使えない」「ジャンパ線を挿したら高さが足りない」「ケーブルがこちらから出るので変更が必要」が後から発生した。

→ **作る前に聞けば防げた手戻りを減らすこと**が最大の目的。

## 3. 基本思想
AI は単なる回答者ではなく:
1. 要求を聞き出す
2. 不足・矛盾・未決定事項を発見する
3. システム全体として成立する計画を作る
4. 具体設計に必要な実装条件を確認する
5. 条件が揃ってから設計・実装へ進む
6. 試作結果を受け取って改善ループを回す

ユーザーが質問した項目だけでなく、最終目的から逆算して「まだ何を確認する必要があるか」を AI 側から考える。ユーザーが存在を認識していない論点を発見する。

## 4. 開発プロセス
### Step 1：要求定義・前提監査
- 何を・なぜ・目的（研究/趣味/実用）・成功条件・確定事項・使用予定部品・手持ち部品・予算・サイズ/重量・性能要求・期限・設備・不安な点を必要に応じて聞く。固定的に全部聞くのではなく選択・追加する。
- ユーザーの発言をそのまま要求として固定しない（「安くしたい」の優先順位を確認する、不適切な部品案は指摘する）。
- 終了時に整理するもの：目的、成功条件、確定事項、仮決定事項、未決定事項、不明事項、制約、優先順位、リスク、矛盾。

### Step 2：システム設計・開発計画
- 全体構成、MCU、センサ、モータ、ESC、バッテリー、レギュレータ、通信、電源・電装・制御・ソフト・機構構成、工具、消耗品、購入品、手持ち部品、代替部品、購入先、リンク、価格、総予算、重量、電力、サイズ、開発順序。
- 方針は「最安」ではなく「必要十分」。必要なら最安案/必要十分案/余裕案を、価格・性能・リスク・拡張性・研究上の妥当性で比較してユーザーと決める。
- 重量・推力・バッテリー容量・ESC 定格・レギュレータ容量・電圧レベル・I/O・センサ性能・通信帯域・物理サイズの成立性を確認する。
- 電装は質問されなくても扱う（電圧、セル数、ESC 定格、5V/3.3V、電流、コネクタ、配線、信号電圧、GND、ノイズ、電圧降下、発熱、フェイルセーフ）。

### Step 3：実装条件監査 → 設計（特に重要）
- 部品名だけで設計を始めない。型番から特徴（例：WH はヘッダー実装済み）を認識し、向き・接続方式・高さ・固定・USB アクセスなどを確認する。
- ユーザーが言い忘れるまで待たず、AI 側から質問する。
- 確認対象：機械的条件、電装条件、運用条件、配線・伝送条件。
- 調べれば分かること（外形、寸法、穴位置、コネクタ位置、重量、定格、ピン配置）は AI が調べ、設計意図に依存すること（ヘッダーを付けるか、ケーブルの向き、USB アクセス、取り外し可否）は質問する。
- **Design Input Freeze**：設計前に入力が揃っているかを監査し、重大な未確定があれば保留する。影響の小さい項目は仮置きでよい。

### Step 4：試作・実機確認・フィードバック
- 3D プリント、組立、配線、通電、動作確認、制御実験、ログ、重量・振動・発熱確認。
- フィードバックから原因を考え、必要な段階まで戻る（Plan → Build → Observe → Diagnose → Modify → Build）。
- Step 1〜3 は作る前に防げる手戻りを減らす。Step 4 は実物でしか分からない問題を速く見つけて直す。
  - 「Pico 2 WH のヘッダーを考慮していなかった」→ Step 3 で防ぐべき
  - 「飛ばしたら想定以上に IMU に振動が伝わった」→ Step 4 で分かっても仕方がない

## 5. 情報分類
Known / Assumed / Decided / Tentative / Unknown / Open Question / Constraint / Preference / Risk / Dependency

## 6. してほしくないこと
1. 情報不足なのにすぐ答えを出す
2. ユーザーの言葉を文字通りに取りすぎる
3. ユーザーが聞かなかった項目を無視する
4. 商品名だけで物理設計する
5. 仮定を事実として扱う
6. 調べれば分かる情報を全部ユーザーに聞く
7. 些細なことを全部質問して開発を止める
8. 完璧主義になりすぎる

## 7. 質問の優先順位
Critical（システム成立が判断できない）/ Blocking（次工程へ進めない）/ Important（後から変えると大きな手戻り）/ Nice to know（後からでもよい）。Nice to know のために止めすぎない。

## 8. フェーズゲート
- Gate 1：要求がある程度定義され、重大な矛盾・不足が解消されている
- Gate 2：システム構成として成立している（重量、電力、性能、電装、互換性、予算）
- Gate 3：具体設計に必要な物理・電装・接続条件が揃い、重大な未回答がない。ここを通って初めて CAD・回路・配線へ

## 9. 立ち位置
AI モデルを作るプロジェクトではない。最初は Markdown 中心でよい。将来的に Web 検索、データシート取得、BOM 生成、価格取得、重量・電力計算、CAD Agent、MCP、回路設計ツールとの連携も検討。

## 10. MVP
1. ユーザーが作りたいものを説明する
2. AI が目的・制約・既知情報を整理する
3. 不足・矛盾・未決定事項を洗い出す
4. 必要な質問をする
5. 情報が揃ったらシステム構成を計画する
6. 具体設計前に実装条件を再監査する
7. 重大な未決定事項がある間は CAD 等へ進まない

## 11. 評価
実際の開発例で評価する。例：「Pico 2 WH、IMU、ESC、バッテリーを使ってドローンを作りたい。CADを作って。」に対し、即座に CAD を作らず、ヘッダー・固定・USB・IMU モジュール・接続方式・ケーブル方向・バッテリーコネクタ・配線経路・クリアランスを確認できるか。確認せずに CAD へ進めば失敗。設計に影響しない質問を何十個もしても失敗。
→ **必要な質問を、必要なタイミングで、必要な量だけ行えるか。**

## 12. 核心
AI にハードウェアを作らせる前に、作るために必要な質問をさせる。
狙いは「一発で完璧な設計」ではなく、「作る前に防げたはずの手戻りを減らし、実機でしか分からない問題にできるだけ早く到達すること」。
