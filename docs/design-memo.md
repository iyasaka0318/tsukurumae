## 1. 目的と成功条件

### 目的
既存の AI エージェント（Claude Code / Codex）に読み込ませ、ハードウェア開発中の AI の振る舞いを変える。
**作る前に聞けば防げた手戻りを減らし、実機でしか分からない問題に早く到達する。**

### 成功条件（案）
1. 評価ケース「Pico 2 WH、IMU、ESC、バッテリーでドローン。CADを作って。」で、CAD を出さずに必須論点（ヘッダー、固定、USB、IMU モジュール、接続方式、ケーブル方向、バッテリーコネクタ、配線経路、クリアランス）を確認する。
2. 同じケースで、1 ターンの質問が過多にならない（設計に効かない質問を並べない）。
3. 情報が揃っているケースでは、余計な質問をせずに設計へ進む。
4. 実際のドローン・倒立振子開発で使い、手戻りの件数が減ったと本人が感じる。

1〜3 は評価ケースで機械的に確認する。4 は実運用で確認する。

## 3. 参考 Skill から取り入れること

### i-have-adhd（ayghri/i-have-adhd）
- 構成：`SKILL.md` 1 枚（約 140 行）＋ Codex 用 `agents/openai.yaml` ＋ Claude Code 用プラグイン定義（`.claude-plugin/`）＋ 常時有効化フック（SessionStart）。
- 書き方：**ルールごとに Bad / Good の具体例**を付けている。抽象的な原則よりも、AI の振る舞いが安定しやすい。
- **「ルールを破ってよいとき」**の節がある。ルール同士やタスクとぶつかったときの優先順位を明示している。
- **送信前チェック**（Pre-send check）がある。出力直前に自己点検させている。
- 明示起動（`/i-have-adhd`）すると、「stop」と言われるまで会話中ずっと有効になる。

### yomiyasu（nanaism/yomiyasu）
- 構成：`SKILL.md`（約 240 行、日本語）＋ `references/`（分野別の補足、不自然な表現のカタログ）＋ `scripts/`（リンター、差分チェック）。
- **最優先ルールを 1 つ決め**、ほかの原則はそれを壊さない範囲でだけ適用させている。
- **よくある失敗のカタログ**（slop-catalog）を別ファイルにして、本体を軽く保っている。
- 出力フォーマットが決まっており、「確認したい点は最大 2 点まで、なければ見出しごと出さない」のように**量の上限**がある。

### tsukurumae への反映（案）
| 取り入れること | tsukurumae での形 |
|---|---|
| Bad / Good の例 | 各原則に、実際の手戻り（Pico 2 WH、MPU-6050 など）を Bad / Good として載せる |
| 最優先ルール | 「Gate 3 を通るまで CAD・回路・配線を出さない（D2 の例外あり）」を最優先にする |
| ルールを破ってよいとき | 「ユーザーが進めてと言った」「情報が既に揃っている」「安全に関わる」などを明記する |

| 送信前チェック | 「CAD を出そうとしていないか」「仮定を事実として書いていないか」「質問が多すぎないか」などを点検させる |
| 出力の上限 | 1 ターンの質問数に上限を設ける |
| 配布形態 | Claude Code プラグイン（marketplace）＋ Codex 用 `agents/openai.yaml` |

## 4. 仮決定（Tentative）— AI 側の提案。異論がなければこのまま進める

### T1. 言語：本文は日本語、`description` は日英併記
- ドメイン用語（ピンヘッダー、ジャンパ線など）と、手戻りの実例が日本語である。翻訳すると、例のニュアンスがずれやすい。
- Claude Code と Codex はどちらも日本語の指示を問題なく扱える。yomiyasu が日本語本文で実績を出している。
- 自動起動の判定に使う `description` だけは、英語での依頼にも反応するよう日英を併記する。
- ユーザーへの出力は、ユーザーの言語に合わせる。

### T2. 起動方式：自動起動＋明示起動。**台帳ファイルがあれば常に有効**
- ハードウェアの話題を検出したら自動で読み込む（自動起動）。`/tsukurumae` でも起動できる。
- プロジェクトに台帳ファイルがあれば、そのプロジェクトでは毎回この Skill に従う。D4 の台帳ファイルが「このプロジェクトはハード開発中」という目印を兼ねるので、会話をまたいでも状態が引き継がれる。
- i-have-adhd のようなフックによる常時有効化は、MVP では作らない。

### T3. 台帳ファイルの仕様
- 置き場所：プロジェクトのルート。ファイル名は `HARDWARE_LEDGER.md`（大文字にしてエージェントの目に入りやすくする）。
- 形式：Markdown。項目ごとに ID（D1, A3, Q5 など）を振り、会話で参照できるようにする。
- 中身：現在のステップと Gate の状態、目的、成功条件、優先順位、制約、決定、仮決定、確定事実、仮定、未回答の質問（優先度付き）、リスク、依存関係、教訓。
- 更新するタイミング：ステップや Gate が変わったとき、決定や仮定が変わったとき。毎ターンの全文出力はしない。
- 1 ファイルが長くなりすぎた場合の分割方法は、実運用を見てから決める。

### T4. ファイル構成
```
skills/tsukurumae/
  SKILL.md                 本体。最優先ルール、行動原則（Bad/Good付き）、Gate、質問の優先度、送信前チェック
  agents/openai.yaml       Codex 用のメタデータ
  references/
    steps/*.md             各ステップの詳細手順
    component-checklists.md 部品カテゴリ別の実装論点（[聞く]/[調べる] 区分）
    rework-catalog.md      手戻りカタログ（会話データから作る）
    ledger-template.md     台帳の書式
.claude-plugin/            Claude Code プラグイン定義
evals/cases/               評価ケース
docs/                      要件、設計メモ
```
- `SKILL.md` は 250 行程度までに収める。詳細は `references/` に逃がし、必要になったステップで読ませる。

### T5. 質問数の上限
- 1 ターンの質問は**最大 5 個**。Critical / Blocking を優先する。i-have-adhd の「一度に見せるのは 5 個まで」に合わせた。
- 超える分は台帳の未回答欄に積み、次のターンで聞く。

### T6. D2（Gate の例外）の具体的な挙動
「進めて」と言われたら、止めずに次の 3 行を添えて進める。
1. 残っている Critical / Blocking 項目
2. 今回採用する仮定（例：「ヘッダーは下向き、ジャンパ線なしの前提」）
3. それが外れた場合の手戻りの大きさ

採用した仮定は台帳に記録する。
