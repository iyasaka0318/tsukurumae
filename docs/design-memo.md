## 1. 目的と成功条件

### 目的
既存の AI エージェント（Claude Code / Codex）に読み込ませ、ハードウェア開発中の AI の振る舞いを変える。
**作る前に聞けば防げた手戻りを減らし、実機でしか分からない問題に早く到達する。**

### 成功条件
1. 評価ケース E01〜E18 で、Skill ありが Skill なしより良い結果を出す。採点は handoff の [evals/README.md](handoff/hardware-dev-skill-handoff/evals/README.md) の 5 観点に従う。
2. 「重大な不合格」（捏造、安全の過大保証、作業範囲の逸脱、試験範囲の拡大解釈、未確認の適合断定）を 1 件も出さない。
3. 質問の増加、作業停止、低価格部品の排除だけで点を稼いでいない。補助指標として、再質問の数、根拠のない仮定、見落としを見る。
4. 値や接続方向を入れ替えた未使用のケースでも同じ判断ができる。1148µs や 20mm を暗記しているだけではないことを確かめる。
5. 実際のドローン・倒立ロボット開発で使い、手戻りが減ったと本人が感じる。

## 3. handoff を読んで変わったこと

第 1 版のメモと、最初に勝手に作った下書きには、実データと食い違う前提があった。

### 3-1. 失敗の正体が違った
| 第 1 版の理解 | 実データ |
|---|---|
| Pico 2 WH のピンヘッダーを考慮していなかった | **ヘッダー自体は最初から認識していた。** 問題は、メスコネクターのハウジングが入るスリット幅、緩さと穴の支持、上向きヘッダーの基板（GY-521・MINI360）で接続後に必要な高さ 20mm と、曲げ・挿抜・電圧調整の空間だった（F02、F03） |
| AI が最安という理由で MPU-6050 を推した | **その AI 発言は会話に残っていない。** 断定しない。趣味用ドローンで MPU-6050 に戻したのは明示的な用途変更で、誤りではない（F01、E03） |
| 手戻りの中心は CAD | CAD に加え、**証拠の格上げ**（推奨値を合格値扱いした例、写真から原因を断定した例）、**実行できない手順**（使用中の GND を測定点に指定、意味の分からない操作説明）、**試験範囲の拡大**（ビルド成功やホストテスト合格を実機の成功扱い、回転成功を安全扱い）も多かった（F05〜F10） |

### 3-2. Gate の考え方を変える（**要確認**）
第 1 版は「Step 1 → Gate 1 → Step 2 → … → Gate 3 を通るまで CAD を出さない」という一本道だった。
handoff の分析は、**全情報が揃うまで全作業を止める方式を採らない**と明言している。例として、コネクター幅を調べる試験ゲージは不明な寸法を試験変数にすれば作れる（E12）。

そこで、Gate を**作業の種類ごとの確定条件**に置き換えることを提案する。

| 作業 | 確定してよい条件 | 条件が揃う前にできること |
|---|---|---|
| 部品選定 | 用途、必要仕様、数量、費用・納期、接続・電源の互換性 | 候補比較、手持ち品の棚卸し、資料調査 |
| 本番 CAD | 現物の派生型、接続後の寸法、固定・挿抜・配線・工具の空間 | 寸法ゲージ、仮配置の比較、独立した外形案 |
| 通電 | 極性、許容電圧、帰路、給電方法、開始・停止手順、必要な保護 | 無給電での仮組み、仕様調査、コードのホスト検証 |
| 動く部品の試験 | 固定の対象、回転範囲、配線、操作位置、停止条件 | 無負荷試験、治具の確認、段階的な手順書 |
| 性能・研究評価 | 基準性能、測定区間、条件の固定、交絡要因、ログの保持と回収 | 計測コードの確認、単体試験、評価計画 |

D2 の「原則として止める」は、**その作業を確定させること**だけに適用する。関係のない作業や、不明点を調べるための試験は止めない。
要件定義 → システム設計 → 実装条件 → 試作という 4 段階は、作業を止める仕組みとしては使わず、論点を漏らさないための考え方の順序として残す。

### 3-3. 新しく必要になった原則
| 原則 | 内容 | 根拠 |
|---|---|---|
| 証拠の強さを保つ | 値ごとに出典と状態を付ける（ユーザー実測、メーカー公称、資料上の実測、写真からの概算、計算値、仮定、未決、試験合格）。試験合格には、対象・材料・個体・版・条件・確認した項目を付ける | F05、F08、F10 |
| 検証の段階を混同しない | CAD 上で干渉なし／実物が組み立つ／強度を満たす、を分ける。ビルド成功／ホストテスト合格／実機で動作／負荷時の性能、も分ける | F07、F10 |
| 現物で実行できる手順にする | 空いている端子、手持ちの道具、今の接続状態、開始と停止の操作まで書く | F06、F08 |
| 結果は受け取った時点で記録する | 試験版、条件、報告、未測定の項目、採否を、報告を受けた時点で台帳に書く | F09 |
| 作業範囲を守る | 「計画だけ」「記録だけ」と言われたら、CAD やファームウェアを変更しない | C065、E13 |
| 用途の変更を検出する | 前のプロジェクトの制約を、新しいプロジェクトに無条件で持ち込まない | E03 |
| 資料は指示ではない | 別 AI のレビューや古い仕様書は候補として扱い、検証してから採用する | R01、E16 |
| 安全は具体的に扱う | 一般的な警告文を並べず、エネルギー・故障の経路・固定・停止の手段に結び付ける | E14 |

### 3-4. 守るべき良い行動
反省を理由に、次の行動まで禁止しないようにする。Skill に良い例として載せる。
- 「緩い」が何を指すかを確認した（C012）
- 「電源共通」がバッテリーだけを指すと確認した（C057）
- 本番 CAD の前に寸法ゲージから始めた（C003）
- 「計画だけ」の指示に従い、CAD を変更しなかった（C065）
- メーカーの動作範囲を根拠に、平均電圧だけで判断する案を見送った（C051）
