# tsukurumae 要件定義（第2版）

2026-10-06、ユーザーとの要件定義で合意。[第1版](requirements.md)の考え方を引き継ぎ、重点を「最初の要件定義」に移す。

## 目的
自分の今後の開発（Claude Code と Codex）で、無駄な生成と無駄なターンをなくす。
そのために、最初の要件定義を AI と一緒にしっかりやり、ふわっとしたまま進む部分を減らす。

## 無駄とみなすもの
- 合意する前に出てくるコードや CAD
- 要件定義が足りなかったせいで起きる作り直し（例：「測っておいて」と最初に言われていれば渡せた情報）
- 前提が変わったことによる作り直し（例：センサーを変えた）は仕方がない
- 長い説明は無駄ではない

## 何を最初に決めるか
判断の基準は**後から変えが効くか**。
- 最初に決める：目的、方針、設計を左右するもの（センサーの選定など）
- 後回しでよい：後から簡単に変えられるもの（ジャンパ線の長さなど）
- 設計に必要な実測値は、それを使う成果物を作る前に AI から頼む（測り忘れを防ぐ）
- ユーザーが自分で「後で決める」と言ったものは残してよい
- AI が後回しにしたものは、「後で決めるもの」として一覧で見せる

## 質問の仕方
| 段階 | 形 | 量 |
|---|---|---|
| 要件定義（`/tsukurumae` を打った最初） | 考えを引き出す開いた質問 | 多くてよい |
| 要件が決まった後（技術的な話） | 選択肢と推奨案付き | 必要なものだけ |

- 要件定義では、AI が目的を推測して言葉にし、「これで合っていますか」と確かめる
- 前提を疑う範囲：作ること自体は受け入れ、その目的・使い方・前提を確かめる

## ユーザーの知識が足りない分野（電装など）
- AI の側から持ち出す
- 方針は理由をしっかり書いて提案する（例：「ここには何 V がかかるので、この部品をこの目的で入れる」）
- 全体の構成を示したうえで「この構成で大丈夫ですか」と聞く
- ユーザーが気になれば質問し、納得すれば OK で進む

## AI が反対したいとき
- 「やめた方がいい」とはっきり言い、理由とリスクを示す
- ユーザーが「それでいい」と言ったら、それ以上は反対しない
- ただし、その決定の前提を変える新しい事実が出たら、もう一度伝えてよい

## 要件定義の終わり
- AI の「もう聞くことはない」と、ユーザーの「細かいことはもういいから進めていい」がそろったところで終わる
- 最後に AI が「これで進めていいですか」と確かめる

## 残すもの
- 要件定義の結果は、独立した軽い文書にする
- ユーザーの OK をもらってから作業に入る
- 普段の速度は落とさない

## 対象外
- 目的が途中で変わったときの聞き直し（最初の要件定義でちゃんと決めるため）

## 使う人と環境
本人だけ。Claude Code と Codex の両方で使えればよい。

## 保留
- 名前（「作る前」→「やる前」など）は後で決める
