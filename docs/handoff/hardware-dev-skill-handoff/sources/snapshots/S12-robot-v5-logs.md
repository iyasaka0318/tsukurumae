# 倒立ロボット 計測・遅延注入・ログ保持の実装仕様 v5

2026-10-03。設計段階の実装仕様。FMP3の実プロジェクトへの組込み・コンパイル・実機検証は未実施。

## 時刻源と観測できる区間

| 観測量 | 主手段 | 注意 |
|---|---|---|
| Core0のISR入口→制御タスク開始→PWMレジスタ書込み完了 | Core0のDWT CYCCNT | 150MHzで1cycle≈6.67ns。分解能は計測精度の保証ではない |
| 実DRDYエッジ→タスク開始マーカー／書込み完了マーカー | 外部ロジックアナライザ | 割り込み受付待ちも含む。GPIO書込み自体の遅れを校正する |
| Core0とCore1の前後関係、試行開始・終了、長時間の対応 | 共通ハードウェアタイマー | 標準1µs、共有バスからの読み出し。短いCore0区間の主計測にしない |
| PWM書込み→実際の入力波形への反映 | 実IN波形＋書込みマーカー | 20kHzのwrap待ちは最大約50µs。指令が同じなら反映が波形に現れないこともある |

DRDYはCYCCNTへ自動ラッチされない。ISR入口で読んだ値は**DRDY発生時刻そのものではない**。CYCCNTの差をDRDY→PWMの全応答時間と呼ばず、IRQ受付遅延を外部測定で補う。制御タスクは同じDRDYのISR入口スタンプを引き継ぐ。DWT読出し、ログ、GPIOマーカーの空測定を行い、Core1アイドル／バス負荷で計測負荷が変わる分も確認する。

Core0のクロックを150MHzに固定し、DWTを初期化。32bit差分は符号なし減算で周回処理する。約28.63秒より長い区間は単純な1回の差分で測らない。試行中にCYCCNTをリセットしない。両コアのCYCCNT同士を直接引き算しない。

CYCCNTがidle/sleep・デバッグ停止でどう進むか、採用したRTOSと実機で確認する。WFIやクロックゲートを挟む区間で壁時計時間を表していない場合、活動区間のみDWTで評価し、待ち時間込みの応答は外部計測へ回す。ns分解能を理由にその確認を省略しない。周期をまたぐ指令の年齢も単純なCYCCNT差だけで断定しない。

## 本編の実験条件

自然な干渉試験、遅延感度の校正、対策比較を同じ研究の本編に含める。基準制御・電源構成・機体・床・温度・計測コードは各比較内で固定する。

1. Core1負荷：アイドル、計算、SRAM、XIP、TinyML。出力結果は最初は制御へ反映しない。
2. 微小遅延：0/10/25/50/100/200/400µs。演算後の予約出力方式で試験し、ゼロ追加遅延でも同じ処理を通す。予定より遅れた書込みとPWMのwrap待ちを実測する。
3. **周期単位の遅延：k=0/1/2/3/5/8周期**。T≈1msなら0/1/2/3/5/8msに相当。制御計算を止めず、毎周期の出力をk周期前の指令にする。400µsを校正範囲の上限にしない。
4. ジッタ：微小遅延は同平均の固定条件と比較する事前生成系列を使う。周期遅延では例として平均3周期に対し2/3/4周期を同割合で用い、固定3周期と比較する。指令のスキップ・再出力が起きる可変遅延モデルであることも記録する。
5. **L0固定反映を対策候補**に追加：即時書込みと、ISR入口基準のL0で書く条件を同じCore1負荷で比較する。演算ジッタを吸収する代わりに平均遅延が増える。ISR入口以前の遅れは吸収できない。L0は十分な演算余裕から決め、L0未達は1ms制御締切超過と区別する。µs注入にL0を使う条件とも識別する。

5～10Hzは機体の測定帯域ではなく、レビューの仮定。位相換算はΔφ=360*f*τ。400µsで0.72～1.44°、8msで14.4～28.8°になる。ただしこの式だけで閉ループの安定限界を決定しない。

各条件5試行・20秒から開始し、基準条件で安定倒立を確認してから遅延を段階的に増やす。角度RMS、安定維持時間、電源異常、傾角停止、接地、watchdog、締切超過を分けて記録する。試験開始直後の停止も失敗として数え、安定した試行だけ選ばない。安全停止まで差が見えなかった場合も「ここまでの範囲で差なし」と報告し、8msで必ず境界が得られるとは保証しない。

## k周期遅延線

左右指令、元のサンプル番号、時刻を持つ9要素のリングを全条件で使用する。周期nで新指令を格納してからn-kの要素を出力する。k=0も同じ経路を通す。

```text
毎制御周期 n:
  センサ／エンコーダ取得 → 推定 → 新指令u[n]を計算
  history[n % 9] = {u[n], 元サンプル番号, 時刻}
  command = history[(n-k) % 9]       # 実装では負の剰余を避ける
  現在の安全判定・電圧補償・飽和処理 → PWMへ書込み
  n / 元サンプル番号 / 新指令 / 実出力を記録
  制御完了 → watchdogを更新
```

注入は指令列の遅延で、8msのCPU待機ではない。計算・PWM書込み・watchdog更新は1msごとに続くため、4ms watchdogと矛盾しない。STOPや電源異常は遅延線を通さず、その場でLL停止し履歴を破棄する。古い指令が再ARM後に出ないよう再初期化する。ARM前は履歴をゼロとし、充填前の指令を出した周期は識別する。起動過渡を全条件で同じ手順にし、途中停止を隠さない。

正確に制御できるのは**kという周期差**。IMU周期の誤差、制御リリースの揺れ、PWM反映待ちがあるため「ぴったり8.000msの物理遅延」と断定しない。欠測・処理落ち・サンプル番号不一致は記録し、その周期を予定どおりの注入成功と数えない。乱数は事前生成する。PIDの係数・積分処理を条件ごとに調整せず、飽和と実際に出した指令もログに残す。

## watchdog後のログ保持

通常の.bssにログを置かない。リンカで専用 `.research_log (NOLOAD)` と `RAM_LOG` 領域を予約し、**C/FMP3の起動ゼロクリア・データコピー・スタック・ヒープ・推論arenaから除外**する。名前だけ`.noinit`にしてもリンカと起動処理が除外しなければ保持できない。Bootrom・起動スタックが使用する領域も避け、mapで確認する。試行間もログ領域の配置を固定する。

開始予算は物理ログ16byte×200Hz×20秒=64,000byte、詳細タイミング32byte×2048リング=65,536byte（直前約2.048秒）、ヘッダー512byte、計130,048byte。32byte内に有効性／シーケンスも含める。詳細タイミングの全20秒は外部測定と集計で補い、リングで全時間を保持したとは言わない。520KBからログ・推論arena・RTOS・スタック・その他データを引いて余裕を確認する。

Core0のみがログを書く。レコードは本文→メモリ順序バリア→32bitコミット番号の順で確定し、次のスロットの旧コミットを先に無効化する。回収時は範囲・世代・シーケンス・チェック値を検証し、途中の1件は捨てて直前までを回収する。ログ処理量とチェック処理は全比較で同じにする。

通常Flash起動とSDK標準のシステムwatchdogリセットを使用する前提で、scratch0=実験magic/版、scratch1=状態/最後の処理段階/明示停止理由、scratch2=試行番号、scratch3=最後のコミット番号を割り当てる。**scratch4～7はSDK/Bootrom用に触らない。** RP2350の特殊BOOTSEL/RAM_IMAGE/FLASH_UPDATE起動ではscratch2/3にも意味があるため、実験ログ用途と混在させない。

各周期の処理段階をscratch1へ先に記録する。CPUが固まった後には停止理由を書けないので、再起動側でwatchdogリセット情報と最後の段階を組み合わせ、`WDT_TIMEOUT＋最終段階`として報告する。これだけで固まった根本原因まで確定したとは扱わない。

再起動時はモーターをLLに保ち、reset原因・scratch・ログmagic/版/世代を**再初期化や再ARMより先に**確認する。有効ログがあれば回収専用状態へ入り、Core1負荷を始めず、USBへ保存して確認後に新試行を明示開始する。検証不能なら「ログ保持失敗」と記録する。

保持対象は、電池接続中のwatchdogリセットと、モーター電源スイッチOFFによる停止。v5ではモーター電源スイッチが制御系を切らないので、試行を途中で止めてもPicoは電池給電で動作を続け、RAMログはそのまま残る。電池の取り外し・MASTER_SW（追加する場合）のOFF・RUNリセット・chip-level reset・brownout・デバッガによる再書込みまで保持を保証しない。**試行中はUSB非接続を標準条件**とし、ログは試行後に電池を接続したままUSBをつないで回収する。保存を確認するまで電池を抜かない。

USBケーブルを試行中に機体へ接続しないため、ケーブルの外力・取り回しは交絡要因から外れる。USBを挿したまま行うデバッグ試行は別条件として記録し、比較データへ混ぜない。USBの挿抜空間は [設計・配置v5](倒立ロボット_設計レビューと配置_v5.md) に従う。

### 実装後に必須の確認

1. 特定パターンのログを書き、watchdogを故意に未更新にして再起動。パターン、scratch、世代が保持され、モーターがLLのまま回収状態へ入ることを確認。
2. ログの途中書込みでリセットを起こし、不完全な末尾だけ破棄して回収できることを確認。
3. cold boot、電源断、RUN、USB再接続を試し、古い／不正ログを新試行へ混入しないことを確認。
4. k=0/1/2/3/5/8の元サンプル番号を外部波形と照合。8周期遅延でもwatchdog更新が1周期ごとに続くことを確認。
5. CYCCNTと外部計測の差、PIO取得時間、計測コードの負荷をCore1アイドル／バス負荷で測る。
6. USBなしで試行し、モーター電源スイッチOFFで停止させた後、USBを接続してログを回収できることを確認。USB接続時にPicoがリセットされないことも確認する。
