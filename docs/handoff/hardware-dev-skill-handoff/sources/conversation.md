「ピンヘッダーがあるのでこの向きでは使えない」

「ジャンパ線を挿したら高さが足りない」

「ケーブルがこちら側から出るので設計変更が必要」

などの問題が後から発生し、何度もモデル修正が必要になった。

このような、

**作る前に聞けば防げた手戻り**

を減らすことが、このSkillの最大の目的である。

---

# 3. 基本思想

AIは、ハードウェア開発時に単なる「質問への回答者」として振る舞うのではなく、

1. 要求を聞き出す
2. 不足・矛盾・未決定事項を発見する
3. システム全体として成立する計画を作る
4. 具体設計に必要な実装条件を確認する
5. 条件が揃ってから設計・実装へ進む
6. 試作結果を受け取って改善ループを回す

という順序で動いてほしい。

重要なのは、

**ユーザーが質問した項目だけを見るのではなく、最終目的から逆算して「まだ何を確認する必要があるか」をAI側から考えること。**

ユーザーが知っていることを答えさせるだけでは不十分。

ユーザー自身が存在を認識していない論点、つまり「何を質問すべきかすら分かっていない項目」をAI側から発見してほしい。

# 4. 開発プロセス

こういうやつ作ろうと思ってるのよ。

ここまでおｋ？

### AI（回答）

**ここまでOK。実際に起きた手戻りと、Skillで改善したい行動がつながっている。** 「最終目的から必要な条件を見つけ、具体設計の前に確認する」という軸で進めていい。

開発プロセスに入れる前に、次の3点を明確にすると使いやすくなる。

1. **AIが調べることと、ユーザーに聞くことを分ける。** 公称寸法や仕様はAIが調べ、手持ち部品の加工状態・接続方向・使い方はユーザーに確認する。
2. **未決事項は、影響する作業だけを止める。** コネクタの高さが未確認なら、その収納部分の確定を待つ。独立した回路検討や単体試験は進められる。
3. **確認済み・実測・仮定・未決を区別して残す。** 試験では「コードに停止処理がある」と「実機で停止を確認した」も分ける。次の設計が何を根拠にしているか追えるようにする。

特に「条件が揃ってから設計へ進む」は、**その設計を確定するために必要な条件が揃ったら進む**という意味にすると、質問ばかりで止まるのを防げる。

**次の「4. 開発プロセス」は、各工程の「確認すること・残す記録・次へ進める条件」をセットで整理するといい。**
