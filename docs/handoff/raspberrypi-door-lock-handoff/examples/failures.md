# 手戻り・失敗の分析

## F01 — ビルド成功と実機動作を分離する
- **証拠**：[C004–C008](../sources/conversation.md#c004)、[C010–C018](../sources/conversation.md#c010)
- **何が起きたか**：ビルド成功通知の後、Piでpigpio初期化失敗・native SIGSEGVが出て、HTTP応答後もサーボが動かない事象が報告された。
- **原因の分析**：ビルドはPi固有のネイティブGPIO、USB、権限、配線を検証しない。
- **作る前に防げたか**：実機動作は実際に試すまで不明。検証範囲の説明不足は防げる。
- **改善候補**：ビルド、Pi起動、HTTP、入力イベント、GPIO指令、実際の駆動を別段階として報告する。
- **評価**：E01、E07

## F02 — 診断依頼を変更許可と取り違えない
- **証拠**：[C009](../sources/conversation.md#c009)、[C016–C020](../sources/conversation.md#c016)
- **何が起きたか**：ユーザーは先輩版で鍵は動いていた、自作コードでもセンサー不調は続いたと説明し、コード変更前に相談したいと明言。後に管理画面では開錠でも物理モータが動かない事象を報告。
- **原因の分析**：症状の層（入力、解錠判定、GPIO、駆動回路、機械機構）を区別する必要がある。ログの指令は物理駆動を証明しない。
- **作る前に防げたか**：判断できない。物理原因は測定が必要だが、作業境界の確認は事前にできる。
- **改善候補**：変更目的・残す差分・復元範囲を先に確認。診断のみの依頼なら非破壊観測にとどめる。
- **評価**：E02

## F03 — USB列挙を入力正常の証拠にしない
- **証拠**：[C021–C022](../sources/conversation.md#c021)、[C026–C029](../sources/conversation.md#c026)
- **何が起きたか**：USB一覧でデバイスが見えるのに、カード入力がアプリログに出ない症状があった。FeliCaの同期USB転送待ちがスレッドダンプにあった。
- **原因の分析**：列挙成功は転送・OSイベント・アプリ受信の正常性を保証しない。故障層はログだけで確定できない。
- **作る前に防げたか**：判断できない。再現時の観測・トレースが必要。
- **改善候補**：USB列挙→転送→evdev→アプリ読取→認証を分けて観測し、一覧表示から正常と断定しない。
- **評価**：E03

## F04 — アイドル時間だけを理由に電源断しない
- **証拠**：[C021–C023](../sources/conversation.md#c021)、[C032](../sources/conversation.md#c032)
- **何が起きたか**：最終タッチから60分でUSB電源をcycleする仕組みが記録され、1時間ごとの反復と複数reopenedログがあった。
- **原因の分析**：無操作は故障の証拠ではない。定期切断や重複再オープンを生んだ可能性（後者は仮説）。
- **作る前に防げたか**：防げた。故障判定条件と復帰プロトコルを先に定義できる。
- **改善候補**：アイドルでなく実応答失敗を基準にする。転送停止・ハンドル解放後、一回だけ再列挙／再オープンし、読取テストで復旧を判定。
- **評価**：E04

## F05 — service restartとPi rebootを混同しない
- **証拠**：[C040–C041](../sources/conversation.md#c040)
- **何が起きたか**：journalctlにkeylocker unitのstop/startが短時間に二組。ユーザーはPiの二度再起動はしていない認識、pgrepではJava一つ。
- **原因の分析**：unit lifecycleはOS bootと異なる観測。screen介在時のunit statusはアプリ実プロセスとずれることもある。
- **作る前に防げたか**：防げた。
- **改善候補**：boot ID／boot一覧、unit journal、JVM起動、プロセス数を同一時刻範囲で比較し、各コマンドの証拠範囲を説明。
- **評価**：E05

## F06 — 初心者が実行可能な診断コマンドにする
- **証拠**：[C006](../sources/conversation.md#c006)、[C013](../sources/conversation.md#c013)、[C028–C029](../sources/conversation.md#c028)
- **何が起きたか**：誤ったCLI入力があり、Windows PowerShellのcurl別名でUriを促された。grepはログをbinary扱いし、`-a` が必要だった。
- **原因の分析**：OSや端末ごとのCLI差は初心者に自明でない。出力にNUL等があるとgrepの表示も変わる。
- **作る前に防げたか**：防げた。
- **改善候補**：端末（Pi SSH / PowerShell）を指定し、コピー可能な一つのコマンドと期待出力を示す。
- **評価**：E06

## F07 — 検知・復旧操作・実復旧を別々に計る
- **証拠**：[C028–C032](../sources/conversation.md#c028)、[C036](../sources/conversation.md#c036)
- **何が起きたか**：USB抜き差しでは復旧せず、Pi再起動後に復旧したとの報告。別の期間にはフリーズ検出とUSB電源サイクルがログにあった。
- **原因の分析**：転送、ハンドル、デバイス状態のどれが原因かは提示記録では確定しない。検知ログだけではカード読取復帰を証明しない。
- **作る前に防げたか**：判断できない。
- **改善候補**：復旧操作の前後に診断情報を保存し、再オープンとテストカード読取を独立の成功基準にする。
- **評価**：E03、E04
