# プロジェクト概要

[会話記録](../sources/conversation.md)の70ターンで何をしていたか、どこまで到達したかをまとめる。事実と分析は区別して書く。実機の状態を直接確認した記録は少なく、ほとんどはユーザーが貼ったログと報告に基づく。

## 何を作っていたか

研究室のドアに付いている電子ロックの保守である。先輩が作ったシステムを、卒業後に後輩（ユーザー）が引き継いだ。

- FeliCa カードと磁気カードで解錠する
- サーボモーターで物理的に施錠・解錠する
- ドアベルのボタンを押すと Discord に通知が飛び、同じ機器上の別プロセスが音を鳴らす
- Web の管理画面でカードの登録と履歴を見る

最初の依頼は、「先輩のコードと、自分が手を入れたコードを比べて、Discord bot の対応だけを残して他は元に戻したい」だった。その後、実機へ反映して起きた障害の調査と、FeliCa・磁気リーダーの無反応への対策が、会話の大半を占める。

**止まると、朝一番に来た人が部屋に入れない。** 中からは出られるため、閉じ込めは起きない（C012）。

## 目的

- 依頼の直接の目的：Discord bot の互換性対応を残し、FeliCa 周りの自作コードを元に戻す（C001）
- 会話中に加わった目的：実機障害の復旧（C011〜C028）、FeliCa・磁気リーダーの無反応の解消（C029〜C031、C044 以降）、Discord 通知の改修を後輩へ引き継ぐ資料づくり（C034〜C041、C060）、AI 開発ツールの運用設定（C063〜C066、C069）

## 技術構成

| 領域 | 内容 |
| --- | --- |
| 言語・ビルド | Kotlin Multiplatform（JVM 側が本体、JS 側は管理画面）、Gradle 7.1（wrapper）、Kotlin 1.6.10 |
| サーバー | Ktor（Netty）、SQLite（Exposed） |
| GPIO | pi4j 2.1.1（pigpio プラグイン）。サーボは PWM、ドアセンサ・ボタン・LED はデジタル入出力 |
| FeliCa リーダー | Sony RC-S380 を usb4java（javax.usb）で直接制御する、外部から移植したドライバ |
| 磁気リーダー | USB の疑似キーボード。`/dev/input` のイベントを直接読む |
| Discord | JDA 5.0.0-beta.12（Kotlin 側、通知の送信）。別の Python プロセス（discord.py）が通知を拾ってボイスチャンネルで音を鳴らす |
| 運用 | systemd の unit、`screen` 経由で起動、`tee` でログをファイルへ。ログは日次ローテーション |

## 実行環境

| 項目 | 内容 |
| --- | --- |
| 本番機 | Raspberry Pi 3 Model B（64bit、4コア、メモリ1GB）、Debian 11 系、JDK 17.0.14 |
| 開発機 | Windows 11、JDK 17、PowerShell と Git Bash |
| 本番機への接続 | ユーザーが SSH で操作する。AI の環境からは鍵認証が通らず接続できない（C050） |
| デプロイ | `./gradlew shadowJar` → `scp` → `systemctl restart`。ユーザーが実行する |
| 検証手段 | `compileKotlinJvm` と `shadowJar` のみ。自動テスト、CI、lint はない（S01） |

**実機（GPIO と USB）に依存するため、手元で動作を確認する方法がない。** これが、この会話で手戻りが実機を動かすまで分からなかった主な理由である（分析）。

## 到達点

### 確認済み（ユーザーが貼ったログ・報告に基づく）

- 修正版 jar の起動、管理画面（HTTP 200）、磁気カードでの解錠（C022、C053）
- ログが復活した（C026）
- サーボ設定値を戻すと動作した（C028 の「これでおｋ」、ユーザー報告）
- FeliCa のフリーズ検知が実際に発火し、約19秒で自動復帰した（C048）
- 修正後の運用で、フリーズ検知が0件になった（C062）
- FeliCa の応答時間が、全期間で 16〜18 ms（正常時の基準 17.0 ms）に収まる（C062）
- 磁気リーダーのイベント境界ずれの記録がなく、起動も9日間で1回だった（C049）
- 無条件のウォッチドッグを削除すると FeliCa が約2日半無反応のままになり、USB ポートの電源断で復旧した（C052〜C055）

### 未確認

- 40分停止（C068）の原因：ログの途絶以外に、機序を示す直接の証拠はない。修正（cdd9f74）も、会話の終了時点で実機に反映されていなかった（C068、C070）
- USB を抜いた場合の挙動：欠陥の修正（C058）は、実機で試していない。ユーザーが抜き差ししたと述べた時期と、ログのUSBエラーの少なさは、食い違ったまま
- RF 停止を応答時間で検知できるか：まだ起きておらず、判定できない（C059、C062）
- JDA を更新すると Discord の常時接続が直るか：後輩への引き継ぎとして残っており、実施していない（C038、C060）。原因として挙げた Discord 側の仕様変更は、確認していない（F12）
- 磁気リーダーの「システムから見えなくなる」症状への対策の効果：該当の事象が記録に出ていない
- 二重に再起動が実行されたこと（C070）は、アプリの二重起動ではなかった

## 会話外の事実（リポジトリのコミットログ）

この会話の後に、同じリポジトリへ FeliCa の初期化・復旧に関するコミットが追加されている。コミットメッセージだけが確認でき、内容と、会話中の修正との関係は確認していない。会話の範囲外なので、分析には使っていない。

- `2231edf` FeliCaの初期化で止まると全体が停止する問題を修正
- `1101864` FeliCaの初回復旧と古いエラー通知の競合を修正
- `c643c82` FeliCa監視の例外耐性とブロッキング処理を改善

## Skill 開発に関わる観察（今回の分析）

- ハードウェアに依存し、テストが書けない保守作業である。検証の手段が「ビルド成功」と「実機でのログ」しかなく、前者は動作の証拠にならない（G10）
- 障害の多くは、ユーザーが覚えていない実機側の変更（常駐プロセス、設定値）、または、冗長に見える安全装置の撤去で起きた（F01、F07、F11）
- 同じ種類の誤りが、会話の中で複数回起きた：「相関を因果と読む」（F02、F07）、「自分の修正の影響を机上で確認しない」（F08、F11）
- 失敗の直後に、AI は誤りを認めて直した（G08）。ただし、防げた誤りが多い
- ドメインは、組込み機器（ファームウェアに近い層）、運用スクリプトとログ、Web サーバー、外部 API の連携にまたがる。Skill の評価ケースは、ハードウェア固有の語に依らず書いた（[評価ケース](../evals/cases.md)）
