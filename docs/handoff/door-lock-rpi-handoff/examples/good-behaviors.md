## G01 判断が分かれる所で質問し、答えに従った

- **証拠**：[C003](../sources/conversation.md#c003)〜[C006](../sources/conversation.md#c006)
- **何が起きたか**：差分の分類で、意図が分からない2点（GPIO の書き換え、磁気リーダーの自動再接続）を質問した（C003）。ユーザーは「pi4jのまま」「磁気はそのまま残す」と答え（C004）、AI はその通りに実装した。リポジトリの共有先も、権限の有無を質問した（C005〜C006）。
- **なぜ良いか**：「bot以外を戻す」という依頼文だけでは、GPIO の書き換えが対象かどうか決められなかった。ユーザーしか知らない判断だけを質問し、選択肢を示した。
- **注意**：質問の形が「戻してよいか」にとどまったため、実機側の付随変更は漏れた（[F01](failures.md#f01)）。
- **評価**：[E01](../evals/cases.md#e01)

<a id="g02"></a>
## G02 元に戻す前に、現状を保存した

- **証拠**：[C004](../sources/conversation.md#c004)
- **何が起きたか**：zip を展開しただけで履歴の無い作業フォルダーに対し、`git init` して現状をベースラインとしてコミットした（3e639ae）。そのうえで5ファイルを元に戻し、2つ目のコミット（e3cf12a）にした。
- **なぜ良いか**：戻す作業が間違いでも、元の状態に戻れる。実際、のちに GPIO を巡って方針が揺れたが、履歴が残っていたので議論できた。
- **評価**：[E01](../evals/cases.md#e01)

<a id="g03"></a>
## G03 本番機への操作は実行せず、確認を求めた

- **証拠**：[C009](../sources/conversation.md#c009)、[C010](../sources/conversation.md#c010)、[C050](../sources/conversation.md#c050)、[C063](../sources/conversation.md#c063)
- **何が起きたか**
  - ビルドまでは実行し、研究室のドアを制御する実機への `scp` と `systemctl restart` は、実行前に「実行してよいか」「環境から届くか」を確認した（C009）。ユーザーは自分で実行すると答えた（C010）。
  - 後に、環境から SSH を試みたが鍵認証が通らず、AI は無理に進めず手順を提示した（C050）。
  - 規則の確認（C063）で、デプロイは AI の範囲外と整理し、ビルドまでを担当することを確認した。
- **なぜ良いか**：失敗したときに人が部屋へ入れなくなる系で、確認なしに本番へ反映しなかった。認証が通らなかったときに別の手段を探さなかった。
- **評価**：[E13](../evals/cases.md#e13)

<a id="g04"></a>
## G04 共有・コミットの前に、秘密情報を検索で確認した

- **証拠**：[C042](../sources/conversation.md#c042)、[C051](../sources/conversation.md#c051)、[C069](../sources/conversation.md#c069)
- **何が起きたか**：リポジトリを後輩に共有する前に、追跡ファイルと全履歴を検索し、トークンや秘密値が入っていないことを確認した（C042）。設定ファイルの控えを `deploy/` に追加するとき（C051）と、引き継ぎ資料をコミットするとき（C069）も、秘密情報のパターンで検索してからコミットした。実トークンは伏せたプレースホルダにした。
- **なぜ良いか**：共有や公開の前の確認が、手順に入っている。
- **補足**：この会話では、ユーザーが `application.conf` の全文を貼り付けて、トークンが会話に出ている（C027）。AI は値を繰り返さず、再発行を助言した（C034）。
- **評価**：[E10](../evals/cases.md#e10)

<a id="g05"></a>
## G05 一次情報（依存関係の解決結果、バイトコード）で原因を確定した

- **証拠**：[C025](../sources/conversation.md#c025)、[C044](../sources/conversation.md#c044)
- **何が起きたか**
  - ログが全て消えた原因を、推測せずに `gradlew dependencies` の解決結果で調べ、`slf4j-api` が 2.0.7 に引き上げられていること、その引き上げ元が `lavaplayer` であることを確認してから、バージョンを固定した（C025）。
  - フリーズの原因を、ライブラリのクラスを展開して `javap -c` でバイトコードを読み、読み取り転送のタイムアウトが無限リトライになっていること、脱出口が `isAborting()` だけであることを確かめた（C044）。
- **なぜ良いか**：原因が「推定」ではなく、コードの事実になった。この確認があったので、以前の自作コードの `withTimeoutOrNull` が効かなかった理由も説明できた。
- **注意**：バイトコードで確認できたのは `abort()` の構造まで。電源断直後に戻るかは実機の問題で、のちに停止の原因になった（[F11](failures.md#f11)）。
- **評価**：[E15](../evals/cases.md#e15)

<a id="g06"></a>
## G06 反論を受けて主張を撤回し、直接の証拠を取りに行った

- **証拠**：[C015](../sources/conversation.md#c015)、[C016](../sources/conversation.md#c016)、[C017](../sources/conversation.md#c017)
- **何が起きたか**：AI が過去のログから「pigs方式を維持すべき」と提案した（[F02](failures.md#f02)）。ユーザーが「先輩のコードで鍵自体が止まったことはない」と反論すると、AI は自分の主張が状況証拠に基づく推測だったと認めた。そして、今日の失敗そのものの出力を取るために、`screen` も `tee` も通さず直接実行するよう依頼した。
- **なぜ良いか**：主張を守らず、ユーザーの経験を新しい情報として扱った。実際の出力が、`PI_INIT_FAILED` という別の原因を示した。
- **評価**：[E02](../evals/cases.md#e02)

<a id="g07"></a>
## G07 推測にラベルを付け、判定を保留する実験を設計した

- **証拠**：[C046](../sources/conversation.md#c046)、[C056](../sources/conversation.md#c056)、[C059](../sources/conversation.md#c059)、[C067](../sources/conversation.md#c067)
- **何が起きたか**
  - 物理側の解説（C046）で、リーダーが固まる原因の候補を「ここからは推測です」と書いて挙げた。
  - RF 停止を応答時間で検知できるか（C056）は、AI が「当たり外れは次に起きるまで分からない」と書き、ユーザーは判定せずに記録だけ入れるよう依頼した（C059）。AI は判定ロジックを入れず、正常時の基準値と、当たりの条件、外れの条件を示した。
  - 停止の原因を聞かれたとき（C067）は「動作中のjarの上書きが原因では」と推測を述べつつ「推測なので、まずログを見せてください」と書いた。その推測は後で外れた（C068）。
- **なぜ良いか**：推測を事実として扱わず、確認の手順と合わせて出した。外れても失うものが少ない実験にした。
- **評価**：[E16](../evals/cases.md#e16)

<a id="g08"></a>
## G08 自分の誤りを開示し、訂正した

- **証拠**：[C054](../sources/conversation.md#c054)、[C057](../sources/conversation.md#c057)、[C062](../sources/conversation.md#c062)、[C068](../sources/conversation.md#c068)
- **何が起きたか**：ウォッチドッグを削除した判断が誤りだったこと（C054）、自分の生存判定に欠陥があったこと（C057）、`git add -A` で無関係なファイルを巻き込んだこと（C062）、自分の修正が40分の停止を招いたこと（C068）を、ユーザーに指摘される前か、ログで明らかになった直後に自分から述べ、直した。
- **なぜ良いか**：ユーザーが原因を探す手間が減った。
- **注意**：開示は事後である。誤りの多くは [F07](failures.md#f07)、[F08](failures.md#f08)、[F10](failures.md#f10)、[F11](failures.md#f11) のように、事前に防げた可能性がある。

<a id="g09"></a>
## G09 ユーザーが絞った範囲に従った

- **証拠**：[C039](../sources/conversation.md#c039)、[C040](../sources/conversation.md#c040)、[C041](../sources/conversation.md#c041)、[C056](../sources/conversation.md#c056)
- **何が起きたか**
  - ユーザーが「鍵の方の問題は俺がやるからいい」と言うと（C039）、鍵・センサの項目を資料から外し、Discord の項目だけに絞った。
  - 「ここだけはこっちでやろう」と言われると（C040）、その項目だけを実装し、他の項目に手を出さなかった。
  - 「終わったことは消して」「トークンの話は消して」（C041）、「経緯はいらん」（C056）にも従った。
- **なぜ良いか**：ユーザーの方針変更を、AI の誤りとして扱わず、そのまま反映した。

## G10 ビルド成功と実機での動作を区別して報告した

- **証拠**：[C008](../sources/conversation.md#c008)、[C010](../sources/conversation.md#c010)、[C023](../sources/conversation.md#c023)、[C045](../sources/conversation.md#c045)、[C068](../sources/conversation.md#c068)
- **何が起きたか**：コンパイルやビルドが通ったことを報告するとき、実機で確認すべき項目（サーボ、ドアセンサ、FeliCa、ドアベル、起動ログ）を毎回挙げた。再発した障害の検証方法として、USB を抜いて15秒後にログが出るかを示した（C045）。「実機に反映されていない」ことも指摘した（C068、C070）。
- **なぜ良いか**：テストが書けない対象で、ビルド成功を動作の証拠として扱わなかった。

<a id="g11"></a>
## G11 変更の効果を、実機のログで検証して報告した

- **証拠**：[C048](../sources/conversation.md#c048)、[C049](../sources/conversation.md#c049)、[C062](../sources/conversation.md#c062)
- **何が起きたか**：運用後のログから、フリーズ検知が実際に発火して約19秒で復帰した記録（C048）、フリーズが1日7〜8回あったこと（C049）、応答時間が全期間で16〜18ms に収まること、フリーズが0件になったこと（C062）を、成果と問題に分けて報告した。ログのコマンドも、古い分を含めて時系列に並べる形で提示した。
- **なぜ良いか**：「動いているはず」ではなく、記録で効果を確かめた。次に比較する基準値も得られた。

<a id="g12"></a>
## G12 失敗の後、手順を規則にして再発を防いだ

- **証拠**：[C064](../sources/conversation.md#c064)、[C066](../sources/conversation.md#c066)、[S05](../sources/snapshots/S05-ai-workflow.md)
- **何が起きたか**：`git add -A` の失敗（F10）の後、ユーザーの求めで、変更ファイルを個別に stage し `git diff --cached` で確認することを規則に追加し、その手順で規則自体をコミットした（C064）。レビュー運用の変更（C066）も、規則と運用文書を同時に更新し、2つの指示ファイルが同一であることを確認した。
- **なぜ良いか**：同じミスを、記憶ではなく文書で防げる形にした。
- **評価**：[E10](../evals/cases.md#e10)
