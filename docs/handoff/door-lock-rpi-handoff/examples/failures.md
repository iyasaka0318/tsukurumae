# 手戻り・失敗の分析

対象は、Raspberry Pi 上で動く電子ロックの保守を行った70ターンの会話である。各項目は次の形で書く。

- **証拠**：[会話記録](../sources/conversation.md)のターン（`Cxxx`）と、[保存済みファイル](../sources/README.md)（`Sxx`）へのリンク
- **何が起きたか**：事実だけ。出典を「ユーザー発言」「AI発言（要約）」「保存済みファイル」で区別する
- **原因の分析**：今回の分析であり、推測は推測と書く
- **作る前に防げたか**：防げた／実際に動かすまで分からなかった／判断できない
- **改善候補**：AIがどう振る舞えばよかったか
- **評価**：[評価ケース](../evals/cases.md)の番号

ユーザーが方針を変えた箇所（例：C040 で範囲を絞る、C066 でレビュー運用を簡略化）は誤りに数えていない。AI発言は逐語ではなく要約なので、細かい言い回しを根拠にする場合は元の会話に当たること。

## F01 元に戻す前に、実機側の常駐プロセスと設定を確認しなかった

- **証拠**：[C003](../sources/conversation.md#c003)、[C004](../sources/conversation.md#c004)、[C011](../sources/conversation.md#c011)、[C017](../sources/conversation.md#c017)〜[C019](../sources/conversation.md#c019)、[C023](../sources/conversation.md#c023)、[C026](../sources/conversation.md#c026)〜[C027](../sources/conversation.md#c027)
- **何が起きたか**
  - AI発言（要約）：C003 で、差分から GPIO 制御が pi4j から `pigs` コマンド方式に書き換えられていると分かった。`pigs` は pigpio デーモンをコマンドラインから叩く方式だと説明し、「pi4j自体が動かなくなっていたなら戻すと全滅しうる」と警告して質問した。
  - ユーザー発言：「pi4jのままで今も動く」（C004）。AI は3ファイルを元の pi4j 版に戻した。
  - ユーザー発言：デプロイ後に「なんも動かんくなった」（C011）。
  - ログ：pi4j の初期化が `PI_INIT_FAILED` で失敗した（C017）。`pigpiod` が有効化されたまま起動していた（C018）。さらに、デーモンを止めて `sudo` で実行すると起動したが、サーボは動かなかった。`application.conf` のサーボ位置が `pigs` 向けに 2.55 倍した値（15、28）のまま残っていたためだった（C026〜C027）。
  - ユーザー発言：「ラズパイ側でしか見れないプログラムもある程度変えた覚えがある」（C019）。
- **原因の分析**
  - コードを元に戻す変更に、ユーザーが実機側で行った変更（常駐デーモン、設定値）が付随していた。AI が確認したのはコードの差分と、ユーザーの記憶に基づく「pi4jは動くか」だけだった。
  - ユーザー自身が付随する変更を忘れていた（C019）。質問の形が「戻してよいか」だと、記憶に頼った回答しか得られない。
  - 推測：`pigs` がデーモンを必要とする点は AI の説明に含まれていたので、「デーモンが残ったまま pi4j に戻すとどうなるか」はデプロイ前に問えた。
- **作る前に防げたか**：一部防げた（推測）。デーモンの有無と設定値は、実機で `systemctl status` と `cat application.conf` を確認すれば分かる。ただしユーザーの記憶が曖昧な状況で、実機を見る前に確定できたかは判断できない。
- **改善候補**：「元に戻す」変更の前に、その変更に付随して実機側で変えたもの（常駐プロセス、設定ファイル、パッケージ）がないかを質問し、回答が曖昧なら実機で見るコマンドを先に出す。戻した後の起動手順に、環境差を確認する項目を含める。
- **評価**：[E01](../evals/cases.md#e01)

## F02 4か月前の1件のログを、原因として断定的に報告した

- **証拠**：[C015](../sources/conversation.md#c015)、[C016](../sources/conversation.md#c016)、[C023](../sources/conversation.md#c023)
- **何が起きたか**
  - ユーザー提供のログ（C015）：`keylog2.txt` の末尾に、2026-04-16 の JVM クラッシュ（`libpigpio` の `gpioRead` で SIGSEGV）が残っていた。今回の障害時の出力は含まれていない。
  - AI発言（要約）：「核心的な証拠が見つかった」「この4月のクラッシュこそ pigs 方式への書き換えの本当の理由では」と述べ、pi4j 関連3ファイルは戻さず `pigs` 方式を維持する提案をした。
  - ユーザー発言：「先輩のコードで動かしてても鍵自体が動かないなんてことはなかった」（C016）。
  - AI発言（要約）：C016 への返答で「状況証拠に基づく推測だった」と認めた。
  - その後の結果：今回の障害の原因は `pigpiod` の競合とサーボ設定値だった（F01）。SIGSEGV は終了時だけ起きる無害なクラッシュで、過去の `status=1/FAILURE` も同じだった（C023）。
- **原因の分析**：日付が4か月前の1件のログと現在の障害を結び付けた。ログの日付は AI 自身が示していた。推測を、見出しの強い言葉で事実のように述べた。
- **作る前に防げたか**：防げた。現在の障害の出力が取れていない時点で、過去のログは「候補」として扱える。
- **改善候補**：現在の障害の出力・再現と一致するまで、過去ログは原因として書かない。「見つかった事実」と「そこからの推測」を分けて報告する。反論を受けたら主張を維持せず、直接の証拠を取りに行く（[G06](good-behaviors.md#g06)）。
- **評価**：[E02](../evals/cases.md#e02)

## F03 本番と違う条件の再現結果から「ほぼ確定」と述べた

- **証拠**：[C017](../sources/conversation.md#c017)〜[C020](../sources/conversation.md#c020)
- **何が起きたか**
  - AI発言（要約）：`pigpiod` が有効なのを見て「それが原因でほぼ確定」と述べ、停止後に直接実行するよう依頼した。
  - ユーザーの実行結果：停止・無効化後も同じ `PI_INIT_FAILED`（C019）。AI が出したコマンドに `sudo` は付いていなかった。サービスは systemd（root）で動いている。
  - AI発言（要約）：C019 への返答で `sudo` の欠落に気づき、先輩の README にも `sudo java -jar` とあると述べて再実行を依頼した。`sudo` 付きでは初期化が通った（C020〜C022）。
- **原因の分析**
  - 手動再現の条件（実行ユーザー）が本番と違った。AI が提示したコマンドの欠陥で、ユーザーの操作ミスではない。
  - 推測：非 root でも `PI_INIT_FAILED` が出る可能性があり、`pigpiod` 停止の効果は切り分けられていない。最終的に何が決め手だったかは、会話からは断定できない。
- **作る前に防げたか**：防げた。コマンドを出す側が本番の実行主体を揃えられる。
- **改善候補**：手動再現は、本番の実行ユーザー、作業ディレクトリ、環境変数を揃えて指示する。単一の要因を「確定」と言う前に、要因を1つずつ動かした結果を見る。
- **評価**：[E03](../evals/cases.md#e03)

## F04 実行場所の書かれていない手順で、ユーザーが実行できなかった

- **証拠**：[C012](../sources/conversation.md#c012)、[C020](../sources/conversation.md#c020)、[C021](../sources/conversation.md#c021)
- **何が起きたか**
  - C011 への返答：4つのコマンドを1つのコードブロックで渡した。ユーザーは一部だけ実行してエラーになった（C012）。AI は1つずつ別ブロックで再提示した。
  - C020 への返答：「別のターミナルを開いて `curl -i http://localhost:8080`」とだけ書いた。ユーザーは Windows の PowerShell で実行し、引数入力待ちになった（C021）。AI は「ラズパイに SSH してから実行」と訂正した。
- **原因の分析**：ユーザーの環境（手元は Windows の PowerShell、対象は SSH 先のラズパイ）を前提に、どのマシンで実行するかを書いていなかった。`localhost` は実行場所で意味が変わる。
- **作る前に防げたか**：防げた。
- **改善候補**：コマンドには実行するマシンを明記し、貼り付けやすい単位（1コマンド1ブロック）で出す。PowerShell と Bash で挙動が違うコマンド（`curl`）には注意を添える。
- **評価**：[E04](../evals/cases.md#e04)

## F05 調査用のDEBUGログを既定で入れ、運用中のログを埋めた

- **証拠**：[C031](../sources/conversation.md#c031)、[C053](../sources/conversation.md#c053)、[C055](../sources/conversation.md#c055)
- **何が起きたか**
  - AI発言（要約）：磁気リーダーの修正（C031）で、1イベントごとの `mag event` を DEBUG で出すようにした。「多すぎればlogbackで抑制できる」とも述べた。
  - ユーザー提供のログ（C053）：貼付された末尾40行の大半が磁気リーダーの DEBUG 行だった。
  - AI発言（要約）：C055 で、磁気リーダーのログを INFO に抑制した。
- **原因の分析**：1回のスワイプで数十行が出る出力を、既定で有効にした。抑制の手段は事前に述べていたが、既定値を運用向けにしていなかった。
- **作る前に防げたか**：防げた。出力量は見積もれる。
- **改善候補**：調査用の出力は、既定で抑制するか、サンプリングや要約にする。後で抑制する前提なら、有効にした旨と戻し方をその場で伝える。
- **評価**：[E05](../evals/cases.md#e05)

## F06 診断した原因より広い範囲を、未検証のまま書き換えた

- **証拠**：[C031](../sources/conversation.md#c031)、[C048](../sources/conversation.md#c048)、[C062](../sources/conversation.md#c062)
- **何が起きたか**
  - AI発言（要約）：磁気リーダーの原因を「アプリ側の `onError` と内部の `scheduleReconnect` が二重に再接続している」と特定した（コードの読解）。修正は大幅な書き換えで、再接続経路の一本化に加えて、境界ずれの検知、デバイスノード変更の検知、`open` が連続して失敗したときの USB 電源断などを同時に入れた。検証はコンパイルのみだった。
  - ログ（C048、C062）：その後、磁気リーダーの `desync` や読み取りエラーは記録されず、9日間で起動ログは1回だった。
- **原因の分析**：二重再接続の修正以外は、ユーザーの症状から直接は導けない追加機能だった。結果として問題は出ていない。
- **作る前に防げたか**：判断できない。追加分が不要だったか、効いたかは、会話の範囲では分からない。
- **改善候補**：診断した原因への修正と、念のための追加を分けて提示し、追加分は同意を取るか、別のコミットにする。
- **評価**：[E06](../evals/cases.md#e06)

## F07 検知できない故障を担う安全装置を、相関を根拠に削除した

- **証拠**：[C029](../sources/conversation.md#c029)、[C046](../sources/conversation.md#c046)、[C048](../sources/conversation.md#c048)〜[C049](../sources/conversation.md#c049)、[C052](../sources/conversation.md#c052)〜[C055](../sources/conversation.md#c055)
- **何が起きたか**
  - ユーザー発言（C029）：「通電してるだけの状態」「USBを抜き差しすると治る」。
  - AI発言（要約）：C046 で、USB は正常なまま RF（磁界）側だけが死ぬ可能性を、推測として挙げていた。この時点では観測されていない。
  - ログ（C049）：毎時の電源断が深夜に発動し続けていた。04:08:15 の電源断の約100秒後にフリーズ検知が出ていた。
  - AI発言（要約）：C049 で、毎時の電源断を「正常なリーダーを無駄に落としている」「誘発している疑い」として削除し、検知を5秒に短縮した（コミット 07d795a）。
  - ログ・ユーザー報告（C052〜C054）：その後の再起動（08-22 01:20）から 08-24 15:54 まで、FeliCa のタッチが0件、フリーズ検知も0件のまま無反応だった。
  - ユーザー報告（C055）：USB ポートの電源断で復旧した。AI は削除が誤りだったと認め、ウォッチドッグを元の設定で戻した。
- **原因の分析**
  - 「電源断の直後にフリーズした」1件の相関を因果として扱った。同じログの別の部分では、フリーズは電源断と無関係に1日7〜8回起きていた。
  - RF 停止は、リーダーが「カード無し」と同じバイト列を返し続けるため、検知ができない。復旧手段は電源断だけで、定期的に無条件で行うしかなかった。この前提は C046 の時点で AI が説明していた。
- **作る前に防げたか**：防げた。削除ではなく、閾値を緩める、設定で切り替えられるようにする、戻す条件と確認方法を付けて数日試す、といった選択肢があった。
- **改善候補**：冗長に見える保険を消す前に、それが拾っていた故障モードがないかを確認する。検知できない故障のための安全装置は、観測で不要と示せるまで残す。消す場合は、戻す条件と、効果を見るログを先に決める。
- **評価**：[E07](../evals/cases.md#e07)

## F08 自分が書いた生存判定が、失敗をnullに変換する呼び出し先を考慮していなかった

- **証拠**：[C029](../sources/conversation.md#c029)、[C045](../sources/conversation.md#c045)、[C057](../sources/conversation.md#c057)、[C058](../sources/conversation.md#c058)
- **何が起きたか**
  - AIの作業（C029 の進捗）：`RCS380.kt` を読んでいる。`sendCommand()` が `UsbException` を握り潰して `null` を返す実装だった。
  - AI が書いたフリーズ検知（C045）は、`sendCommand` の戻り値に関わらず「最後に完了した時刻」を更新していた。
  - ユーザー発言（C057）：「USB抜き差しでも治らなかったけど、それは何で？」。AI は自分のコードを見直し、USB を抜いた後も「生きている」と判定され続け、検知が発火しない欠陥を見つけた。修正した（8bd8eda、C058）。
  - ログ（C058）：2日半の無反応の間、USB エラーの記録は2件だけだった。AI は、その2日半は RF 停止（別件）で、抜き差しの欠陥は実在するが今回は踏んでいない、と整理した。ユーザーが抜き差しした時期との食い違いは、会話内で解決していない。
- **原因の分析**：呼び出し先が失敗を値に変換していることを読んでいながら、生存判定の条件にその知識を反映しなかった。
- **作る前に防げたか**：防げた。コードも呼び出し先も、書いた時点で手元にあった。
- **改善候補**：生存や成功を判定するコードを書くときは、呼び出し先が失敗をどう返すか（例外、null、エラーコード）を確認し、成功を示す戻り値のときだけ更新する。USB を抜かれる、応答しない、といった失敗経路を机上でたどる。
- **評価**：[E08](../evals/cases.md#e08)

## F09 文書に経緯を書き込み、ユーザーに削らせた

- **証拠**：[C055](../sources/conversation.md#c055)、[C056](../sources/conversation.md#c056)、[S04](../sources/snapshots/S04-readme.md)
- **何が起きたか**
  - AI発言（要約）：C055 で、README とコードのコメントに「一度削除して復活させた」経緯を含めて書いた。
  - ユーザー発言：「経緯はいらん。原因と結果だけ簡素に入れてくれ」（C056）。AI は削った（6f29f19）。
  - 以後、AI は原因と結果だけで書いている。
- **原因の分析**：文書の粒度についての方針をユーザーが述べていなかったため、AI が自分の判断で書いた。述べられた後は従った。
- **作る前に防げたか**：判断できない。好みは、聞くか、1回書いて見てもらわないと分からない。
- **改善候補**：README やコメントは、既定で「原因と結果」の短さにする。経緯が必要ならコミットメッセージに書く。ユーザーが文書の方針を述べたら、以後の文書に適用する。
- **評価**：[E09](../evals/cases.md#e09)

## F10 `git add -A` で無関係なファイルを巻き込み、確認せずpushした

- **証拠**：[C062](../sources/conversation.md#c062)、[C064](../sources/conversation.md#c064)
- **何が起きたか**
  - AI発言（要約）：C062 で、`git add -A` を使ってコミットし、push した（07265cd）。コミットには、ユーザーが別途導入した `AGENTS.md`、`CLAUDE.md`、`docs/AI_RULES.md`、`docs/AI_WORKFLOW.md` が混ざっていた。コミットメッセージは別の内容だった。
  - AI は push 後に気づいて中身を確認し、秘密情報が含まれていないことを確かめたうえで、自分のミスだと開示して分割するか質問した。
  - C064 で、ユーザーがルールを更新するよう求め、`git add -A` と `git add .` の禁止を規則に明文化した。
- **原因の分析**：直前まで同じコマンドを使っており、作業ツリーに他のファイルが増えたことに気づかなかった。`git status` を stage の前に見ていなかった。
- **作る前に防げたか**：防げた。
- **改善候補**：変更したファイルを個別に stage し、`git diff --cached` で確認してから commit する。push の前に `git status` を見る。
- **評価**：[E10](../evals/cases.md#e10)

## F11 実害のない現象を並行処理の変更で直し、40分の停止を招いた

- **証拠**：[C045](../sources/conversation.md#c045)、[C062](../sources/conversation.md#c062)、[C068](../sources/conversation.md#c068)
- **何が起きたか**
  - AI発言（要約）：C045 の実装前に `AbstractIrpQueue.abort()` のバイトコードを読み、進行中の転送の完了をタイムアウトなしで待つ作りだと確認したうえで、「リトライループがabort状態を見るので1秒以内に戻る」と述べた。電源断でデバイスが消えた直後にも戻るかは、実機で確認していない。
  - AI発言（要約）：C062 で、リーダーが二重に開かれる現象を「`open()` が先頭で `close()` を呼ぶので実害は出ていない」としたうえで、`@Synchronized` と「接続済みなら再接続を見送る」条件で直した（07265cd）。
  - ログ・ユーザー報告（C068）：次の電源断のあと、フリーズ検知の1行を最後に FeliCa 関連のログが40分途絶え、ユーザーが手動で再起動するまで復旧しなかった。
  - AI発言（要約）：原因を「`abort()` が戻らない → `@Synchronized` の `close()` がモニタを握ったまま → `open()` も待たされる → `isConnected()` が true のまま → ウォッチドッグが見送る」と推定し、打ち切りの追加とウォッチドッグの条件削除で修正した（cdd9f74）。実機での再現確認はない。
- **原因の分析**
  - 修正前の二重オープンを、AI 自身が「実害なし」と書いていた。その見た目の問題の修正が、復旧経路を1つ塞いだ。
  - 上の機序は推測。確認できた事実はログの途絶と、手動再起動で復旧したことだけである。
- **作る前に防げたか**：判断できない（一部は防げた）。実害のない現象に手を入れない判断は取れた。ロックと待ちの組み合わせは机上で検討できた。一方、電源断直後に `abort()` が戻らない現象は、実機でないと確認できない。
- **改善候補**：実害のない見た目の問題は直さない。復旧経路に手を入れるときは、「どこか1箇所が固まっても別の経路が必ず復旧する」ことを確認し、待ちを足すなら上限を付ける。「戻る」と述べた前提が未検証なら、そう書く。
- **評価**：[E11](../evals/cases.md#e11)

## F12 外部サービスの仕様変更を、一次情報で確認せず原因として述べた

- **証拠**：[C037](../sources/conversation.md#c037)、[C038](../sources/conversation.md#c038)
- **何が起きたか**
  - AI発言（要約）：Discord botの常時接続が壊れた原因として、「Discord が2024年後半にボイス接続の暗号化方式を変え、JDA 5.0.0-beta.12 はその前のバージョンなので対応できない」と述べた。チャット本文では「原因の見当がつきました」「症状と一致する」と書き、引き継ぎ資料には「推定」「要検証」と書いた。
  - 公式リリースノート等で確認した記録は、会話に残っていない。この仮説は会話内では検証されておらず、後輩に委ねられた（C038、C060）。
- **原因の分析**：外部サービスの仕様変更の時期と内容を、記憶に基づいて述べた。症状との一致は、原因の証拠として弱い。本文と資料で確信度の表現が違った。
- **作る前に防げたか**：判断できない。確認には、リリースノートの調査か、実際にJDAを上げて試す必要がある。
- **改善候補**：外部の仕様変更を原因として述べるときは、一次情報で確認するか、確認していないと明記する。確信度は、チャットと資料で揃える。
- **評価**：[E12](../evals/cases.md#e12)
