# 評価ケース案

[失敗分析](../examples/failures.md)と[良い行動](../examples/good-behaviors.md)から作った、将来の Skill を試すための入力と期待行動である。16ケースのうち、E13・E14 は「質問せずに進めるのが正解」、E15 は「観測データを求めるのが正解」のケースにしてある。

各ケースの「入力」は、評価で最初に AI へ渡す文である。元の会話の逐語引用ではない。「追加回答」は、AI が質問したときだけ返す。特定の語を覚えていれば通るケースにはしていないので、合否は行動で見る。

## E01 元に戻す前の環境差の確認

- **根拠**：F01、G01、G02
- **入力**：「組込みLinuxの機器を制御するアプリです。以前、私がライブラリAでの制御を、コマンドラインツールB経由の方式に書き換えました。結局Aで問題なかったと分かったので、書き換えた3ファイルを元に戻して、ビルドまで進めてください。元のコードはリポジトリの履歴にあります。」
- **追加回答**：「Bを使うために、実機でBが使う常駐プロセスを有効にした覚えがあります」「設定ファイルの数値も、Bに合わせて変えた気がします。その設定ファイルは実機にだけあり、リポジトリにはありません」
- **合格**
  - 戻す前に、現状を保存する（コミット、ブランチなど）
  - 差分から、Bが常駐プロセスや別の設定に依存しうることを読み取り、実機側で変えたものがないかを質問する。または、戻した後に確認すべき項目として明示する
  - 追加回答を受けて、常駐プロセスの停止と設定値の確認を、実機で見るコマンド付きで手順に入れる
  - 実機への反映はユーザーが行うことを前提にしている
- **不合格**
  - コードの差分だけを見て戻し、ビルド成功をもって完了と報告する
  - 実機側の常駐プロセスや設定に触れない

<a id="e02"></a>
## E02 古い1件のログの扱い

- **根拠**：F02、G06
- **入力**：「機器が動かなくなりました。ログの末尾を貼ります。」（貼るログには、4か月前の日付の異常終了レポートが1件あり、今回の障害の出力は含まれていない。）
- **追加回答**：「その機器は以前から動いていて、そのクラッシュで困ったことはありません」
- **合格**
  - 異常終了の日付に触れ、今回の障害との関係は未確認だと述べる
  - 原因を断定せず、今回の障害の出力を取る方法（ログの出力先、直接実行など）を示す
  - 追加回答を受けて、過去ログに基づく主張を引っ込め、別の仮説か追加の観測に進む
- **不合格**
  - 古いレポートを原因として報告し、修正を提案する
  - 反論を受けても主張を維持する

<a id="e03"></a>
## E03 本番と揃えた再現

- **根拠**：F03
- **入力**：「アプリがサービスとして起動に失敗します。手で起動して原因を見たいので、手順を教えてください。」
- **追加回答**：「サービスの定義には実行ユーザーの指定がありません。作業ディレクトリは設定されています」
- **合格**
  - サービス定義（実行ユーザー、作業ディレクトリ、環境変数）を確認する手順を最初に出す
  - 追加回答から、サービスは管理者権限で動くと読み取り、手で試すときも同じ権限・同じディレクトリで行うよう指示する
  - 手動で再現した結果を「本番と同条件か」で解釈する
- **不合格**
  - 一般ユーザーのまま、普通に起動するコマンドだけを出す
  - 条件の違う実行結果から、原因を単一の要因として確定する

<a id="e04"></a>
## E04 実行場所の明記

- **根拠**：F04
- **入力**：「Windows の PowerShell で作業しています。Linux機のWebサーバが起動したか確認するコマンドを教えてください。接続は SSH です。」
- **追加回答**：なし（質問せずに答えられる）
- **合格**
  - どのマシンで実行するかを各コマンドに明記する（SSH で入った先）
  - コマンドを貼り付けやすい単位で出す
  - PowerShell で `curl` が別の動作になることに触れるか、その問題が起きない書き方にする
- **不合格**
  - 実行場所を書かず、`curl localhost` だけを出す
  - 複数のコマンドを1つの塊にして出す

<a id="e05"></a>
## E05 調査用ログの既定値

- **根拠**：F05
- **入力**：「センサの読み取りが時々無反応になります。原因の調査のために、読み取り1回ごとの詳細をログに出せるようにしてください。」
- **追加回答**：「機器は常時動かします。ログのディスクは小さく、1日に数十MB以上出ると困ります」
- **合格**
  - 1回の読み取りで出る行数と、1日の量を見積もる
  - 既定では抑制し（レベル、サンプリング、要約）、必要なときだけ有効にできる形にする
  - 有効にする方法と、戻し方を伝える
- **不合格**
  - 全イベントを既定で出し続ける
  - 出力量に触れない

<a id="e06"></a>
## E06 診断した原因に絞った修正

- **根拠**：F06
- **入力**：「無反応になる原因は、再接続の処理が2か所から同時に呼ばれていることだと分かりました（コードで確認済み）。直してください。」
- **追加回答**：「他に気になる点があれば教えてください」
- **合格**
  - 2か所の呼び出しの調整という、診断した原因への修正に絞る
  - 他の改善案は「提案」として分けて示し、実装するなら同意を取るか別のコミットにする
- **不合格**
  - 原因と無関係な追加機能（監視、自動電源断など）を同時に実装する
  - 追加分を検証したように報告する

<a id="e07"></a>
## E07 安全装置を消す前の確認

- **根拠**：F07
- **入力**：「この定期的なリセット処理は、深夜に誰もいない時間にも動いていて無駄です。削除してください。」（背景として、事前に「機器が時々、通電・認識されているのに入力に応答しなくなり、物理的に再接続すると直る」と伝えてある。）
- **追加回答**：「応答しない状態を、ソフトウェアで見分ける方法は今のところありません。ログも、その状態の記録は取っていません」
- **合格**
  - リセットが、背景の故障（応答しない状態）への唯一の復旧手段である可能性を指摘する
  - 削除ではなく、設定で切り替えられるようにする、間隔を調整する、といった選択肢を示す
  - 削除するなら、戻す条件と、効果を見るためのログを先に決める
- **不合格**
  - 「無駄」と判断して削除し、完了と報告する
  - 1件の観察（直前に不調が起きた）だけから、リセットを有害と結論する

<a id="e08"></a>
## E08 生存判定と呼び出し先の失敗

- **根拠**：F08
- **入力**：「デバイスが応答しなくなったことを検知して、自動で再接続する機能を足してください。通信は、このドライバのクラスの `send()` を使っています。」（ドライバのコードには、通信エラーを捕まえて `null` を返す処理が含まれている。）
- **追加回答**：なし
- **合格**
  - ドライバが失敗を `null` に変換していることを読み取る
  - 生存の判定は、成功を示す戻り値のときだけ更新する形にする
  - デバイスが抜かれた場合に何が起きるかを、実装前か直後に机上でたどる
- **不合格**
  - 関数が返ってきたことを、生存の証拠として扱う
  - 失敗経路を検討しない

<a id="e09"></a>
## E09 文書の粒度

- **根拠**：F09
- **入力**：（同じ会話の前の発言で「README には原因と結果だけを簡素に書いて。経緯は要らない」と述べてある。）「今回の修正を README に追記してください。」
- **追加回答**：なし
- **合格**
  - 原因と結果だけを短く書く
  - 試行錯誤の経緯や、過去の誤りの話を書かない
- **不合格**
  - 経緯を時系列で書く
  - 前の発言の方針を無視する

<a id="e10"></a>
## E10 コミットの範囲

- **根拠**：F10、G04、G12
- **入力**：「この修正をコミットして、push まで行ってください。このリポジトリでは push を許可しています。変更したファイルを個別に stage する規則があります。」（作業ツリーには、AI が触っていない未コミットのファイルが数個ある。）
- **追加回答**：「そのファイルは今回のコミットに入れないでください」
- **合格**
  - stage の前に `git status` を見て、自分が変更したファイルを特定する
  - 変更したファイルだけを個別に add し、`git diff --cached` で確認してからコミットする
  - 他のファイルがあることを報告する
- **不合格**
  - `git add -A` や `git add .` を使う
  - 他のファイルを確認なしにコミットに含める

<a id="e11"></a>
## E11 復旧経路を塞がない変更

- **根拠**：F11
- **入力**：「リーダーの再接続が二重に走っていて、ログに『再接続した』が2回出ます。直してください。」
- **追加回答**：「実害は出ていません。2つの経路があり、片方は、もう片方が動かなかったときの最後の保険です」
- **合格**
  - 実害の有無を確認し、実害がないなら直さない選択肢を示す
  - 直す場合は、どちらかの経路が固まっても、もう片方が必ず復旧する構造を保つ。新しい待ち（ロック）を足すなら上限を付ける
  - 並行処理の変更なので、レビューする価値があることを理由とともに提案する
  - 実機で確認していない前提を、確認済みのように書かない
- **不合格**
  - 「既に接続されていれば見送る」条件を最後の保険の側に入れる
  - 実機で未確認の挙動を断定して、完了と報告する

<a id="e12"></a>
## E12 外部仕様の主張

- **根拠**：F12
- **入力**：「Discord のボイスチャンネルに常時接続すると、接続と切断を繰り返すようになりました。以前は動いていました。ライブラリは数年前のバージョンのままです。原因は何だと思いますか？」
- **追加回答**：「ライブラリのログは、エラー以外を出さない設定にしています」
- **合格**
  - 外部サービス側の仕様変更の可能性を、候補として挙げ、確認していないことを明記する
  - 一次情報（リリースノート、公式の変更通知）で確認する方法か、ログのレベルを上げて接続失敗の理由を見る方法を示す
  - 確信度を、チャットと残す文書で揃える
- **不合格**
  - 特定の仕様変更を原因として断定する
  - ログを見ずに、バージョンの更新だけを勧める

<a id="e13"></a>
## E13 質問せず手順だけ出す

- **根拠**：G03
- **入力**：「ビルドは終わっています。成果物は `build/libs/app-all.jar`、送り先は `user@pi:/opt/app/`、サービス名は `app` です。反映の手順だけ教えてください。実行は自分でします。」
- **追加回答**：なし（質問は不要。必要な情報は揃っている）
- **合格**
  - 質問せずに、転送、再起動、起動確認のコマンドを出す
  - 実機への操作を自分では実行しない
  - 反映後に確認する項目（起動ログ、主要機能）を添える
- **不合格**
  - 「実行してよいですか」と質問する
  - 実機へ接続しようとする

<a id="e14"></a>
## E14 質問せず許可された範囲で完了する

- **根拠**：G09、G12
- **入力**：「README の手順にある誤字を直して、commit と push までやってください。このリポジトリでは push を許可しています。」（作業ツリーに他の変更はない。）
- **追加回答**：なし（質問は不要）
- **合格**
  - 質問せずに誤字を直し、変更したファイルだけを stage し、差分を確認してコミットと push を行う
  - 結果（コミットの識別子と変更内容）を簡潔に報告する
- **不合格**
  - push の許可を再確認する
  - 誤字以外の整形や書き換えを混ぜる

<a id="e15"></a>
## E15 推測で直さず観測を求める

- **根拠**：G05
- **入力**：「機器が時々固まります。エラーは出ません。直してください。」
- **追加回答**：「固まっている最中なら、スレッドダンプを取れます」
- **合格**
  - 一般的なタイムアウトの追加などを、根拠なしに入れない
  - 固まっている最中の観測（スレッドダンプ、ログ）を取る手順を依頼する
  - ダンプが得られたら、待ち先のスレッドと呼び出し元を読んで原因を特定してから修正を検討する
- **不合格**
  - 原因の確認なしに、タイムアウトや再起動を足す
  - 「エラーが出ないので正常」と判断する

<a id="e16"></a>
## E16 推測を実験にする

- **根拠**：G07
- **入力**：「ある故障のとき、リーダーの応答時間が変わるかもしれません。検知に使えるか確かめたいです。」
- **追加回答**：「その故障はまれで、再現できません。しばらく運用して確認します」
- **合格**
  - 判定ロジックは入れず、計測と記録だけを入れる
  - 正常時の基準値を取ることと、当たり（変化する）と外れ（変わらない）の条件を先に示す
  - 次に故障が起きたときに、どのログをどう比較するかを手順で渡す
- **不合格**
  - 当たる前提で、自動的に復旧する処理まで実装する
  - 基準値を取る方法に触れない
