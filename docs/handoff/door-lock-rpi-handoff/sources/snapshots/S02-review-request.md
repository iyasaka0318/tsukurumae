## 何を直したのか

2026-08-28 10:13、USB ポートの電源断の直後に FeliCa が停止し、**40分間まったく復旧しませんでした**。手動でサービスを再起動するまで無反応でした。

ログはフリーズ検知の1行を最後に完全に途絶えています。

```
10:13:49.606  Power-cycling USB port 1-1.1:2.
10:13:56.113  felica reader frozen: no usb response for 6710ms. aborting transfer
              ← ここから40分、FeliCa 関連のログが1行も無い
10:53:26.633  FeliCa reader opened          ← 手動再起動
```

推定した機序は次の通りです。

1. 電源断でデバイスが消え、後始末の `RCS380.abort()` が usb4java 内部のタイムアウト無しの `wait()` から戻らなくなった
2. `FelicaService.close()` は `@Synchronized` なので、モニタを握ったまま停止した
3. 再接続の `FelicaService.open()` も同じモニタ待ちで停止した。だから `reopen failed` すら出ていない
4. `felicaReader` が null にならないため `isConnected()` が true を返し続けた
5. 直前のコミット `07265cd` で入れた「既に接続済みなら再接続を見送る」条件により、**最後の砦であるウォッチドッグが復旧を見送った**

対策は2つです。

- `reader.close()` と `reader.abort()` を別スレッドで実行し、5秒で打ち切る (`runBounded`)
- ウォッチドッグは `isConnected()` を見ず、必ず `close()` + 再接続を行う

## 特に見てほしい点

**1. `runBounded` が打ち切ったスレッドを放置している**

タイムアウト後もスレッドは生き続けます。デーモンスレッドなのでプロセス終了は妨げませんが、次の点が気になっています。

- 電源断は1時間ごとに起きます。毎回打ち切られた場合、スレッドが積み上がりませんか
- 放置されたスレッドは古い `RCS380` と USB インターフェースを掴んだままです。新しく `open()` した側と競合しませんか
- 放置されたスレッドが後から完了したとき、既に破棄された `FelicaReader` の状態を触って問題を起こしませんか

**2. `@Synchronized` との組み合わせ**

`FelicaService.open()` と `close()` は `@Synchronized` です。ブロッキング部分を別スレッドに逃がしたことでモニタ保持は最大5秒程度に収まる想定ですが、この読みが正しいか確認してください。ロックの粒度としてこれが妥当かも見てほしいです。

**3. 二重オープンが残っている**

ポーリング側のエラー経路とウォッチドッグの両方が `open()` を呼びます。`open()` が先頭で `close()` を呼ぶため実害はないと判断して**意図的に残しました**。一度この二重オープンを条件分岐で潰そうとして今回の停止を招いたので、慎重に判断しています。この方針が妥当か、あるいは競合が残っていないか見てください。

**4. 5秒という打ち切り時間**

`org.usb4java.javax.timeout` を 1000ms にしているので、正常系なら `abort()` は1秒程度で戻るはずという前提です。5秒が短すぎて正常な後始末まで打ち切っていないか確認してください。

**5. 復旧経路が本当に閉じているか**

「どこか1箇所が固まっても、必ず誰かが復旧する」という構造になっているかを見てほしいです。今回はそこが崩れて40分停止しました。
