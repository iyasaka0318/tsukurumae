# レビュー依頼：Skill「tsukurumae」の「目的から考える」の節

## お願いしたいこと

AI エージェント（Claude Code / Codex）に読ませる指示書（Agent Skill）の、ある1つの節の文章を考えてほしい。
これまで何度か書き直したが、ユーザーの意図に届いていない。下の資料を読み、ユーザーが求めていることを満たす節の文案を出してほしい。あわせて、なぜその書き方にしたかと、これまでの案のどこがずれていたかの見立ても書いてほしい。

## 前提（最低限）

- **tsukurumae とは**：ユーザー本人だけが使う Agent Skill。ハードウェア・ソフトウェアの開発を始めるときに `/tsukurumae` と打つと、AI がユーザーと一緒に要件定義をする。合意したら、要件定義書と、その案件専用の指示書を作る。作業は別の会話で、その指示書を読んだ AI が進める。
- **tsukurumae の目的**：ユーザーの開発を楽にすること。無駄な生成と無駄なターンをなくすこと。そのために、最初の要件定義をしっかりやる。tsukurumae は目的ではなく手段。
- **Skill の書き方の方針（ユーザーと合意済み）**：
  - 細かいチェック項目や手順を並べない。考え方を中心に、軽く書く。細かくすると、AI は決まった提案と検証しかできなくなる。
  - 今回の案件（tsukurumae 自身の開発）など、特定の案件に寄った言葉で書かない。どんな案件にも使える、一段メタな書き方にする。
  - 日本語。短い文。
- **ユーザーと合意済みの関連方針**：
  - 作ること自体が目的なら（例：趣味でドローンを作りたい）、既製品を勧めない。目的に沿うなら、作らない選択肢を出してもよい。
  - 決めるのはユーザー。AI は理由を付けて提案する。
  - 要件定義の段階では、考えを引き出す開いた質問をしてよい（数の上限なし）。

## 一番大事な資料（原文のまま）

会話の中で、AI が自分の失敗とユーザーの求めることを対比した文。ユーザーはこれを引用して「これがやりたいことの答え」と言っている。

> * 私がやったこと：「tsukurumae の Skill をどう良くするか」から考えました。だから出てきたのは、Skill の中身の改善案だけです。tsukurumae という枠の内側でしか考えていませんでした。
> * あなたが求めていること：「開発を楽にする」という目的から考えることです。開発のどこで時間や手間が無駄になっているかを探し、それを減らすために tsukurumae をどう変え、何を足すか。足すものは Skill の文章に限らず、道具でも仕組みでもかまわない。tsukurumae は目的ではなく、楽にするための手段の1つです。

## ユーザーの発言（原文。音声入力のため読みにくい箇所がある）

2. 「開発を楽にする。が目的なのよ。スキルズを改善する。が目的ではないのよ。開発を楽にする。ために。このスキルズを。どう変えていくか。この違いってわかるかな」

## これまでの案と、ユーザーの評価

**元の節（現行の Skill）**
```
### 目的は何か。それは本当の目的か
- 依頼と現状から「本当はこういうことがしたいんですよね」と推測して書き、「これで合っていますか」と確かめる。
- 改修なら、今どうなっていて、なぜ直したいのかから確かめる。
```
評価：何か足りない。

**案1**：上の節に、「何のため？」を変わらない目的までさかのぼる、動かせない制約（お金・時間）だけ確かめて他は手段として扱う、ユーザーも目的がはっきりしていないので一緒に言葉にする、を足した。
評価：まだ足りないが、案2よりはまし。

**案2**：案1に、「今回の会話で何をしてほしいか」「下へ具体にする（成功条件）」「願いが複数あれば関係を確かめる」「さかのぼる止めどころ」などを足して7項目にした。
評価：却下。項目を増やして一覧化し、方針（細かくしない）に反した。

**案3**
```
- 目的を確かめて終わりにしない。その目的を達成するには何をすべきかを、AI が考える。目的のどこで今つまずいているか、何が無駄になっているか、それを減らすには何が要るか。
- ユーザーが言った手段は、その中の選択肢の1つとして見る。（以下略）
```
評価：近くなった。ただし「つまずき・無駄」は今回の案件（開発を楽にする）に寄りすぎ（発言8）。

**案4**
```
- 目的を確かめたら、その目的を達成するには何をすべきかを考える。ユーザーが言った手段の内側（その手段をどう良くするか）だけで考えない。目的の側から、手段をどう変えるか、何を足すかまで考える。ユーザーが言った手段は、選択肢の1つにすぎない。
- 考えたことは、提案と質問でユーザーに返す。（以下略）
```
評価：7〜8割。まだ狭めている気がする（発言9）。

**案5**
```
- 目的を確かめたら、その目的を達成するには何が必要かを、手段の種類を限らずに考える。ユーザーが言った手段は出発点であって、考える範囲の枠ではない。その手段を良くすることも、変えることも、別のものを足すことも、まったく別のやり方を選ぶことも含めて考える（作るもの、道具、仕組み、進め方、やらないこと、など）。
```
評価：思考の方向性は合っている。前半（手段の種類を限らずに考える）まではよい。ただし、考えたものを目的に照らし直してから出してほしい（発言10）。

**案6（最新）**
```
- 目的を確かめたら、その目的を達成するには何が必要かを、手段の種類を限らずに考える。ユーザーが言った手段は出発点であって、考える範囲の枠ではない。作るもの、道具、仕組み、進め方、やらないことまで含めて、全部考える。
- 考えたものは、出す前に一つずつ目的に照らし直す。ユーザーが言った手段より目的の達成に近いものだけを、理由を付けて提案する。言われた手段が一番よければ、そう伝える。考えるのに足りないことは質問する。決めるのはユーザー。
- 作ること自体が目的なら（趣味で作りたい、など）、作るという手段は変えない。その作り方の中で考える。
- 改修なら、今どうなっていて、なぜ直したいのかから確かめる。
```
評価：ダメ。「それだと追加もできなくない」（発言11）。
（作成した AI の見立て：「言われた手段より目的の達成に近いものだけ」と書いたため、言われた手段を置き換える案しか通らず、言われた手段に何かを足す案、並べて使う案が出せなくなった。また、比べる相手を「言われた手段」にしたことで、結局また言われた手段を基準に考えている可能性がある。）

## この節の置き場所

Skill 本体（約90行）の「要件定義の考え方」の中の1節。同じ「要件定義の考え方」には、ほかに次の節がある（ここは今回の対象外）。
- ユーザーの考えの外側を持ち出す（話題にしていないが方針を左右するもの、詳しくない分野は理由をしっかり書いて提案）
- 今決めるものと、後で決めるもの（基準は後から変えが効くか）
- 質問の仕方（開いた質問、数は気にしない）

## 出してほしいもの

1. この節の文案（数行〜十数行程度。一覧を並べるより、考え方として書く）
2. その書き方にした理由
3. これまでの案がずれていたところの見立て
4. 迷った点や、ユーザーに確かめたい点があれば、その問い
