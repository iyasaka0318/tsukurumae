段階の表示そのものでは加点していない。ただし S3・S4 は表で段階の表示の有無が合否の条件になっているので、その範囲では見た。

## S1 研究用ドローン、センサーが先に決まっている

### X

**ターン 1：部分合格**
- MPU-6050 を目的に照らし、I2C の読み出し時間が干渉の測定に混ざる、振動、互換品という理由を付けて論点にしている。試験台の提案、比べる条件の軸、TinyML の負荷を段階的に変える案など、考えの外側も出せている。成果物は出していない。
- 足りない点：評価する人（指導教員・発表の聴衆）を挙げていない。目的を言い直して確かめる部分がない（質問はすべて仕様の質問）。記録・診断の計画は「ロギングの仕組みや GPIO トグルの準備が変わる」と触れる程度で、計画にはなっていない。
- 記憶で書いた事実に確認の印がない：「MPU-6050 は生産終了（EOL）扱い」「RP2350 は 520KB SRAM」「I2C 最大 400kHz」を断定で書いている。数値自体はおおむね妥当だが、要件の「確認していない数値は明示」に沿っていない。ICM-42688-P という型番を、条件を決める前に出している（理由付きで、勧めではなく例示なので不合格ではない）。

**ターン 2：合格**
- 「制御周期の遅れ」と「姿勢の乱れ」から、I2C の読み出し時間の混入（差分で打ち消す、GPIO で区間を測る）と、制御用 IMU で姿勢を測る自己参照の問題を導いている。後者は IMU を替えても残る指摘で、研究の評価者目線として的確。
- 切り替える条件を3つ示し、まず測ってから決める進め方を示している。結論は「使い続けて大丈夫」寄りで、理由ははっきりしている。
- 「数百マイクロ秒程度かかる見込み（実際の値は測って確かめます）」と見込みであることを示している。「決めるのはユーザー」とはっきり言ってはいないが、判断の条件を渡しており丸投げではない。

### Y

**ターン 1：合格**
- 目的を一文で言い直して確かめ、「主役はドローンではなく干渉の測定か」と問い直している。評価する人（指導教員・発表の聴衆）を挙げ、突っ込まれる点を5つ理由付きで出している（基準、原因の切り分け、測定が結果を変える、再現性、TinyML である意味）。
- MPU-6050 を目的に照らし、「CPU 側の干渉が主題なら交絡要因になる」「I2C を含めた現実的な構成の研究なら筋が通る」と目的によって結論が変わることを示し、決めるのはユーザーと明示している。型番を出さずに「方針が決まってから調べて比べる」としている。
- 考えの外側（飛ばす必要があるか、電源とモーターのノイズ、ファームウェアの土台、モデルの置き場所、法規、スケジュール）を出している。記録・診断の計画を理由付きで示している（GPIO を外から測る、推論の開始と終了、電池の電圧）。
- 「データシートで確かめます」「調べて確認します」と、確認していない事実の扱いが明示されている。成果物なし。
- 長い。ただし長さでは加点していない。

**ターン 2：合格**
- 結論を先に出し（条件付きで使ってよい）、替えたほうがよい条件（数 kHz）を理由付きで示している。0.4ms を「計算値。実機で測る」と明示。
- X と同じく自己参照の問題を挙げ、試験台＋エンコーダーを一番の案として理由付きで勧めている。記録用 IMU を別に載せる案の負荷まで考えている。
- 使う前の基準の確認（静止ノイズ、モジュールの種類、INT ピン）を計画に入れている。今の整理を表で「合意前の候補」として示している。

### 要件に照らした所見

| 観点 | X | Y |
|---|---|---|
| 目的の確認 | 言い直しなし。質問は仕様寄り | 一文で言い直し、主役を問い直した |
| 評価する人の目線 | T1 になし。T2 で「聞かれます」と実質的に出た | T1 から明示、突っ込まれる点を列挙 |
| 決まっていたものを目的に照らす | MPU-6050 は照らした。RP2350 は肯定のみ | MPU-6050・RP2350 とも目的に照らし、ボードの違いが干渉に効く点まで |
| 考えの外側 | 試験台、比較軸、負荷の段階 | 飛行の要否、電源ノイズ、OS、モデルの置き場所、法規、日程 |
| 記録・診断の計画 | 触れる程度 | 理由付きで計画として示した |
| 段階の順番と表示 | 表示なし。順番は守っている（成果物なし） | 表示あり。邪魔にはなっていない |
| 確認していない数値 | EOL、SRAM 容量などを断定 | 確認の要否を明示 |

**優劣：Y。** 2ターン目の中身（差分で打ち消す、自己参照）は両者ほぼ同じ質だが、1ターン目で Y は評価者・目的の確認・記録の計画が揃い、X は欠けている。X は記憶の事実を断定している。

## S2 ソフトをゼロから、技術が先に決まっている

### X

**ターン 1：不合格（軽度）**
- 使う人、ログイン、承認、予約の単位、動かす場所、移行、通知と、使い方の質問は揃っている。コードは出していない。
- ただし Next.js を「研究室規模のアプリには向いている」と一言で受け入れ、目的（引き継ぎ、動かす場所、作る必要そのもの）に照らしていない。最後に「Next.js App Router ＋ データベース ＋ 認証」の構成案を出すと予告しており、技術は決定済みとして扱っている。表の不合格条件「技術の選択を目的に照らさない」に当たる。
- 目的（何に困っているか）を確かめていない。卒業後の保守、個人情報、記録・診断の計画に触れていない。

### Y

**ターン 1：合格**
- 目的を言い直して確かめ、今のやり方と困りごとを聞いている。評価する人に引き継ぐ後輩を含め、「卒業したら誰が直すの」「サーバー代は誰が払うの」を先に言っている。
- Next.js を、動かす場所との相性、引き継ぐ人が読めるか、そもそも作る必要があるか（カレンダーの設備予約で足りる場合）の3点で目的に照らしている。作ることは受け入れたうえで、作る理由を要件の中心にすると言っており、押し付けていない。
- 考えの外側（認証、データの保存先、予約ルール、費用、個人情報と大学の規程、止まったときの代わり、保守）を出している。記録・診断の計画（予約の変更履歴、サーバー側のエラー記録）を理由付きで示している。コードなし。

### 要件に照らした所見

| 観点 | X | Y |
|---|---|---|
| 目的の確認 | なし | あり（困りごとまで） |
| 評価する人の目線 | なし | 利用者・管理者・後輩 |
| 決まっていたものを目的に照らす | 受け入れのみ | 3つの観点で照らした |
| 考えの外側 | 動かす場所・移行・通知 | 保守・個人情報・停止時など広い |
| 記録・診断の計画 | なし | あり |
| 段階の順番と表示 | 表示なし。成果物は出していない | 表示あり。邪魔にはなっていない |

**優劣：Y。** 要件第3版で足した「決まったものを目的に照らす」「考えの外側」「記録・診断の計画」のすべてで差がある。

## S3 段階の順番（要件は合意済み）

前提：両者とも会話の中で主役の型番や数値を受け取っていない。そのため、どちらも具体的な構成を出さず質問で止まっている。型番を記憶で補わなかったのは適切。

### X

**ターン 1：部分合格**
- 段階 3（周りの成り立ち）と示し、「主役から逆算する」と順番を明示している。決める順番（セル数→C レート→容量と重さ→コネクター→載せ方）を主役の仕様から導く形で書いている。
- 主役の値がないので構成を出せず、「この構成で大丈夫ですか」の確認まで行っていない。代わりに運用面の推奨（小さめの電池を複数本で交換）を理由付きで出し、保管・充電場所という考えの外側（LiPo の発火）を持ち出している。価格と在庫に調べた日付を付けると言っている。
- 懸念：「作業フォルダーに要件・台帳ファイルが見当たりませんでした」と、確認したかのように書いている。実際にファイルを見ていないなら、観察の捏造に近い。重大とまではしないが、記録すべき点。

### Y

**ターン 1：不合格（表の条件による）**
- 中身は X とほぼ同じ質：決める項目（セル数、容量、C レート、コネクター、寸法、安全）を理由付きで示し、主役の値を質問している。「主役が決まったので次はバッテリー、順番としてちょうどいい」と順番は意識している。C レートの表記が大きめという注意、「必ずデータシートで確認」もよい。
- 表の不合格条件「段階を示さない」に当たるため不合格とした。型番だけを出す失敗はしていない。
- 構成を示して確認を取る点は X と同じく未達。

### 要件に照らした所見

- 目的・評価者：両者とも飛行時間と飛ばし方を聞いており、同程度。
- 考えの外側：X は保管場所と運用、Y は充電器・耐火バッグ・電圧アラーム。同程度。
- 段階の順番と表示：X は表示ありで、主役→周りの順番を言葉で示した。Y は表示なし。

**優劣：X（わずか）。** 差は段階の表示と、主役から導く順番の説明がやや明確な点。電池の中身の質は同等。X の「見当たりませんでした」は注意点。

### X

- README.md を直し、1行で返している。段階の行なし。修正後の README も正しい。

### Y

**ターン 1：合格**

## 全体の所見

- Y が Skill ありと推測される。要件第3版で足した項目（評価する人の目線、決まったものを目的に照らす、考えの外側、記録・診断の計画）は、S1・S2 の要件定義の段階で明らかに効いている。特に S2 で、X は Next.js をそのまま受け入れたのに対し、Y は「作る必要があるか」まで照らしている。
- 段階の表示は、S1・S2 で邪魔にはなっていない。S4 では正しく付けていない。
- ただし S3 では、Y と推測される側が段階を示さず、X が示している。X が Skill ありなら、S1・S2 の質と合わない。どちらの筋書きで Skill が読み込まれていたかは、伏せた情報と照合して確かめる必要がある。
- S1 では、X の 2ターン目の中身が Y とほぼ同じ質まで追いついている。Skill の差は、1ターン目で先に言えるかどうか（評価者、記録の計画）に出ている。
- 記憶で書いた事実の扱いは Y が安定している。X（S1）は生産終了や SRAM 容量を断定した。
