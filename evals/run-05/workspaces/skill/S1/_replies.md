## ターン 1

段階 1／6：要件定義（目的の確認）　次：研究で「何を比べ、何を測るか」を決め、そこから機体と IMU の条件を導く

この段階では、コードや回路図はまだ出しません。先に研究の中身を一緒に固めます。質問が多くなりますが、思いつくところから答えてもらえれば十分です。

---

### 1. 目的の確認

いただいた内容から、目的をこう推測しました。

> **卒業研究として、RP2350 の上で「姿勢制御のループ」と「TinyML の推論」を同時に動かしたとき、お互いにどんな悪影響（干渉）が出るかを測り、示したい。ドローンはその干渉が実際の制御に効く場面を作るための実験台。**

これで合っていますか。特に次の2点を確かめたいです。

- **主役は「ドローン」ではなく「干渉の測定」ですか。** そうだとすると、ドローンは「干渉が制御の質にどう効くかを見せる場」であり、飛ばせること自体は必須ではないかもしれません（後述の「飛ばす必要があるか」）。
- **「干渉」で何を指していますか。** 例えば、制御ループの周期の揺らぎ（ジッタ）、締め切りに間に合わない回数、センサーを読んでからモーターに指令が出るまでの遅れ、推論にかかる時間の伸び、その結果としての姿勢の乱れ、など。どれを主に見たいかで、測り方も部品も変わります。

### 2. 評価する人と、突っ込まれそうなところ

評価するのは、指導教員と、卒研発表の聴衆（他の先生方）だと推測しています。その人たちに聞かれそうな点を先に挙げます。

1. **「何と比べて干渉と言っているのか」**：推論なしで制御だけを動かしたときの基準値が要ります。基準そのものが安定していることを先に示す必要があります。
2. **「その干渉の原因は CPU なのか、バスなのか、センサーの読み出しなのか」**：RP2350 はコアが2つあるので、「同じコアで動かす」「別々のコアに分ける」で結果が大きく変わるはずです。分けても、メモリ（SRAM のバンク）、フラッシュからの読み出し（XIP）、割り込み、I2C などの共有資源で干渉が残る可能性があります。どこまでを研究の範囲にするかを決めておかないと、「それは実装の問題では」と言われやすいです。
3. **「測定そのものが結果を変えていないか」**：マイコンの中でログを取ると、その処理自体が干渉の原因になります。外から測る手段（GPIO を上げ下げしてロジックアナライザで見る、など）を最初から計画に入れることを勧めます。
4. **「再現できるか」**：飛行中の姿勢の乱れは、風・電池の電圧・機体の個体差で毎回変わります。干渉の効果がそれに埋もれないかが問われます。
5. **「TinyML は何をしているのか」**：推論の中身（何を入力に何を判定するか）が、実際にドローンで意味のある処理かどうか。ダミーの重い処理でも同じ結論になるなら、TinyML である意味を説明できるようにしておく必要があります。

### 3. 既に決まっているものを、目的に照らして確かめる

**(a) RP2350**
コアが2つあり（Cortex-M33 ×2、または RISC-V に切り替え可能）、「コアを分けたら干渉は消えるのか」という問いを立てやすいので、研究のテーマに合った選択だと考えます。どのボード（Raspberry Pi Pico 2、他社のボードなど）を使う予定かは教えてください。フラッシュや PSRAM の有無が、モデルをどこに置けるか（＝干渉の出方）に効きます。

**(b) MPU-6050（手持ち品）**
ここは**目的によっては足りない可能性がある**ので、はっきり書きます。

- MPU-6050 の接続は I2C です（SPI はありません。この点と下の速度は、記憶ではなくデータシートで確かめます）。I2C は読み出しに時間がかかり、その時間がバスや割り込みを通じて「干渉」の測定に混ざります。**研究の主題が CPU 側の干渉なら、センサーの読み出しが交絡要因になる**、と突っ込まれやすい点です。
- 一方で、「I2C で読むセンサーを使った現実的な構成で、どのくらい干渉が出るか」を見る研究なら、むしろ MPU-6050 でもよい、という言い方もできます。
- 手持ちの MPU-6050 は、多くが互換品のモジュール（GY-521 など）です。同じ名前でも中身や性能に個体差があることがあるので、**まず静止時のノイズとドリフトを測って、制御の基準として足りるか**を確かめる計画を入れます。
- 入手性（現行品かどうか）も、追加の購入や再現性の説明に関わるので、調べて確認します。

**勧めること**：研究の主題が「CPU・メモリの資源を取り合う干渉」なら、SPI で読めて、データの準備ができたら割り込みで知らせてくれる IMU（ドローン用のフライトコントローラーでよく使われる種類）に替えることを勧めます。センサーの読み出し時間が短く一定になり、干渉の原因を切り分けやすくなるからです。候補と価格・入手性は、方針が決まってから調べて比べます。MPU-6050 のまま進めるのも十分ありで、その場合は「I2C の読み出しを含めた構成での干渉」と研究の範囲を書けば筋が通ります。どちらにするかは目的の答え次第なので、決めるのはあなたです。

### 4. あなたが触れていないが、方針に効くこと

**飛ばす必要があるか**
干渉を測るだけなら、機体を台に固定して1軸だけ回れるようにした試験台（シーソー型やジンバル型）でも、姿勢制御の質の違いは測れます。試験台なら、毎回同じ条件で何度でも測れ、墜落で機体が壊れて実験が止まる心配もありません。最後に「実際に飛んだ」デモを入れるかどうかは、指導教員の期待次第です。ここは研究の進め方を大きく変えるので、早めに決めたいです。

**機体まわり（電源・モーター・ESC・フレーム）**
まだ話に出ていません。干渉の研究では、モーターのノイズと電池の電圧の変化も交絡要因になります。主役（RP2350 と IMU、測り方）が決まってから組みますが、既に手持ちがあるもの、研究室にあるものは教えてください。

**ファームウェアの土台**
Pico SDK を直接使うか、FreeRTOS などの OS を載せるか、Arduino 環境か。タスクの切り替え方そのものが干渉の出方を決めるので、「比べる条件」の一部になります。

**TinyML の中身と置き場所**
モデルの大きさ、使うライブラリ（TensorFlow Lite Micro など）、モデルを SRAM に置くかフラッシュから読むか。これも干渉の原因の候補なので、比べる条件として扱えます。

**安全と法規**
屋外で飛ばすなら、機体の重さによっては航空法上の機体登録などの手続きが要ります（条件は調べて確認します）。屋内でも、プロペラの回る試験は固定のしかたと止め方を段取りしてから行います。大学や研究室に飛行のルールがあるかも確認が必要です。

**スケジュール**
卒研の中間発表・本発表の時期。飛行までやるか、試験台で止めるかの判断に直接効きます。

### 6. 記録・診断の計画（入れるのは合意の後）

- **制御ループの周期と処理時間が分からないと干渉を示せない**ので、ループの開始と終了で GPIO を上げ下げし、外のロジックアナライザで測れるようにします（マイコン内でログを取ると、それ自体が干渉になるため）。
- **推論の開始・終了も同様に GPIO で出す**ので、制御ループと推論が重なったタイミングが波形で見えます。
- **姿勢の乱れを示すため**に、IMU の値・目標値・モーター指令を記録します。記録の方法（USB に流す、メモリにためて後で回収する）は、記録の負荷が測定に混ざらないように選びます。
- **電池の電圧**も記録し、電圧の低下による変化と干渉による変化を区別できるようにします。

## ターン 2

段階 1／6：要件定義（主役の部品を目的に照らす）　次：目標の制御周期と、姿勢の乱れの測り方を決める

測りたいものが「制御周期の遅れ」と「姿勢の乱れ」の2つだと分かったので、MPU-6050 で突っ込まれるかを、この2つに分けて判断します。

### 結論（先に）

**MPU-6050 は、条件付きで使ってよいと考えます。** 突っ込まれるのは MPU-6050 という部品そのものより、「センサーの読み出しを測定からどう切り離したか」と「姿勢の乱れを何で測ったか」の2点です。この2つに答えを用意できれば、手持ち品で通せます。ただし、目標の制御周期を高く（数 kHz）取りたいなら替えることを勧めます。理由を下に書きます。

### 1. 制御周期の遅れについて

**突っ込まれそうな点**：「周期が遅れたのは推論のせいなのか、それとも I2C の読み出しのせいなのか」。

- MPU-6050 は I2C で読みます。加速度と角速度をまとめて読むと、I2C の速度を 400kHz にしても1回あたりおよそ 0.4ms かかります（計算値：やり取りするバイト数とビット数から出した概算です。実際の時間は実機で測ります）。
- この時間は、毎回だいたい一定なら「基準にも含まれる一定の時間」として扱えます。比べるのは「推論なし」と「推論あり」の差なので、一定の読み出し時間は差を打ち消し合います。
- 問題になるのは、**読み出しの時間そのものが推論によって揺らぐ**場合です（割り込みが遅れる、同じコアで処理している、など）。これは干渉の一部として示す価値がありますが、「CPU の干渉」と「バスの干渉」を分けて書けるようにしておく必要があります。

**対策**：制御ループの中を区間に分けて、GPIO の上げ下げで外から測ります。
- 区間 A：センサーの読み出し
- 区間 B：姿勢の計算と制御の計算
- 区間 C：モーターへの指令の出力
- 別の GPIO：推論の開始と終了

こうすれば、推論ありのときに「どの区間が伸びたか」を波形で示せるので、「I2C のせいでは」という質問にそのまま答えられます。

**替えたほうがよい場合**：制御周期を、今の市販のフライトコントローラーに近い数 kHz にしたい場合です。MPU-6050 の I2C の読み出しでは、読み出しだけで周期の大部分を占めてしまい、推論の影響を見る余地が小さくなります。1kHz 前後なら読み出しは周期の一部に収まる見込みです（概算。実測で確かめます）。

### 2. 姿勢の乱れについて

**突っ込まれそうな点**：ここが MPU-6050 よりも重要です。**「姿勢の乱れを、制御に使っているのと同じ IMU で測っているなら、その測定は信用できるのか」**と聞かれます。制御に使っているセンサーの値は、制御がそれに合わせて動いた結果なので、乱れの「ものさし」としては独立していません。センサーが MPU-6050 でも高性能な IMU でも、この指摘は同じです。

**勧めること**：姿勢の乱れは、制御に使うものとは別のものさしで測ります。
- **一番勧める案**：機体を1軸だけ回れる試験台に載せ、軸の角度をエンコーダー（回転角を測るセンサー）で測る。制御と無関係な値で角度が取れ、毎回同じ条件で繰り返せるので、比較実験に向いています。飛ばさずに済むので、安全で、墜落で実験が止まることもありません。
- **次の案**：機体にもう1つ別の IMU を載せて記録だけに使う。ただし、記録用の読み出しが新たな負荷になるので、記録は別のマイコンで取る構成になります。
- 飛行中の姿勢の乱れは、風や電池の電圧で毎回変わるので、干渉の効果が埋もれやすいです。飛行は最後のデモとして位置づけ、比較の本体は試験台で取ることを勧めます。

### 3. 使う前に確かめること（基準の確認）

手持ちの MPU-6050 を使うなら、比較の前に次を確かめる計画を入れます。
- **静止時のノイズとドリフト**：机に置いたまま数分間記録し、制御に使えるか、同じ測定で毎回同じ値になるかを見ます。
- **モジュールの種類**：手持ちのモジュールの名前（基板に印刷されている名前、例：GY-521）と、割り込みのピン（INT）が出ているか。データの準備ができたことを割り込みで受け取れると、読み出しのタイミングが安定します。写真でもかまいません。

これで「基準の性能が安定している」ことを先に示せます。もしノイズやドリフトが大きければ、その時点で替える判断ができます。

### 4. 次に決めたいこと

1. **目標の制御周期**はどのくらいを考えていますか（例：数百 Hz、1kHz、数 kHz）。まだなければ、「市販のフライトコントローラーと比べる」のか「まずは動く周期で干渉を示す」のかを教えてください。MPU-6050 を使い続けられるかがここで決まります。
2. **「制御周期の遅れ」**は、次のどれを主に見たいですか。決まっていなければ、全部を区間の計測で取れるようにします。
   - 周期そのものの揺らぎ（毎回の開始時刻のずれ）
   - センサーを読んでからモーターに指令が出るまでの遅れ
   - 締め切りに間に合わなかった回数
3. **試験台で比較を取り、飛行は最後のデモにする**、という進め方でよいですか。指導教員から飛行を求められているかも教えてください。
4. 前回の質問のうち、**TinyML で何を推論させるか**と、**ロジックアナライザやオシロスコープが手元にあるか**も、引き続き教えてください。外から測る手段は、この研究の測定の中心になります。
