## ターン 1

段階 1／6：要件定義（目的の確認）　次：今の予約のやり方と困りごとを聞き、使い方と運用の方針を決める

作る前に、何を解決したいアプリかを一緒に固めます。この段階ではまだコードは出しません。

---

### 1. 目的の確認

推測ですが、こういうことがしたいのだと考えました。

> **研究室で共有している機材（測定器、PC、3D プリンタなど）を、誰がいつ使うかを事前に押さえられるようにし、使いたいときに他の人とぶつかる・使えない、という事態を減らしたい。**

これで合っていますか。あわせて、

- 今はどうやって予約していますか（ホワイトボード、スプレッドシート、Slack で声をかける、予約なし、など）。
- 今のやり方で、具体的に何が困っていますか（ダブルブッキング、誰が使っているか分からない、借りっぱなし、など）。

を教えてください。困りごとが分かると、必要な機能と、なくていい機能がはっきりします。

### 2. 評価する人と、突っ込まれそうなところ

このアプリを評価するのは、**実際に予約する研究室のメンバー**と、**機材を管理している人（先生や管理担当の学生）**だと推測しています。さらに、あなたが卒業した後に**引き継ぐ後輩**も評価する人に入ります。

その人たちに言われそうなこと：
- 「今のスプレッドシートのほうが早い」→ 予約の操作が今のやり方より手間なら使われません。
- 「ログインが面倒」「パスワードを忘れた」→ 認証の方式で使われるかが決まります。
- 「あなたが卒業したら誰が直すの」「サーバー代は誰が払うの」→ 研究室のアプリでは一番多い終わり方です。

### 3. 既に決めていることを、目的に照らして確かめる

**Next.js**
予約の一覧・カレンダー表示・予約の登録といった Web アプリを作るには十分な選択です。ただし、目的に照らして次を確かめたいです。

- **動かす場所との相性**：Next.js は Vercel のようなホスティングだと手軽ですが、研究室や学内のサーバーで動かす場合は Node.js の常駐と更新の手間がかかります。どこで動かすつもりかで、Next.js の使い方（サーバーの機能をどこまで使うか）が変わります。
- **引き継ぎ**：研究室に Next.js（React・TypeScript）を読める人が続くかどうか。読める人がいないなら、構成をできるだけ単純に保つ方針にします。
- **そもそも作る必要があるか**：機材が数台で、Google Workspace や Microsoft 365 を研究室で使っているなら、カレンダーの「リソース（設備）予約」機能で足りることもあります。作ること自体はもちろん受け入れますが、既存の道具では足りない理由（例：使用ルールを強制したい、学習・ポートフォリオとして作りたい）があれば教えてください。その理由が要件の中心になります。

### 4. あなたが触れていないが、方針に効くこと

後から変えにくいので、要件定義の中で方針を決めたい分野です。

- **ログイン（誰が予約したか）**：大学のアカウント（Google、Microsoft など）でログインするか、研究室だけの簡単な仕組みにするか。学外からも使うか。
- **データの保存先**：予約のデータをどこに持つか（データベースの種類、ホスティングに付属するものか）。あとで変えると移行が要ります。
- **予約のルール**：1回の最大時間、事前予約できる期間、承認が要る機材があるか、優先順位（学会前の人を優先、など）、キャンセルや当日の延長。ここがアプリの中身の大部分になります。
- **動かす場所と費用**：無料枠で収まるか、学内ネットワークからしか使えない制約がないか、費用を誰が持つか。
- **個人情報**：名前やメールアドレスを保存するなら、学外のサービスに置いてよいか（大学の規程があるか）。
- **通知**：予約の前日や、ぶつかったときに知らせる必要があるか（メール、Slack など）。
- **止まったときの影響**：アプリが落ちたら予約できない・確認できない。そのときの代わりの手段を決めておくか。
- **保守と引き継ぎ**：誰が管理者になり、機材の追加や不具合の対応をするか。

### 5. 考えを聞かせてほしいこと

1. 予約の対象になる機材は何台くらいで、どんなものですか。
2. 使う人は何人くらいで、誰ですか（学生だけか、先生や他研究室の人も含むか）。
3. どんな画面・操作ができたら「完成」と言えますか。
4. このアプリを作る理由に、学習やポートフォリオの意味もありますか。
5. 研究室で既に使っている道具（Slack、Google Workspace、学内のサーバーなど）は何がありますか。
6. 卒業後も使い続けてほしいですか。そのとき誰に引き継ぐイメージですか。
7. 一番不安なところはどこですか。

### 6. 記録・診断の計画（入れるのは合意の後）

- **「誰がいつ予約を消した・変えた」が後で分からないと、揉めたときに困る**ので、予約の作成・変更・削除の履歴を残します。
- **ログインや予約の登録が失敗したときに原因が見えないと往復が増える**ので、サーバー側でエラーを記録し、見る場所を決めておきます。

### 7. 今決めるもの／後で決めるもの

**今決める（後から変えにくい）**
- 目的と完成の基準
- 動かす場所（ホスティング）とデータの保存先
- ログインの方式
- 予約のルールの骨組み（承認の有無、時間の単位）
- 管理者と引き継ぎの方針

**後で決める（後から変えが効く）**
- 画面のデザイン、色
- 通知の文面
- 機材の一覧の並び順や表示項目

まずは 1 の「今のやり方と困りごと」と、5 の質問のうち答えられるものから教えてください。
