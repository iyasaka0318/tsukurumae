## ケース H-E01
了解です。フレームCADに入る前に、確定に効く点だけ整理します。

**理解したこと**
- 自作ドローンのフレームを CAD で作る。搭載するのは Pico 2 WH、ICM-42688 の基板、お手持ちの ESC。
- 部品の公式図面は私が調べます（Pico 2 WH は Raspberry Pi 公式の機械図面、ICM-42688 はチップのデータシート）。

**見つけた論点**
1. **「ICM-42688 の基板」と「この ESC」の型番がまだ分かりません。** ICM-42688 はチップの名前で、載っている基板（販売元）によって外形・穴位置・ピンの並びが変わります。ESC も同じで、型番が分からないと公式図面を引けません。
2. **フレームは部品単体の外形だけでは決まりません。** Pico 2 WH はヘッダーがはんだ付け済みの型なので、ジャンパ線やソケットを挿した後の高さ・ハウジングの幅・線の出口が占有範囲になります。これは図面に載っていないので、接続の仕方を教えてもらう必要があります。
3. **モーター・プロペラ・電池がまだ出ていません。** アームの長さ（軸間距離）、モーターの取付穴、電池の置き場所と固定方法はフレームの骨格そのものなので、これが決まらないと本番のCADは確定できません。
4. **組み立てた後に触るもの**：Pico の USB（書き込み・ログ回収に使うか、いつ挿すか）、電池の交換、電源スイッチ。ここへの開口を後から足すと作り直しになりやすいです。

**質問（各1行で大丈夫です）**
1. ICM-42688 基板と ESC の型番か、購入ページのリンク — 公式図面を引くために必要です。
2. モーターの型番とプロペラのサイズ、電池（セル数・容量・コネクター）— アーム長とフレームの大きさを決めます。決まっていなければ、こちらで候補を出して仮決定します。
3. Pico・IMU 基板・ESC はどうつなぐ予定ですか（ジャンパ線／ソケット基板に挿す／直接はんだ付け）。ピンはどちらの面に出ていますか — 搭載の高さと向きを決めます。推奨：ジャンパ線なら、挿した状態の高さを一度だけ実測してもらいます。
4. 組み立てた後も USB を挿しますか（書き込み、ログ回収）— 開口の位置に効きます。推奨：挿せるようにしておく。
5. 使える3Dプリンタと材料（または板材から切り出すか）— 肉厚・穴の作り方・造形サイズに効きます。

**今すぐ進めること**
- Pico 2 WH の公式機械図面（外形・取付穴・USB 位置）と ICM-42688 のデータシートを調べ、値を「メーカー公称」として台帳に記録します。型番をもらえれば IMU 基板と ESC も同様に調べます。
- 部品の配置に依存しない部分（Pico の取付穴の位置合わせや、ネジ穴径の試験片）は先に作れます。必要なら、穴径を数段階変えた小さな試験片の CAD を出します。
- フレーム全体（アーム、中央板の配置）は、上の 2・3 が揃うまで「仮配置」として扱い、本番として確定しません。

**台帳**：プロジェクトのルートに `TSUKURUMAE_LEDGER.md` を作り、目的（自作ドローンのフレーム）、搭載部品と派生型（Pico 2 WH＝ヘッダー付き・無線あり）、未回答の質問 Q1〜Q5、作業の状態（本番 CAD：保留、足りない条件＝IMU/ESC 型番・モーター/プロペラ/電池・接続方式と接続後の寸法）を記録します。

## ケース H-E02
「高級機体にしたいわけではない」は了解です。そのうえで、手持ちの MPU-6050 で足りるかは「卒研で何を示すか」で決まるので、そこだけ確かめさせてください。

**理解したこと**
- 卒業研究で倒立振子型のロボットを作る。費用は抑えたい。手持ちの MPU-6050 を使えるなら使いたい。

**見つけた論点**
- 倒立を保つだけなら MPU-6050 で実現している例は多いです。ただし研究として「何かを比べる」場合は、センサーの雑音・ドリフト・サンプリング周期が比較結果に混ざる（交絡する）ことがあります。研究の中身によって「十分」の基準が変わります。
- 「安く」は部品単価だけでなく、総額（モーター・ドライバ・電池・エンコーダの有無、送料）で見る必要があります。IMU は全体の中では安い部類なので、ここを削っても総額はあまり変わらないことがあります。逆に、理由なく高いセンサーへ替える必要もありません。
- MPU-6050 は古い部品なので、今の入手性（手持ちが壊れたときの予備）を調べておきます。手持ちのモジュールの型（GY-521 など）も確認したいです。

**質問**
1. 卒研で何を評価・比較しますか（例：制御手法 A と B の比較、外乱からの復帰時間、倒立を保つこと自体の実証）— センサーに要る精度と周期がここで決まります。決まっていなければ、それを一緒に決めるところから始めます。
2. 制御周期とマイコンの想定はありますか — MPU-6050 の読み出し速度（I²C）で足りるかを計算します。特に希望がなければ、こちらで一般的な値を仮置きして計算します。
3. 予算の上限（全体でおおよそ何円）— 総額で比べるために使います。
4. 手持ちの MPU-6050 は何個で、どの基板（GY-521 など）ですか — 予備の有無と、取付・配線に効きます。

**今すぐ進めること**
- MPU-6050 のデータシートから、雑音密度・ジャイロのドリフト・最大サンプリング周期・I²C の速度を調べ、倒立制御でよく使われる周期と照らします（調べた値は「メーカー公称」として記録します）。
- MPU-6050 の現在の入手性・価格を調べ、日付付きで記録します。
- 質問1の答えを待つ間、「MPU-6050 で十分な場合」と「足りない場合の代替候補（総額比較つき）」の両方を用意しておきます。結論は研究の目的が決まってから出します。
- 研究なら、比較の前に「基準の性能」（何もしない／基本制御での倒立の状態）を測る計画も入れることを提案します。

**台帳**：`TSUKURUMAE_LEDGER.md` を作り、用途＝研究（卒研）、優先順位（研究の妥当性 > 価格 > 作りやすさ、と仮置き）、手持ち部品＝MPU-6050、未回答の質問 Q1〜Q4、作業の状態（IMU の選定：保留、足りない条件＝評価する内容と必要な周期・精度）を記録します。

## ケース H-E03
了解です。今回は研究用の倒立ロボットとは**別の、趣味のドローン**として扱います。研究機体で ICM-42688 を選んだ理由（研究の評価に必要な性能）はこちらには持ち込まず、余っている初代 Pico W と MPU-6050 を前提に進めます。

**理解したこと**
- 趣味でドローンを作る。マイコンは初代 Pico W（RP2040）、IMU は MPU-6050 を使う。
- 研究機体と「電源だけ」共用したい。

**見つけた論点**
1. **「電源を共用」が何を指すか**で設計が変わります。
   - (a) 電池（と充電器）を両方の機体で使い回すだけ
   - (b) 電源基板・レギュレータまで共通の設計にする
   - (c) 同じ電池を同時に両方につなぐ
   ドローンはモーターの電流が大きいので、電池の放電能力・コネクター・電圧が研究機体の電池で足りるかを確かめる必要があります。(a) なら電池の仕様の確認だけで済みます。
2. **研究機体と変わるもの**：マイコンの世代（初代 Pico W は RP2040）、IMU（MPU-6050）、ファームウェア（ドローンは別に書く）、機械（フレーム）。研究機体のコードや設定をそのまま流用できるとは限らないので、流用する部分は個別に確かめます。
3. **現物の状態**：余っている Pico W はヘッダーをはんだ付けしていますか。MPU-6050 はどの基板（GY-521 など）ですか。搭載方法と高さに効きます。

**質問**
1. 「電源を共用」は上の (a)〜(c) のどれですか — 推奨：特に希望がなければ (a) 電池の使い回し、として進めます。
2. 研究機体の電池の仕様（セル数・容量・放電レート C・コネクター）— ドローンのモーター電流に耐えるかを計算します。
3. Pico W のヘッダーの有無と、MPU-6050 の基板の種類 — 搭載・配線の形に効きます。
4. ドローンの大きさ（プロペラのサイズ）や、まず目指すところ（ホバリングできればよい、など）— モーターと ESC の選定、電池が足りるかの判定に効きます。推奨：まずは小型でホバリングを目標に仮決定します。

**今すぐ進めること**
- RP2040（Pico W）の PWM・I²C の仕様と、MPU-6050 のデータシート（読み出し速度・雑音）を調べ、ドローンの姿勢制御の周期で使えるかを確認します。
- 電池の仕様をもらったら、想定するモーターの電流と照らして、共用が成り立つかを計算します。

**台帳**：この趣味ドローン用に別の `TSUKURUMAE_LEDGER.md` を作ります（研究機体の台帳とは分けます）。用途＝趣味、手持ち部品＝初代 Pico W・MPU-6050、研究機体との共有範囲＝電源（範囲は未確認、Q1）、未回答の質問 Q1〜Q4 を記録します。

## ケース D-E01
了解です。ライブラリ A の方式に戻して、ビルドまで進めます。進める前に1点だけ確認させてください。

**確認したいこと（戻した後に動かなくなるのを防ぐため）**
B 経由の方式に書き換えたとき、**リポジトリの外で変えたもの**はありませんか。例えば：
- 機器側でコマンドラインツール B を使うために入れたパッケージや、有効にした常駐プロセス（systemd のサービスなど）
- 機器にだけ置いた設定ファイルや、変えた設定値
- A を使わなくなったときに外したもの（A が使うデバイスの権限、カーネルモジュールなど）

コードだけを A に戻しても、機器側に B 用の常駐プロセスが残ってデバイスを掴んでいたり、A 用の設定が消えていたりすると動きません。覚えていなければ、それを確かめるコマンドを機器側で実行する手順にして出します（機器への操作はご自身で行っていただく前提です）。

**答えを待たずに進めること**
1. 今の状態を保存します：作業ツリーの状態を確認し（`git status`）、現在の B 方式のコードをブランチかコミットとして残します。元に戻した後でも B 方式に戻れるようにするためです。
2. 履歴（`git log`）から、A から B に書き換えたコミットを探し、対象の3ファイルを特定します。そのコミットに3ファイル以外の変更（設定ファイル、ビルド設定、依存関係の追加）が含まれていないかも確認します。含まれていれば、戻すかどうかをお聞きします。
3. 3ファイルを書き換え前の版に戻し、差分を確認します。書き換えた後に別の目的で入った変更があれば、それは消さないように扱います。
4. ビルドを実行し、結果をお伝えします。

**ビルドが通っても分かるのは「ビルドが通った」ところまで**です。機器の上で A が初期化でき、制御が実際に効くかは、機器で動かして確かめる必要があります。ビルド後に、機器で確かめる手順（どのマシンで何を実行し、何が見えれば成功か）もお渡しします。

台帳 `TSUKURUMAE_LEDGER.md` を作り、決定（A 方式に戻す）、B 方式の保存先、リポジトリ外の変更の確認状況（未確認）、ビルド結果と未確認の項目（実機での動作）を記録します。
