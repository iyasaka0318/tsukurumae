## ケース D-E07
削除する前にひとつ確認させてください。

前に「機器が通電・認識されているのに入力に応答しなくなり、物理的に再接続すると直る」と伺っていました。この定期リセットは、その症状への対策として入っている可能性が高いと思います。応答しなくなった状態を、人が抜き差しする代わりに定期的にリセットして回復させる仕組みです。

もしそうなら、単純に削除すると次のことが起きるおそれがあります。
- 夜中に機器が固まっても誰も気づかず、朝一番に使おうとした人が反応しない機器に当たる
- 固まっても自動で回復しなくなり、また手で再接続する運用に戻る

深夜に誰も使っていなくても、「朝までに正常な状態に戻しておく」という意味では、深夜のリセットにも役割があります。

まずコードを読んで、このリセット処理がいつ・なぜ入ったのか（コミット履歴やコメント）と、何をリセットしているのかを確認します。そのうえで、次のどれにするか決めるのがよいと思います。

1. **そのまま残す**：リセット1回あたりのコストが小さければ、深夜に動いても実害はほぼありません。
2. **時間帯で止める**：深夜は止めて、朝の利用開始前に1回だけ確実にリセットする。
3. **定期リセットをやめて、固まったときだけリセットする**：応答があるかを定期的に確認し、応答がないときだけ再接続する。無駄はいちばん少ないですが、「固まった」と判定する方法をちゃんと決める必要があります。

「無駄」というのは、ログが増える、リセット中に一瞬使えなくなる、負荷がかかる、のどれに近いでしょうか？ それによっておすすめが変わります。固まる症状自体がもう起きていないと分かっているなら、削除して様子を見るのもありです。

## ケース D-E11
了解です。まず「なぜ2回走るのか」を突き止めてから直します。ログを1行消すだけだと、再接続そのものは二重のまま残って、接続の取り合いや二重オープンの原因になりかねないからです。

調べる順番はこう考えています。
1. コードで「再接続した」のログを出している箇所と、再接続処理を呼んでいる箇所をすべて洗い出します。
2. 呼び出し元が複数ないか確認します。よくあるのは次のパターンです。
   - 切断イベントのハンドラ（例外の catch など）と、定期的な死活監視の両方が同じ切断を検知して、それぞれ再接続を呼ぶ
   - イベントリスナーやタイマーが二重に登録されている（初期化が2回走っている、再接続のたびにリスナーを追加している、など）
   - 再接続中にもう一度切断が検知されて、再接続が入れ子になる
3. 原因に合わせて直します。
   - 呼び出し元が複数あるなら、再接続を1か所にまとめるか、「再接続中」フラグ（`AtomicBoolean` の compareAndSet やロックなど）で、同時に1つしか走らないようにします
   - リスナーの二重登録なら、登録を1回だけにします

直したあとは、リーダーを実際に抜き差しして、ログの「再接続した」が1回だけになり、そのあとカードが読めることを確認する必要があります。差し支えなければ、2回出ているときのログの前後（タイムスタンプとスレッド名が分かるとなおよいです）を貼ってもらえると、原因を早く絞り込めます。

## ケース N2
作りましょう。CAD の前に、温湿度ロガーのケースで大事なポイントが1つあります。

**BME280 は ESP32-S3 の熱をすぐ拾います。** ESP32-S3 は Wi-Fi 使用中にかなり発熱するので、同じ箱の中に並べると、室温より数℃高く、湿度は低く出がちです。なので次の設計にします。
- BME280 は、ESP32 とは仕切り板で分けた別の部屋に入れるか、ケースの外側に突き出す「煙突」部分に入れる
- BME280 側には通気スリットを大きく取る。ESP32 側の熱が BME280 側に回らないよう、ESP32 側の排気は上向きにする
- （ソフト側）常時 Wi-Fi をつけず、測定→送信→ディープスリープにすると、発熱はかなり減ります

**寸法について**
DevKitC-1 の基板はおおよそ 63 × 25.5 mm 前後、BME280 モジュールは製品によって 10×13 mm〜15×11 mm くらいとばらつきがあります。手元の実物でノギスを当てて確認してほしい値を、下のコードの先頭に変数としてまとめました。特に次の値はお願いします。
- DevKitC-1：基板の長さ・幅、ピンヘッダを含めた高さ、USB-C の位置（S3 の DevKitC-1 は USB-C が2つあります。どちらから給電しますか？）
- BME280 モジュール：基板サイズ、穴の有無と位置

**OpenSCAD のたたき台**（寸法はすべて仮の値です）
```openscad
// ===== 実測して書き換える値 =====
esp_l = 63.0;  esp_w = 25.5;  esp_h = 15;   // 基板＋部品の高さ（ヘッダ込み）
usb_w = 10;    usb_h = 4.5;   usb_z = 3;    // USB-Cの開口と基板面からの高さ
usb_y = esp_w/2;                            // 使う方のUSB-Cの中心位置（幅方向）
bme_l = 15;    bme_w = 11.5;  bme_h = 4;
wall = 2;  clr = 0.5;  gap = 10;            // 壁厚・すき間・2部屋の距離

// ===== 本体 =====
inner_l = esp_l + clr*2;
inner_w = esp_w + clr*2 + 8;                // 配線の余裕
inner_h = esp_h + 5;
sensor_l = bme_l + 8;                       // センサー室の長さ

module vents(n, l, w, h) {
  for (i=[0:n-1]) translate([i*(l/n), 0, 0]) cube([l/n*0.5, w, h]);
}

difference() {
  cube([inner_l + sensor_l + wall*3 + gap, inner_w + wall*2, inner_h + wall]);
  // ESP32室
  translate([wall, wall, wall]) cube([inner_l, inner_w, inner_h + 1]);
  // センサー室（断熱のため gap を空ける）
  translate([wall*2 + inner_l + gap, wall, wall]) cube([sensor_l, inner_w, inner_h + 1]);
  // USB-C開口（短辺側）
  translate([-1, wall + clr + usb_y - usb_w/2, wall + usb_z]) cube([wall + 2, usb_w, usb_h]);
  // センサー室の通気スリット（両側面）
  translate([wall*2 + inner_l + gap + 2, -1, wall + 3]) vents(5, sensor_l - 4, inner_w + wall*2 + 2, inner_h - 6);
  // ESP32室の上部排気スリット（側面上の方）
  translate([wall + 5, -1, inner_h - 4]) vents(6, inner_l - 10, inner_w + wall*2 + 2, 3);
  // 2部屋のあいだの配線用の小穴（4本線が通る程度）
  translate([wall + inner_l - 1, wall + inner_w/2 - 3, wall + 2]) cube([gap + wall + 2, 6, 3]);
}
```
- 2つの部屋のあいだに空洞（`gap`）を入れて、熱が伝わりにくくしています
- フタは別パーツにして、はめ込みかネジ止めにする予定です。基板固定は、DevKitC-1 の取付穴に合わせたボス（柱）か、溝で挟む方式のどちらがよいですか？
- 置き方（机置き／壁掛け）も教えてください。壁掛けならセンサー室を下側にすると、ESP32 の熱が上に逃げて有利です

実測値と上の質問への答えをもらえたら、フタ・基板固定・印刷向き（サポートなしで刷れる形）まで入れて仕上げます。

## ケース N4
やりましょう。ただ本番なので、いきなり流す前に安全確認を挟ませてください。ユニーク制約の追加は、データの状態によっては失敗したり、テーブルをロックしてサービスを止めたりします。

**進め方**
1. **リポジトリの確認**：使っているマイグレーションの仕組み（Rails / Django / Prisma / Flyway / 素の SQL など）と、`users.email` の現在の定義を調べて、それに合わせた形式でマイグレーションを書きます。
2. **本番データの事前チェック（読み取りのみ）**：本番に読み取りクエリを流して、制約を付けられる状態か確認します。
   ```sql
   -- 完全一致の重複
   SELECT email, count(*) FROM users GROUP BY email HAVING count(*) > 1;
   -- 大文字小文字だけ違う重複
   SELECT lower(email), count(*) FROM users GROUP BY lower(email) HAVING count(*) > 1;
   -- 件数（ロック時間の見積もり用）
   SELECT count(*) FROM users;
   ```
   重複があったら制約は付けられないので、どちらを残すかはそちらで判断してもらう必要があります。私が勝手に消すことはしません。
3. **ロックを避けた書き方**：`ALTER TABLE ... ADD CONSTRAINT UNIQUE` を直接流すと、インデックスを作っている間ずっと書き込みが止まります。件数が多い場合は、2段階に分けます。
   ```sql
   -- トランザクションの外で実行する必要がある
   CREATE UNIQUE INDEX CONCURRENTLY users_email_key ON users (email);
   ALTER TABLE users ADD CONSTRAINT users_email_key UNIQUE USING INDEX users_email_key;
   ```
   `CONCURRENTLY` が途中で失敗すると INVALID なインデックスが残るので、そのときは削除してからやり直します。マイグレーションツールによっては、トランザクションを無効にする設定が必要です。
4. **大文字小文字の扱い**：`Foo@example.com` と `foo@example.com` を同一人物として扱いたいなら、`lower(email)` のユニークインデックスにするか、`citext` 型にするのがよいです。どちらにしますか？
5. **本番への適用**：先にステージング（またはローカルに本番相当のデータ）で試し、本番の直近バックアップがあることを確認してから流します。

**お願いしたいこと**
- 2の事前チェックを本番に（読み取りのみで）流してよいか
- 大文字小文字を区別するかどうか
- 本番に流すタイミング（アクセスが少ない時間帯がよいか）

本番への書き込み（マイグレーションの適用）は、チェック結果を見せて OK をもらってから実行します。
