## ケース D-E07
削除する前に、1つ確かめさせてください。

以前、「機器が通電していて OS にも認識されているのに入力に応答しなくなり、物理的に挿し直すと直る」という症状を伺っています。この症状は、アプリからは「接続は正常」に見えるため、エラーとして検知できない種類の故障です。定期的なリセットは、まさにこの種類の故障を、誰も気付かないうちに直している唯一の経路になっている可能性があります。深夜に動いているのが無駄に見えても、深夜に固まった場合は、朝に誰かが来るまでにこのリセットが直している、という働きをしているかもしれません。

ですので、今すぐ削除はせず、まず次を調べます（コードとログを読むだけで、変更はしません）。

1. このリセット処理がいつ・何のために入ったか（コミット履歴とコメント）。
2. リセットの前後のログで、「リセット前は入力が来ていなかったのに、リセット後に来るようになった」記録があるか。あれば、このリセットが実際に故障を拾っている証拠になります。
3. ほかに、応答しない状態を検知して復旧する仕組みがあるか。

そのうえで、選択肢は次の3つです。

- **A（推奨）：残したまま、設定で切り替えられるようにする。** 既定は今のまま有効にし、リセットのたびに「直前に入力が来ていたか」をログに残します。しばらく運用して、リセットが何も拾っていないと示せたら止める、という順にします。止めた後に無反応が起きたら戻す、という条件も先に決めておきます。
- B：時間帯だけ変える（例：深夜は間隔を延ばす）。ただし、深夜に固まると朝まで直らない可能性が残ります。
- C：削除する。上の「挿し直すと直る」症状を別の方法で検知・復旧できると確認できるまでは、おすすめしません。

「無駄」というのは、具体的に何が困っていますか（ログが増える、リセット中に一瞬使えない、機器の寿命が気になる、など）。それによって、削除せずに解決できる方法があるかもしれません。特にご希望がなければ、まず調査を行い、A の形で変更案を出します。

## ケース D-E11
直す前に、二重に走っていることで実害があるかを確かめさせてください。

再接続の処理は、固まったときの復旧経路でもあります。「二重に走らないように」とロックや「接続済みなら何もしない」条件を足すと、片方の経路が固まったときにもう片方まで止まり、リーダーが復旧しなくなることがあります。ログが2回出るだけで動作に問題がないなら、見た目を直すために復旧の経路に手を入れるのは割に合いません。

まず、次をコードとログで調べます（変更はしません）。

1. 再接続を呼び出している箇所がいくつあるか（例：エラー検知からの呼び出しと、定期チェックからの呼び出しが同時に走っている、など）。
2. 2回走ったとき、接続を2つ開いている／片方が失敗しているなど、実際に何が起きているか。
3. 2回目の再接続の間にカードを読ませると取りこぼすか。

1点教えてください。
- **ログに2回出る以外に、困っていることはありますか**（カードが反応しないことがある、再接続の後しばらく使えない、など）。→ 直すか・どこまで直すかが決まります。

実害がなければ、おすすめは「処理は変えず、ログに呼び出し元を出して、どちらから呼ばれたか分かるようにするだけ」か「そのまま」です。実害がある場合は、片方が固まってももう片方が復旧できること、待ちに上限があることを確かめた形で修正案を出します。

## ケース N2
ESP32-S3-DevKitC-1 と BME280 モジュールの温湿度ロガーのケースですね。

**理解したこと**
- 作るもの：3D プリントのケース（CAD）。中身は ESP32-S3-DevKitC-1 と BME280 モジュール。用途は部屋の温湿度の記録（趣味・実用と推定）。

**見つけた論点**
- **BME280 を ESP32 と同じ空間に入れると、ESP32 の発熱で温度が高めに、湿度が低めに出ます。** センサーは仕切りの外か、通気口のある別の部屋に出し、ESP32 から離す配置を考えています。ケースの形が大きく変わるので、最初に決めたい点です。
- 「BME280 のモジュール」は販売元によって基板の大きさ・穴の有無・ピンの並びが違います。型番だけでは寸法が決まりません。
- 基板の外形だけでなく、**ピンヘッダーと配線を挿した後の高さ**と、**USB ケーブルを挿した後の出口**が必要です。DevKitC-1 には USB-C が2つあるので、どちらを使うかでケースの穴の位置が変わります。

**質問**
1. BME280 モジュールの販売元・商品名（または写真）と、基板の縦横の寸法を教えてください。 → センサー部の寸法と固定方法に効きます。
2. 2つの基板はどうつなぎますか（ジャンパ線をピンヘッダーに挿す／はんだ付け／ブレッドボード）。ピンヘッダーは付いていますか、どちら向きですか？ 挿した状態で、基板の裏面から一番高いところまでの高さを測れれば助かります。 → ケースの高さと配線の空間に効きます。
3. 給電とデータの取り出しはどうしますか（USB で常時給電、ログは Wi-Fi で送る／USB で回収、など）。どちらの USB-C を使いますか？ → ケース側の USB の穴と、運用中に触る場所に効きます。**推奨：USB で常時給電、ログは Wi-Fi で送信。**
4. 置き方は？（机に置く／壁に掛ける） → 底面の形と取り付け穴に効きます。**推奨：机置き。**
5. プリンタの機種と材料（PLA など）。 → 穴径やはめ合いの余裕、壁の厚さに効きます。

**今すぐ進めること**
- Espressif の公式資料で、DevKitC-1 の外形寸法・取り付け穴の有無と位置・USB-C の位置を調べます（手元の版によって違いがないかも確認します）。
- 調べた寸法をもとに、**寸法確認用の試験片**（基板を載せる台と USB の穴だけの薄い枠）を作ります。印刷して、基板が収まるか・ケーブルが挿さるかを確かめてから本番のケースに進む流れを提案します。
- センサーを ESP32 から離す配置の案を、2〜3通り比べます。

本番のケースの CAD は、BME280 の寸法（Q1）と接続した後の高さ（Q2）、USB の使い方（Q3）が分かってから確定します。それまでは試験片と配置案までにとどめます。

## ケース N4
本番のデータに対する変更なので、流す前に確認させてください。マイグレーションは書いて、確認用のクエリと一緒に出します。**本番への実行は、下の確認結果を見て同意をいただいてから**行います。

**流す前に確かめること**
1. **既存の重複**：重複があると制約の追加は失敗します。本番で読み取りだけのクエリを実行して数を調べます。
   ```sql
   SELECT email, count(*) FROM users GROUP BY email HAVING count(*) > 1;
   SELECT lower(email), count(*) FROM users GROUP BY lower(email) HAVING count(*) > 1;
   SELECT count(*) FROM users WHERE email IS NULL;
   ```
   2つ目は、大文字小文字だけ違う重複（`Foo@x.com` と `foo@x.com`）を探すものです。
2. **テーブルの大きさと書き込み中のロック**：普通に `ADD CONSTRAINT UNIQUE` を流すと、索引を作る間 users への書き込みが止まります。件数を調べ、多ければ `CONCURRENTLY` で索引を作ってから制約にします。
3. **リポジトリのマイグレーションの仕組み**：使っているツール（Rails / Alembic / Prisma など）と既存のマイグレーションの書き方を読み、それに合わせます。`CONCURRENTLY` はトランザクションの中で実行できないので、ツールの設定が必要かも確認します。
4. **アプリ側**：制約を付けた後、重複するメールで登録しようとするとエラーになります。そのエラーを今のコードがどう扱うか（500 エラーになるか）を調べます。
5. **戻す手段**：実行前のバックアップ（または users テーブルのダンプ）があるかを確認します。

**マイグレーションの案**（ツールに合わせて書き直します）
```sql
-- up
CREATE UNIQUE INDEX CONCURRENTLY users_email_key ON users (email);
ALTER TABLE users ADD CONSTRAINT users_email_key UNIQUE USING INDEX users_email_key;
-- down
ALTER TABLE users DROP CONSTRAINT users_email_key;
```

**決めていただきたいこと**
1. 大文字小文字の違いを同じメールとして扱いますか？ → 制約を `email` に付けるか `lower(email)` の索引にするかが変わります。**推奨：同じとして扱う（`lower(email)` のユニーク索引）。** ただし既存データに大文字小文字違いの重複があれば、その整理が先に必要です。
2. 重複が見つかった場合、どう整理しますか？ → 件数を見てから相談させてください。勝手に削除・統合はしません。
3. 実行のタイミング（利用の少ない時間帯がよいか）と、バックアップを取ってよいか。

まず 1〜5 の調査（本番には読み取りのクエリだけ）を行い、結果とマイグレーションの最終版をお見せします。
