## ケース D-E07
教えてくださってありがとうございます。それなら、**この定期リセットは削除しない方がよい**と考えます。

「応答しない状態をソフトで見分けられない」ということは、いま固まった機器を自動で回復させている仕組みはこの定期リセットだけ、ということです。削除すると、固まったときに気づく手段も直す手段もなくなります。結果として、使おうとした人が反応しない機器に当たってはじめて分かり、手で抜き差しする運用に戻ります。ログにも記録がないので、削除したあとに「固まる症状がどれくらい起きていたか」を確かめることもできません。

深夜に動くことにも意味があります。夜中に固まった場合、次のリセットまでは固まったままなので、深夜のリセットは「朝には使える状態にしておく」役割を果たしています。

それでも深夜の動作を減らしたい場合は、次の折衷案ができます。
- **深夜帯は止めて、朝の利用開始前に1回だけ確実にリセットする**
  - 深夜の実行回数は減ります。そのかわり、朝の1回が失敗したり時刻がずれたりすると、固まったまま朝を迎えるリスクが少し上がります。
  - 利用開始の時刻（例：何時から人が来るか）を教えてもらえれば、その少し前に入れます。

あわせて、今後のためにおすすめしたいことがあります。
- **リセットを実行した時刻と、その前後で最後に入力を受け取った時刻をログに残す。** 「リセット前は長時間入力がなかったのに、リセット直後に入力が来た」というパターンが積み重なれば、固まっていた可能性が高かった時間帯が見えてきます。将来「固まったときだけリセットする」方式に切り替えられるかの判断材料にもなります。

まずコードを読んで、リセットの実行間隔と、1回のリセットで何をしているか（どれくらいの時間使えなくなるか）を確認します。そのうえで、
1. 現状のまま残す（ログ追加だけする）
2. 深夜は止めて、朝の前に1回リセットする

のどちらにするか決めてもらえますか？ 削除はおすすめしませんが、それでも削除したい場合は、そのリスクを承知のうえでということで対応します。

## ケース D-E11
なるほど、2つの経路は意図した設計で、片方は保険なんですね。それなら保険の経路は残したまま直します。

ログが2回出るということは、**本来の経路で再接続が成功しているのに、保険の経路も「動かなかった」と判断して再接続している**可能性が高いです。いまは実害がなくても、次のような問題につながりかねません。
- 保険が「本命が失敗したとき」だけでなく毎回動いているので、保険としての条件判定が意図どおりになっていない
- 2回目の再接続で、1回目でつながった接続を閉じて開き直していると、タイミングによってはその瞬間のカード読み取りを取りこぼす
- ログを見ても、本当に保険が必要だった場面と区別できない

**直し方の方針**
1. 保険の経路が動く条件を確認します。「一定時間待っても接続が戻っていなければ再接続」のような条件になっているはずなので、その判定が「本命の再接続が成功した」ことを見ているかを調べます。
2. 保険の経路は、再接続する前に「もう接続できているか」「本命の再接続がいま進行中か」を確認し、どちらかなら何もしないようにします。両方の経路が同時に走らないよう、再接続そのものもフラグかロックで1つに絞ります。
3. ログに経路を区別するための情報を入れます（例：「再接続した（通常）」「再接続した（保険）」）。今後、保険が実際に働いたときに分かるようになります。

**確認方法**
- リーダーを抜き差しして、「再接続した（通常）」が1回だけ出て、カードが読めること
- できれば、本命の経路を一時的に失敗させて（テスト用に）、保険の経路だけで再接続できることも確認したいです。保険は普段動かない分、壊れていても気づきにくいので。

コードを読んで、2つの経路と保険の発動条件を確認してきます。

## ケース N2
ありがとうございます。いただいた条件で設計を更新します。

**条件から決めたこと**
- **壁掛け**：センサー室を下、ESP32 室を上に配置します。ESP32 の熱は上に逃げるので、下のセンサーに熱が回りにくくなります。背面には鍵穴型の穴を2つ開けて、壁のネジやピンに引っかけられるようにします。
- **常時給電**：Wi-Fi をつけっぱなしにすると発熱が続くので、2部屋の分離はより重要になります。ソフト側で、測定の間隔をあけてスリープさせると、さらに有利です。
- **USB-C ケーブル**：ESP32 室の側面から出して、下に垂らす形にします。
- **BME280（ピンヘッダ上向き、ジャンパ線）**：ヘッダ（約8.5 mm）＋ジャンパ線のコネクタ（約14 mm）が上に立つので、モジュールの上には少なくとも 25 mm 程度の空間が必要です。ケースの奥行きはこれで決まります。
- **2部屋の間の配線**：ジャンパ線4本を通す穴を開けます。通したあとに穴をパテや練り消しなどでふさぐと、ESP32 室の暖かい空気がセンサー室に流れ込みにくくなります。

**確認したいこと**
1. DevKitC-1 側も、ジャンパ線でつなぎますか？ 標準ではピンヘッダが下向きにはんだ付けされているので、その場合は基板の下にも 25 mm 程度の空間が必要です（下のコードはこの前提で、基板を柱で浮かせています）。
2. 給電は2つある USB-C のどちらを使いますか？ 開口の位置が変わります。
3. 寸法の実測値（DevKitC-1 の基板サイズと取付穴の位置、BME280 モジュールの基板サイズ）。下のコードはまだ仮の値です。

**OpenSCAD 更新版（寸法は仮の値）**
壁に付く背面を XY 平面、奥行きを Z（手前方向）として作っています。
```openscad
// ===== 実測して書き換える値 =====
esp_l = 63.0; esp_w = 25.5;             // DevKitC-1 基板
esp_hole_dx = 58; esp_hole_dy = 20;     // 取付穴の間隔（仮）
usb_w = 10; usb_h = 4.5;                // USB-C 開口
bme_l = 15; bme_w = 11.5;               // BME280 基板
// ===== 設計値 =====
wall = 2; clr = 0.5;
standoff_h = 25;      // ESP32 基板を浮かせる高さ（下向きピン＋ジャンパ線）
depth = 45;           // 内寸の奥行き（柱＋基板＋部品＋余裕）
gap = 10;             // 2部屋の間の空洞（断熱）
in_w = esp_l + clr*2 + 6;               // 内寸の幅（基板を横向きに配置）
esp_room_h = esp_w + clr*2 + 10;
bme_room_h = 30;
total_h = wall + bme_room_h + wall + gap + wall + esp_room_h + wall;

module slots(n, len, w, h) { for (i=[0:n-1]) translate([i*len/n,0,0]) cube([len/n*0.5, w, h]); }
module keyhole() { // 鍵穴：頭用の丸穴＋上に伸びる溝
  cylinder(d=8, h=10, $fn=32);
  translate([-2,0,0]) cube([4,8,10]);
}

difference() {
  cube([in_w + wall*2, total_h, depth + wall]);  // 前面は開放、フタは別パーツ
  // センサー室（下）
  translate([wall, wall, wall]) cube([in_w, bme_room_h, depth + 1]);
  // 断熱用の空洞
  translate([wall, wall + bme_room_h + wall, wall]) cube([in_w, gap, depth + 1]);
  // ESP32 室（上）
  translate([wall, wall + bme_room_h + wall*2 + gap, wall]) cube([in_w, esp_room_h, depth + 1]);
  // センサー室の通気スリット（下面と両側面）
  translate([wall + 4, -1, wall + 5]) slots(6, in_w - 8, wall + 2, depth - 10);
  translate([-1, wall + 4, wall + 5]) rotate([0,0,90]) translate([0,-in_w - wall*2 - 2,0]) slots(4, bme_room_h - 8, in_w + wall*2 + 4, depth - 10);
  // ESP32 室の排気スリット（上面）
  translate([wall + 4, total_h - wall - 1, wall + 5]) slots(6, in_w - 8, wall + 2, depth - 10);
  // USB-C 開口（左側面、基板面の高さ）
  translate([-1, wall + bme_room_h + wall*2 + gap + esp_room_h/2 - usb_w/2, wall + standoff_h]) cube([wall + 2, usb_w, usb_h]);
  // 配線穴（空洞を貫通、ジャンパ線4本分）
  translate([wall + in_w/2 - 5, wall + bme_room_h - 1, wall + 10]) cube([10, gap + wall*2 + 2, 6]);
  // 背面の鍵穴（壁掛け用）
  for (x = [wall + 10, in_w + wall - 10]) translate([x, total_h - 20, -1]) keyhole();
}
// ESP32 を浮かせる柱（M2.5 ネジ用の下穴付き）
esp_y0 = wall + bme_room_h + wall*2 + gap + (esp_room_h - esp_hole_dy)/2;
esp_x0 = wall + (in_w - esp_hole_dx)/2;
for (dx=[0,esp_hole_dx], dy=[0,esp_hole_dy])
  translate([esp_x0 + dx, esp_y0 + dy, wall]) difference() {
    cylinder(d=6, h=standoff_h, $fn=24);
    cylinder(d=2.2, h=standoff_h + 1, $fn=16);
  }
// BME280 を挟む溝付きの台（センサー室の中央、背面に固定）
translate([wall + in_w/2 - bme_l/2 - 2, wall + bme_room_h/2 - bme_w/2 - 2, wall]) difference() {
  cube([bme_l + 4, bme_w + 4, 4]);
  translate([2 - clr/2, 2 - clr/2, 2]) cube([bme_l + clr, bme_w + clr, 3]);
}
```
- 印刷は、背面を下にして置けばサポートなしで刷れる形にしています（鍵穴とスリットの上端だけ、ブリッジになります）。
- フタ（前面）は、上の箱の外形に合わせた板に、センサー室側だけ通気スリットを入れて、はめ込み式で作る予定です。
- BME280 は、溝に置いてフタで軽く押さえる形にしています。溝がきつい・ゆるい場合は `clr` で調整できます。

上の1〜3を教えてもらえたら、実寸に合わせてフタまで含めて仕上げます。

## ケース N4
了解です。20万行で、ログインに email を使っているとのことなので、それに合わせて進めます。

**20万行なら**
インデックス作成は短時間で終わる見込みですが、ログインで常に読み書きされるテーブルなので、念のため書き込みを止めない `CREATE UNIQUE INDEX CONCURRENTLY` の方式で進めます。

**これからやること（本番への読み取りのみ）**
本番に次の確認クエリを流します。どれも SELECT だけで、データは変更しません。

```sql
-- 1. 完全一致の重複
SELECT email, count(*) FROM users GROUP BY email HAVING count(*) > 1;

-- 2. 大文字小文字・前後の空白だけ違う重複
SELECT lower(trim(email)) AS norm, count(*), array_agg(id) AS ids
FROM users GROUP BY lower(trim(email)) HAVING count(*) > 1;

-- 3. email が NULL の行の数（ユニーク制約では NULL は重複扱いにならない）
SELECT count(*) FROM users WHERE email IS NULL;

-- 4. email 列の型と、すでにあるインデックス・制約
SELECT column_name, data_type FROM information_schema.columns
WHERE table_name = 'users' AND column_name = 'email';
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'users';
```

あわせてリポジトリ側で、
- ログイン時に email をどう照合しているか（完全一致か、`lower()` などで大文字小文字を無視しているか）
- 新規登録時に email を小文字に揃えているか
- 使っているマイグレーションの仕組み

を確認します。ログインの照合方法によって、作るべき制約が変わるためです。
- 完全一致で照合しているなら：`Foo@x.com` と `foo@x.com` は別アカウントとして存在できてしまっているので、2のクエリで重複が見つかれば「同じ人が2つアカウントを持っている」状態です。
- 大文字小文字を無視して照合しているなら：制約も `lower(email)` に対するユニークインデックスにしないと、制約とログインの挙動が食い違います。

**結果が出たあとの流れ**
1. 確認結果をそのままお見せします（重複が見つかった場合は、該当の id とメールアドレスの一覧）。
2. 重複があれば、どちらのアカウントを残すか・統合するかはそちらで判断してください。ほかのテーブルが user の id を参照している可能性があるので、私の判断では消しません。
3. 重複がなくなったら、マイグレーションを書いて、ステージング（またはローカル）で試します。
4. 本番適用は、バックアップの確認と、実行タイミングについての OK をもらってから行います。`ALTER TABLE ... ADD CONSTRAINT ... USING INDEX` の瞬間だけ短時間テーブルをロックするので、`lock_timeout` を設定して、長いクエリの後ろで待ちが連鎖しないようにします。

まず上の確認クエリを本番で実行し、リポジトリのログイン処理を読みます。結果が出たら報告します。
