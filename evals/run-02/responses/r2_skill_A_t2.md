## ケース H-E01
ありがとうございます。接続の向きが分かったので、フレームのどこに空間が要るかが決まりました。台帳に反映します。

**今回分かったこと（台帳に記録）**
- Pico 2 WH：ピンは下向き。メスのジャンパ線を**下から**挿す → Pico の**下側**に「基板の厚さ＋ヘッダー＋ジャンパのハウジング＋線の曲げ」の空間が要る。
- IMU 基板：ヘッダーは上向き → ジャンパは**上から**挿す → IMU の**上側**に同じ種類の空間が要る。
- USB：組み立てた後も書き込みで使う → Pico の USB 端子の前は、ケーブルのプラグが挿さる空間を空けておく（フレームの壁や電池と干渉させない）。
- 挿した後の高さ・線の出口：未測定。

**設計への影響**
- Pico を板に直接寝かせることはできません。Pico は**スペーサーで浮かせる**か、**中央板に窓を開けてジャンパを下へ逃がす**かのどちらかになります。どちらを取るかは、下にどれだけの高さが要るかと、線をどちらへ出すかで決まります。
- IMU は上に線が出るので、その上に別の板（電池の台など）を重ねる場合は、IMU の上の高さが効きます。
- ジャンパのハウジングは1本ずつ並ぶと幅も取るので、ヘッダーの列の外側にも余裕が要ります。

**測ってほしいこと（実際に挿した状態で）**
1. Pico：**Pico 基板の下の面**から、挿したジャンパの**線がまっすぐ出る先端**まで。そのまま線を横へ曲げたとき、曲げた線の一番下まで。
2. IMU：**IMU 基板の下の面**から、挿したジャンパの線の一番上まで（曲げた状態も）。
3. 線を出したい方向：Pico と IMU それぞれ、どの辺の方へ線を逃がしたいか（ESC の方、など）。決めていなければ「特になし」で大丈夫です。こちらで ESC の位置に合わせて提案します。

測る基準（基板の下の面から）をそろえてもらえれば、写真でなく数字で設計できます。

**まだ答えをもらっていないこと（前回の質問から）**

- モーター・プロペラのサイズと電池 — フレームの大きさを決めるため。決まっていなければ「お任せ」で、小型機の推奨案で仮決定して進めます。

**今すぐ進めること**

## ケース H-E02
ありがとうございます。研究の問いが分かったので、センサーの判断基準がはっきりしました。

**研究の整理（仮）**
- 問い：RP2350 上で、制御と TinyML 推論を同時に動かすと、制御がどれだけ影響を受けるか。
- 比較する条件：①制御だけ（基準） ②制御＋推論（推論の負荷や実行の仕方を変えるなら、その段階も）
- 測るもの：制御の応答（周期・遅れ・揺らぎ）と、倒立の性能（傾きの揺れ、外乱からの復帰）

**MPU-6050 の判断への影響**
この研究で比べるのは「同じ機体での条件の違い」なので、センサーが最高性能である必要はありません。必要なのは次の2点です。
1. **倒立の性能を測る道具として**、条件の間の差より、センサーの雑音やドリフトが十分小さいこと。
2. **制御周期に追いつく読み出し速度**があり、その読み出し自体が推論と干渉の原因にならないこと（I²C の待ちや割り込みは、まさに測りたい「干渉」と混ざります）。

どちらも、周期が決まらないと判定できません。そこで、**手持ちの MPU-6050 で仮決定し、基準の測定（①）で雑音と読み出し時間を実測して、足りるかを判定する**進め方を推奨します。足りなければ、その時点で代替候補を総額で比べます。いま高いセンサーに替える必要はありません。

**決めておくべきこと（周期と測り方）**
周期と測り方はまだ決まっていないとのことなので、こちらで案を作ります。案の前提だけ確認させてください。
1. 推論はどのコアで動かす想定ですか（制御と同じコアで割り込み／もう一方のコアで並行／未定）— 「干渉」の中身（CPU 時間の取り合いか、メモリやバスの競合か）が変わり、比較の条件の作り方が変わります。未定なら、両方を比較条件に入れる案を出します。
2. 推論するモデルや入力はある程度決まっていますか（何を推論するか、だいたいの大きさ）— 推論の負荷の段階を決めるのに使います。未定なら、負荷を変数にできる仮のモデルで進めます。
3. 使える測定器はありますか（ロジックアナライザ、オシロスコープ）— 制御周期の揺らぎを、マイコンの外から測れるかに効きます。なければ、マイコン内のタイマーで記録する方法にします（ただしその記録自体の負荷も見積もります）。
4. 提出・発表の期限 — 基準の測定にどれだけ時間を割けるかに効きます。

**今すぐ進めること**
- MPU-6050 のデータシートから雑音・最大出力レート・I²C の速度を調べ、候補の制御周期（数段階）ごとに、読み出しにかかる時間を計算します。計算値として記録し、実測で確かめる前提にします。
- 評価計画の下書きを作ります：基準（制御だけ）の測定 → 推論を加えた条件 → 測る区間（例：IMU 読み出しからモーター指令までの時間を、ピンの上げ下げで外から測る）→ 倒立の指標 → 交絡要因（電池の電圧、床、温度、ログ出力の負荷）→ 差が出なかった場合の扱い。
- ログの取り方（測定がそれ自体の負荷にならない方法、異常停止時にデータが残るか）も計画に入れます。

**台帳の変更点**：目的に研究の問いを記録。マイコン＝RP2350（ユーザー申告）。IMU＝MPU-6050 で**仮決定**（確かめる方法＝基準の測定で雑音と読み出し時間を実測。外れたときの影響＝IMU の交換と配線・ドライバの変更）。未回答の質問に上の1〜4を追加。比較実験は保留（足りない条件＝周期、測る区間と方法、基準性能の確認）。

## ケース H-E03
ありがとうございます。台帳に反映しました。

**今回分かったこと**
- 研究機体と共有するのは**バッテリーだけ**。それ以外（電源回路、マイコン、IMU、ファームウェア、機体）は趣味ドローン用に別に決めます。
- Pico W はヘッダー付き → ジャンパ線やソケットで配線する前提になります。搭載するときは、挿した後の高さと線の出口が必要になります（CAD に入る段階で測ってもらいます）。
- 給電の方法と、バッテリーの交換の方法はこれから決める。

**バッテリーだけ共有することで決まること**
- ドローン側は、**研究機体のバッテリーをそのまま挿せるコネクター**にするか、変換ケーブルを用意する必要があります。
- バッテリーの**外形と線の出口**が、ドローンの電池の台の寸法を決めます。両方の機体で使い回すので、ドローン側の固定（ベルトやトレー）は、工具なしで素早く外せる形が向いています。
- 一番大事なのは、**そのバッテリーがドローンのモーター電流に耐えられるか**です。倒立ロボットより大きな電流が流れることが多いので、放電能力（C レート）と電圧（セル数）を確かめます。足りなければ、共有はやめてドローン専用の電池にする判断になります。

**決めることの選択肢（推奨つき）**
1. **給電の方法**（Pico W への 5V などをどこから取るか）
   - A：ESC に付いている BEC（5V 出力）から取る
   - B：別の降圧レギュレータをバッテリーから取る
   どちらが使えるかは、使う ESC とバッテリーの電圧で決まります。推奨は、ESC の仕様を見てから決めることです。ESC が決まっていなければ B を仮置きにします。
2. **交換の方法**：推奨は、機体の上か下にバッテリーをベルトで留め、コネクターに手が届く位置に置く形です。充電は機体から外して行う前提にします。

**お聞きしたいこと（前回からの続き）**
1. 研究機体のバッテリーの仕様（セル数・容量・C レート・コネクターの種類）と、だいたいの外形 — 共有が成り立つかの計算と、電池の台の寸法に使います。型番か購入ページがあれば、こちらで調べます。
2. ドローンの大きさ（プロペラのサイズ）か目標（まずホバリング、など）— モーター電流の見積もりに使います。特になければ、小型でホバリングを目標に仮決定します。

**今すぐ進めること**
- RP2040（Pico W）と MPU-6050 の仕様（I²C、PWM、電源電圧）を調べ、ドローン制御に使えるかを確認します。
- Pico W の給電端子（VSYS など）と電圧の範囲を公式資料で調べ、上の A・B のどちらでも給電できる配線の候補を用意します。
- バッテリーの仕様をもらい次第、モーター電流の見積もりと照らして、共有できるかを判定します。

**台帳の変更点**：共有範囲＝バッテリーのみ（決定、ユーザー申告）。Pico W＝ヘッダー付き（ユーザー申告）。未回答の質問：給電の方法、交換の方法（推奨案つき）、バッテリーの仕様、機体の大きさ。リスク：バッテリーの放電能力がドローンの電流に足りない可能性（対策＝仕様で計算、足りなければ専用電池）。

## ケース D-E01
教えていただきありがとうございます。それが分かったのは大きいです。コードを A に戻すだけでは、**実機で B の常駐プロセスが動き続け、設定ファイルの数値も B 用のまま**になるので、A が動かない可能性が高いです。実機側も一緒に戻す必要があります。

**進め方**
リポジトリの作業（保存 → 3ファイルを戻す → ビルド）はこのまま進めます。実機側は、ご自身で操作していただく前提で、確認 → 保存 → 戻す、の順に手順を出します。

**1. リポジトリ側（こちらで行います）**
- 今の B 方式のコードをブランチとして保存します。
- 履歴から A→B に書き換えたコミットを探し、3ファイルを書き換え前の版に戻してビルドします。
- 同時に、リポジトリの中で**設定ファイルの項目を読んでいるコード**を探し、A 方式のときに使っていた値の手がかり（既定値、コメント、サンプル設定、書き換えコミットの説明）がないかを調べます。設定ファイルが実機にしかないので、元の数値はここから推定するしかないかもしれません。見つかったものは「推定」として示し、確定値としては扱いません。

**2. 実機側：まず今の状態を見る（変更はしません）**
どれも**実機に SSH などでログインした端末（Linux のシェル）**で、1行ずつ実行してください。

B の常駐プロセスの名前を探す（`B` の部分はツール B の名前に置き換えてください）：
```
systemctl list-units --type=service --all | grep -i B
```
→ サービス名が1行以上出れば、それが対象です。何も出なければ、systemd 以外で起動している可能性があるので教えてください。

そのサービスが有効か・動いているかを見る（`サービス名` は上で出た名前）：
```
systemctl status サービス名
```
→ `Loaded:` の行の `enabled`、`Active:` の行の `active (running)` を見てください。

設定ファイルの場所が分かっていれば、その中身を見る：
```
cat 設定ファイルのパス
```
→ 場所が分からなければ、ファイル名の一部やアプリの名前を教えてください。探すコマンドを出します。

出力を貼っていただければ（パスワードやトークンが含まれていたら、その部分は伏せてください）、どの値を B に合わせて変えたのかを一緒に見ます。

**3. 実機側：戻す前に保存する**
設定ファイルは実機にしかないので、変える前に必ずコピーを残します。上で場所が分かったら、日付付きのコピーを作るコマンドを出します。これで、A に戻してうまくいかなかったときに B の状態へ戻せます。

**4. 戻す順番（案）**
1. 設定ファイルをバックアップする
2. B の常駐プロセスを**停止**する（無効化＝自動起動の解除は、A の動作を確かめた後にする。うまくいかなければ再び起動するだけで B 方式に戻れるため）
3. 設定ファイルの数値を A 用に戻す
4. A でビルドしたものを実機に入れて、制御が効くかを確かめる
5. A で動くと確認できたら、B の常駐プロセスを無効化する

A 用の元の数値が分からない場合、3で何を入れるかが一番の未決になります。手がかりが見つからなければ、選択肢を示して相談させてください。

**確認したいこと**
- B のために**手で入れたパッケージ**もありましたか。残っていても A の動作に影響しないことが多いので、今回は消さずに残す（後で整理）ことを推奨します。

**台帳の変更点**：リポジトリ外の変更として「B の常駐プロセスを有効化（ユーザーの記憶）」「実機のみにある設定ファイルの数値を B 用に変更（ユーザーの記憶、変更箇所は未確認）」を記録。リスク：設定ファイルの A 用の元の値が不明。決定：B の常駐プロセスは、A の動作確認まで停止のみで無効化しない。
