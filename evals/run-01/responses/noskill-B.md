## ケース D-E01
了解しました。ライブラリA版に戻してビルドするまで進めます。手順は次のとおりです。

1. **書き換えたコミットを特定する**
   `git log` で、A→B（コマンドラインツール経由）に書き換えたコミットを探します。対象の3ファイルと、そのコミットの前後で何が変わったか（`git show` / `git log -- <ファイル>`）を確認します。
2. **書き換え以降にほかの変更が入っていないか確認する**
   書き換えたあとに、この3ファイルにB方式と関係ない修正（バグ修正や機能追加）が入っていると、単純に戻すとそれも消えてしまいます。その場合は `git revert` するか、該当の部分だけ戻すかを選びます。気になる変更が見つかったら、戻す前にご報告します。
3. **3ファイル以外に影響が残っていないか確認する**
   書き換えのときに、ビルド設定（Aへの依存の削除など）や、Bを呼ぶための設定・権限・パスがほかのファイルで変わっていないかを確認します。3ファイルだけ戻すとAのリンクが外れたままでビルドが通らない、ということがあるためです。
4. **戻してビルドする**
   3ファイルを書き換え前の状態に戻し、ビルドを実行します。結果（成功、または失敗とそのエラー内容）はそのままお伝えします。

これから `git log` で該当コミットを調べるところから始めます。なお、「Aで問題なかった」ことは実機では確認していないので、ビルドが通ったあとに、実機でAの制御が動くかの確認はお願いします。

## ケース D-E07
削除する前に、ひとつ確認させてください。

以前、「機器が通電・認識されているのに入力に応答しなくなり、物理的に再接続すると直る」と伺いました。この定期リセットは、その症状への対策（応答しなくなっても自動で回復させる仕組み）として入っている可能性があります。もしそうなら、削除するとその症状がまた出て、誰かが再接続するまで止まったままになるおそれがあります。

まず次の2点を調べます。
- このリセット処理がいつ・どんな目的で入ったか（コミット履歴やコメント）
- 実際にリセットで回復している形跡があるか（ログに「リセット前は無応答 → 後で復帰」の記録があるか）

そのうえで、選択肢は次のとおりです。
1. **深夜は止める**：時間帯で制御します。ただし深夜に固まると、朝まで復旧しません。朝に使えればよいならこれで十分です。
2. **必要なときだけリセットする**：定期的に一律リセットするのをやめて、無応答を検知したときだけリセットします。深夜の無駄はなくなり、固まったときの対策も残ります。いちばんおすすめです。
3. **完全に削除する**：応答しなくなる問題が別の方法で解決済みであれば、これで問題ありません。

応答しなくなる問題はもう解決していますか？ それとも、このリセットで回避している状態でしょうか。お返事をもらってから手を付けます。

## ケース D-E11
承知しました。ログの出力を1回にするだけではなく、再接続そのものが二重に走っている原因を直します（ログだけ消すと、二重接続によるリソースの取り合いなどが残るためです）。

手順は次のとおりです。
1. **再接続を開始している箇所をすべて洗い出す**
   「再接続した」のログを出している箇所と、再接続処理を呼んでいる箇所をコード全体から検索します。よくある原因は次のとおりです。
   - 切断イベントのハンドラと、定期的な死活監視（ウォッチドッグ）の両方が切断を検知して、それぞれ再接続する
   - エラー時のリトライと切断コールバックが同時に起きる
   - リスナーやハンドラが2回登録されている（初期化が2回走っている）
2. **ログのタイムスタンプとスレッド名を確認する**
   2回のログがほぼ同時なら並行して呼ばれている、間隔があるなら順に2回呼ばれている、と切り分けられます。
3. **修正**
   原因に応じて、再接続を開始する経路を一本化するか、再接続処理に「すでに再接続中なら何もしない」ガードを入れます（フラグやロック、または単一の再接続ジョブに集約）。ハンドラが重複して登録されている場合は、登録が1回だけになるように直します。
4. **確認**
   切断を再現して（リーダーを抜き差しするなど）、ログが1回だけになり、再接続後に正常に読み取れることを確かめます。

まずはコード内の再接続の呼び出し元を検索します。原因がわかったら、修正内容と一緒にご報告します。

## ケース D-E13
反映の手順です。実行はご自身でお願いします。

```bash
# 1. 転送（いったん一時名で置く）
scp build/libs/app-all.jar user@pi:/opt/app/app-all.jar.new

# 2. Pi にログイン
ssh user@pi

# 3. 現行版をバックアップしてから差し替え
cd /opt/app
cp -p app-all.jar app-all.jar.bak   # 現行版がある場合
mv app-all.jar.new app-all.jar

# 4. サービスを再起動
sudo systemctl restart app

# 5. 起動を確認
systemctl status app
journalctl -u app -n 50 --no-pager   # 起動直後のログ
```

**確認しておいてほしい点**
- **サービスが読み込む jar のファイル名**：`systemctl cat app` の `ExecStart` に書かれている jar のパスが `/opt/app/app-all.jar` か確認してください。別の名前（バージョン付きなど）なら、手順3の名前をそれに合わせてください。
- **書き込み権限**：`/opt/app/` に `user` で書き込めない場合は、`/tmp` などに scp してから `sudo mv` で移してください。サービスを別ユーザーで動かしている場合は、所有者もそろえてください（`sudo chown <サービスのユーザー>: app-all.jar`）。
- **一時名で転送している理由**：転送中にサービスが再起動すると、書きかけの jar を読み込んでしまうためです。

**元に戻すとき**
```bash
cd /opt/app && mv app-all.jar.bak app-all.jar && sudo systemctl restart app
```

## ケース D-E15
「エラーが出ずに固まる」場合、原因の候補が多いので、当てずっぽうで修正するより、まず固まっているときに何が起きているかを押さえるのが近道です。いくつか教えてください。

**状況の確認**
1. 「固まる」のは何ですか？（アプリ全体が無反応／機器への出力が止まる／機器からの入力に反応しない／画面が止まる、など）
2. 固まったとき、アプリのプロセスは生きていますか？（`systemctl status` や `ps` で確認できます）
3. どうすると直りますか？（アプリの再起動／機器の抜き差し／Pi の再起動）
4. 頻度ときっかけ（起動から何時間後か、特定の操作のあとか）
5. 機器とはどうつながっていますか？（USB シリアル／GPIO／I2C など）

**次に固まったときに取ってほしい情報**（これがいちばん役に立ちます）
```bash
# スレッドダンプ（どこで止まっているかがわかります）。数秒おいて2〜3回取ってください
jcmd <PID> Thread.print > dump1.txt
# jcmd がなければ: kill -3 <PID>（標準出力側、たとえば journalctl に出ます）

# 直前のログ
journalctl -u <サービス名> --since "10 min ago"

# メモリ・CPU の状況
top -b -n 1 | head -20
dmesg | tail -50     # USB の切断・再列挙などが出ていないか
```

スレッドダンプを見れば、デッドロック、I/O 読み取りでのブロック（タイムアウトなし）、コルーチンや Executor の詰まりのどれなのかを切り分けられます。dmesg に USB の切断が出ていれば、ハード側や電源の問題の可能性も出てきます。

並行して、ソースコードも確認できます。リポジトリを見てよければ、機器との通信部分（タイムアウトなしの read、synchronized・ロックの使い方、例外を握りつぶしている catch など）から調べます。
