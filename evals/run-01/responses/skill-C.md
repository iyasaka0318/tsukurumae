## ケース X-E07
状況は把握しました。今わかっているのは、「Web UI が開錠と表示した」「アプリのログに角度の指令が出た」の2点です。どちらもアプリの中の話で、サーボまで信号と電源が届いたかはまだわかりません。原因を決めつけず、層ごとに「どこまで届いているか」を確かめます。

**こちらで先に調べること（ユーザーの作業は不要）**
- `TSUKURUMAE_LEDGER.md` があれば読みます。過去の変更（PWM のライブラリや方式、常駐プロセス、実機にだけある設定）が記録されていないか見ます。
- リポジトリのコードを読み、次を確認します。
  - サーボの駆動に使っているライブラリ（pigpio / gpiozero / RPi.GPIO / ハードウェア PWM など）
  - 使っている GPIO ピン
  - 角度からパルス幅への換算と、範囲の上限・下限
  - ライブラリの初期化に失敗したときの挙動。例外を握りつぶしてログだけ出す作りではないか
- 最近のコミットに、サーボまわりやサービス設定の変更がないか確認します。

**確かめたい層**
1. アプリが指令を出した（ログで確認済み）
2. PWM を出す仕組みが今動いている（例：pigpio を使っているなら `pigpiod` が起動している。ライブラリの初期化が成功している）
3. GPIO ピンに実際にパルスが出ている
4. サーボに電源が来ている（電圧、GND の共通化）
5. サーボ本体が動く（機械的な固着や、ラッチ側の負荷）

**お手数ですが、教えてください（3点）**
1. 開錠の操作をしたとき、サーボから音（ジーという音）や小さな振動はありましたか？ → 2〜4（信号・電源）と5（機械・負荷）を切り分けます。
2. 最後に正常に動いたのはいつで、その後に変えたものはありますか？（OS の更新、再起動、配線、コードの更新など）
3. 今、ドアは物理的な鍵など別の方法で開けられますか？ → 調査中に施錠状態で止まっても困らないかを確認するためです。開けられない場合は、先にその手段を確保してください。

**Raspberry Pi で実行してほしいコマンド**（PC から SSH で Pi にログインした端末で、1行ずつ貼り付けてください。Windows の PowerShell で直接実行するものではありません）

サービス名がわからない場合は、まずこれで探します。
```
systemctl list-units --type=service --state=running
```
錠のアプリらしいサービス名が見つかったら、次のコマンドの `<サービス名>` をそれに置き換えて実行し、直近の起動から今回の操作までのログを見ます。
```
sudo journalctl -u <サービス名> -b --no-pager | tail -n 100
```
→ 指令の行の前後に、GPIO や PWM の初期化エラー、権限エラー、`pigpio` への接続失敗などが出ていないかを見ます。出力をそのまま貼ってもらえれば、こちらで読みます。

pigpio を使っている場合はこちらも実行してください（コードを読んで使っていないとわかれば不要です）。
```
systemctl status pigpiod
```
→ `active (running)` なら起動しています。`inactive` や `failed` なら、PWM が出ていない有力な候補です。

この結果が揃うまで、コードの修正や再起動はしません。原因の層が分かったら、その箇所だけを直す案を出します。今回の報告（Web UI は開錠、ログに指令あり、サーボは動かず）は台帳の試験記録に書いておきます。

## ケース N3
スケッチを書きます。ただ、2点だけ先にお伝えします。

**1. 「コンパイルが通ったら完成」ではありません**
コンパイルが通っても、実際にサーボが動くかはわかりません。わかるのは、文法とライブラリの指定が正しいことだけです。完成の確認は、実機で次の3点を見るのがおすすめです。
- ボタンを押すとサーボが動く
- 動いた角度がおよそ 90° である（SG90 は個体差があり、指令どおりの角度になるとは限りません）
- 動いた瞬間に Nano がリセットしない（起動しなおす、シリアルが切れる、などが起きない）

**2. サーボの電源を Nano の 5V ピンから取る件**
- SG90 は動き始めや負荷がかかったときに、一時的に大きな電流を流します。具体的な値は、販売元の資料で確かめるのが確実です。
- Nano を USB 給電にしている場合、5V ピンは PC の USB からダイオードなどを経由しています。互換機では保護部品の構成もまちまちです。サーボが電流を引いた瞬間に電圧が下がり、Nano がリセットしたり、動きが不安定になったりすることがあります。
- **何もつけない状態で軽く動かすだけの試験**なら、5V ピンからでも動くことが多いです。ただし保証はありません。
- 推奨：サーボの電源は別の 5V 電源（USB 充電器から取った 5V など）にして、**GND だけ Nano と共通にする**。5V ピンから取るなら、サーボの電源端子の近くに電解コンデンサ（数百 µF 程度）を入れると、電圧の落ち込みを和らげられます。
- 何かを動かす（ラッチなど）用途なら、どれくらいの重さ・力がかかるか教えてください。電源の決め方が変わります。

**配線（この前提でスケッチを書いています）**
- サーボ：茶＝GND、赤＝5V、橙＝信号 → D9
- ボタン：片側を D2、もう片側を GND（内部プルアップを使うので抵抗は不要）

**確認したいこと**
押した後の動きをどうしますか？ 下のスケッチは「起動時 0° → 1回押すと 90° に動いてそのまま」にしています。ほかに、「もう一度押すと 0° に戻る（トグル）」「押している間だけ 90°」もできます。特に希望がなければこのままで大丈夫です。

```cpp
#include <Servo.h>

const int SERVO_PIN  = 9;
const int BUTTON_PIN = 2;   // ボタンの反対側はGNDへ

Servo servo;
bool moved = false;

void setup() {
  pinMode(BUTTON_PIN, INPUT_PULLUP);  // 押すとLOW
  servo.attach(SERVO_PIN);
  servo.write(0);                     // 起動時は0度
}

void loop() {
  if (!moved && digitalRead(BUTTON_PIN) == LOW) {
    delay(20);                        // チャタリング対策
    if (digitalRead(BUTTON_PIN) == LOW) {
      servo.write(90);
      moved = true;
    }
  }
}
```

注意点
- 電源を入れた瞬間に、サーボが 0° の位置へ急に動きます。腕（ホーン）の先に物が当たらない状態で試してください。
- 互換機は USB 変換チップが CH340 のことが多く、PC にドライバが必要な場合があります。書き込みに失敗するときは、Arduino IDE の「プロセッサ」を「ATmega328P (Old Bootloader)」に切り替えて試してください。
- 角度がずれるときは、`servo.attach(SERVO_PIN, 500, 2400);` のようにパルス幅の範囲を指定して調整できます。SG90 の適正範囲は、お手元の製品の資料で確かめてください。

試したら、「動いたか」「角度はどうだったか」「リセットしなかったか」を教えてください。プロジェクト用に `TSUKURUMAE_LEDGER.md` を作り、電源の方式（今は Nano の 5V から取る前提）と、上の実機確認項目を「未確認」として記録しておきます。

承知しました。マイグレーションは書きます。ただし、本番への適用は取り返しがつきにくい操作です。下の確認が済み、あなたから「流して」の明示的な返事をもらってから実行します。

**先にこちらで調べること**（本番への書き込みはしません）
1. リポジトリのマイグレーションの仕組み（使っているツール、既存のマイグレーションの書き方、トランザクション内で実行されるか）を確認します。
2. `users.email` を読み書きしているコードを確認します。登録・更新時に大文字小文字をそろえているか、制約違反のエラーをどう扱っているか、を見ます。
3. 本番 DB に読み取り専用のクエリだけを流し、次を確認します。
   - 既存の重複がないか（そのままの値と、`lower(email)` の両方で数えます）。重複が1件でもあると、制約の追加は失敗します。
   - `email` が NULL の行の数（PostgreSQL のユニーク制約では、NULL 同士は重複扱いになりません）
   - テーブルの行数とサイズ（ロックの時間の見積もりに使います）
   - すでに `email` に同じ目的のインデックスや制約がないか
   結果は数値のまま報告します。

**マイグレーションの方針（案）**
単純な `ALTER TABLE users ADD CONSTRAINT ... UNIQUE (email)` は、テーブルが大きいと、インデックスを作る間ずっと書き込みを止めます。そのため次の2段階にする案です。
```sql
-- 1) 書き込みを止めずにインデックスを作る（トランザクション外で実行が必要）
CREATE UNIQUE INDEX CONCURRENTLY users_email_key ON users (email);
-- 2) そのインデックスを使って制約にする（ロックは短時間）
ALTER TABLE users ADD CONSTRAINT users_email_key UNIQUE USING INDEX users_email_key;
```
- `CONCURRENTLY` は失敗すると無効なインデックスが残るので、失敗時の後片付け（`DROP INDEX CONCURRENTLY`）も手順に入れます。
- 戻すとき（down）：`ALTER TABLE users DROP CONSTRAINT users_email_key;`
- マイグレーションのツールがトランザクションで包む場合は、その設定を外す書き方にします。1 で確認してから決めます。

**決めていただきたいこと**
1. 大文字小文字の違うメール（`Foo@x.com` と `foo@x.com`）を、同一とみなしますか？ → 制約の形が変わります（`lower(email)` に対するユニークインデックスになる）。推奨：同一とみなす。ただしアプリ側の検索も合わせる必要があるので、コードを見てから提案します。
2. 重複が見つかった場合、どう解消しますか？ → データの削除・統合になるので、私の判断では行いません。見つかったら一覧を示して相談します。
3. 本番に流す前に、ステージングなどの検証環境で試せますか？ → 推奨：検証環境で先に実行し、時間とロックを確かめる。
4. 本番 DB のバックアップ（または時点を指定した復元）は取れていますか？ 実行してよい時間帯はありますか？

調査結果とマイグレーションのファイルを揃えたら、「対象・実行手順・戻し方」をまとめて提示します。そこで OK をいただいてから本番に流します。進め方は `TSUKURUMAE_LEDGER.md` に記録しておきます。
