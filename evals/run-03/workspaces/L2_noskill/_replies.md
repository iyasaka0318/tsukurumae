3. **「無反応」の様子**：
   - アプリは動いている（ログが出ている・Discord 通知の他の機能は動く）のに、カードだけ読めない？ それともアプリごと固まっている？

6. **電源**：Pi 3 の AC アダプタの定格、USB にリーダー以外に何がつながっているか、リレー/ソレノイドの電源は Pi と共通か。

### 疑っていること（まだ仮説です）

Pi 3 + USB の NFC リーダーで「抜き差しで直る」症状は、だいたい次のどれかが多いです。

- **電源不足・電圧降下**：Pi 3 は USB ポート全体の供給に余裕がなく、ソレノイド動作時の電圧降下でリーダーがリセット/ハングすることがある。→ 起きたタイミングが「解錠直後」と重なるかが手がかりです。
- **USB の切断・再列挙にアプリが追従できていない**：デバイスが一度切れて再認識されても、アプリが古いハンドルを握ったまま。
- **リーダーのファームウェア/ドライバ側のハング**：ポーリングを長時間続けると固まる系。
- **USB オートサスペンド**。

### 次に見てほしいもの（症状が出たとき、抜き差しする前に）

Pi 上で次を実行して、結果を貼ってもらえると切り分けが進みます。

```
dmesg -T | tail -n 50          # USB の切断・リセット・エラーが出ていないか
lsusb                          # リーダーがまだ見えているか
vcgencmd get_throttled         # 0x0 以外なら電圧低下の履歴あり
journalctl -u <アプリのサービス名> --since "1 hour ago"   # アプリ側のログ
```

特に `vcgencmd get_throttled` が `0x50005` などになっていれば電源がほぼ確定、`dmesg` に `USB disconnect` が出ていればアプリ側の再接続処理が論点になります。

その前に、「履歴から3ファイルを戻す」は単純に `git checkout <書き換え前> -- ファイル` すると事故りやすいので、進め方と確認したいことを書きます。

### 確認したいこと

1. **なぜ pigs 方式にしたのか**：当時 pi4j で困ったこと（起動しない・root 権限・wiringPi 非推奨・ピン番号の扱いなど）があったなら、戻すと同じ問題が再発します。覚えている範囲で教えてください。
2. **pi4j のバージョン**：戻す先のコードは pi4j v1（wiringPi ベース）ですか、v2 ですか？ v1 は wiringPi が開発終了していて、OS を上げていると動かないことがあります。Pi の OS（`cat /etc/os-release`）も教えてください。
3. **書き換え以降に、その3ファイルを触ったか**：書き換えた後に、同じファイルへ別の修正（例えば Discord 通知や解錠ロジック）を入れていると、ファイルごと戻すとそれが消えます。
4. **ビルド環境**：Pi 上でビルド？ PC でビルドして jar を転送？ Gradle / Maven？
5. **pigpiod の扱い**：pigs 方式なら `pigpiod` が常駐しているはずです。pi4j に戻したあと pigpiod を止めるのか残すのか（pi4j v2 の pigpio プロバイダと二重に GPIO を掴むと競合します）。

### 進め方（ソースを見られたら）

1. `git log --oneline -- <3ファイル>` で、pigs 化したコミットとその前後を特定します。
2. `git diff <pigs化の直前> HEAD -- <3ファイル>` で、pigs 化以外の変更が混ざっていないか確認します。
   - 混ざっていなければ：その3ファイルを pigs 化直前の版に戻す。
   - 混ざっていれば：pigs 化コミットだけを `git revert`（または手で該当部分だけ戻す）。
3. 3ファイル以外の関連箇所も確認します：`build.gradle(.kts)` / `pom.xml` の pi4j 依存（pigs 化のときに消していたら戻す必要あり）、systemd のユニットファイル（実行ユーザーや pigpiod 依存）。
4. 作業はブランチを切って行い、ビルドします。

### ビルドの後について

ビルドが通っても、それは「コンパイルできた」までで、錠が正しく動くかは別です。電子錠なので、本番の Pi に入れる前に次を確認させてください。

- 今動いている jar（pigs 版）をバックアップしておき、すぐ戻せるようにする
- 入れ替えたら、解錠・施錠が実際に動くか、起動直後にリレーが勝手に ON にならないか（GPIO の初期状態）を、扉の前に人がいる状態で確認する

リポジトリの場所と、上の 1〜5 を分かる範囲で教えてください。分からない項目は履歴やコードから私が調べます。

## ターン 3

まず最優先は錠を使える状態に戻すことです。原因調べはその後にしましょう。

### 1. 先に復旧（切り戻し）

デプロイ前の pigs 版の jar（と、変えていれば systemd のユニットファイル）が残っていれば、それに戻してサービスを再起動してください。

```
sudo systemctl stop <アプリのサービス名>
# バックアップしておいた pigs 版 jar を元の場所に戻す
sudo systemctl start <アプリのサービス名>
journalctl -u <アプリのサービス名> -n 50
```

バックアップがない場合は、pigs 化されていた状態のコミット（pi4j に戻す前の HEAD）からビルドし直して入れます。その間、扉は物理鍵などで運用してもらう必要があります。どちらの状況か教えてください。

### 2. PI_INIT_FAILED について（仮説）

`PI_INIT_FAILED` は pigpio ライブラリの初期化（`gpioInitialise`）が失敗したときのエラーです。pi4j v2 の pigpio プロバイダは、内部でこの pigpio ライブラリを直接使います。

一番疑わしいのは、**pigs 方式のときに使っていた `pigpiod` デーモンがまだ動いていて、GPIO を掴んだまま**という状態です。pigpio はライブラリ直接利用とデーモンが同時に初期化できません。ターン 2 で懸念した競合です。ほかに考えられるのは、アプリを root 以外で動かしている、くらいです。

切り戻した後でいいので、次の結果を見せてください。

```
systemctl status pigpiod
ls -l /var/run/pigpio.pid
ps aux | grep -E 'pigpiod|java'
journalctl -u <アプリのサービス名> -b | grep -B5 -A20 PI_INIT_FAILED
```

`pigpiod` が active なら、ほぼこれが原因と見てよいと思います。ただ、確認する前に断定はしません。

### 3. 4か月前の SIGSEGV（gpioRead）は原因か？

今回の PI_INIT_FAILED の直接の原因ではないと思います。初期化に失敗しているので、gpioRead まで処理が進んでいないはずです。

ただし、**別の意味でかなり重要**です。

- gpioRead は pigpio のネイティブ関数で、pi4j（pigpio プロバイダ）経由で呼ばれた時に JVM ごと落ちた可能性があります。
- 4か月前というのが、あなたが pigs 方式に書き換えた時期と近くないですか？ もし近ければ、**このクラッシュを避けるために pigs 化した**可能性があります。その場合、pigpiod を止めて pi4j に戻すと、初期化は通っても、またそのうち SIGSEGV で落ちるかもしれません。

確認したいこと：
- クラッシュログ（`hs_err_pid*.log` など）の日付と、pigs 化コミットの日付
- クラッシュログの先頭（シグナル、落ちたライブラリ名、スタックの Java 側フレーム）
- pigs 化コミットのメッセージや、当時のメモに理由が書いてあるか

### 4. この後の方針

pigs 化した理由が「SIGSEGV 回避」だと確認できたら、pi4j に戻すこと自体を見直したほうがいいと思います（例：pi4j を使うなら原因を潰してから、または pigs 方式のまま保守性を上げる）。そもそも pi4j に戻したかった理由を教えてもらえれば、それも含めて考えます。

まずは切り戻しができたかどうか教えてください。

## ターン 4

直ってよかったです。記録のために一つ教えてください。**何をして直りましたか？**（pigs 版に切り戻した／pigpiod を止めて pi4j 版のまま動いた、など）。今どちらの版が動いているかで、この後の話が変わります。

### ウォッチドッグを消す前に

消す作業自体は簡単ですが、すぐには消さないほうがいいと思います。

**「1時間ごとに USB の電源を切る」というのは、ターン 1 の FeliCa リーダーが無反応になる問題を回避するために入れたものではないでしょうか。**「USB を抜き差しすると直る」を自動でやっているように見えます。もしそうなら、消すとリーダーが固まったまま気づかれない時間が延びます。特に夜中に固まると、朝最初に来た人が開けられません。

なので、次を確認させてください。

1. **どこで動いているか**：cron（`crontab -l`、`sudo crontab -l`、`/etc/cron.d/`）、systemd timer（`systemctl list-timers`）、アプリ内のスケジューラのどれか。中身（`uhubctl` を呼んでいるか、など）も見せてください。
2. **いつ、誰が、なぜ入れたか**：コメント、コミット、研究室のメモなどで分かれば。
3. **夜中に動いて何が困っているか**：ログが埋まる、その間カードが読めない、ほかの USB 機器や LAN まで切れる、など。
   - 補足：Pi 3 は USB ポートの電源を個別に切れず、まとめて切る仕様だったはずです。モデル（3B / 3B+）によっては有線 LAN も同じチップにつながっているので、電源を切るたびにネットワークも一瞬切れているかもしれません。Discord 通知が時々失敗するなら、これが関係している可能性もあります。ここは実機で確認が必要です。

### 代わりの案

リーダー対策のためのものだと分かった場合は、「消す」より次のどれかがいいと思います。

- **A. 時間帯を絞る**：利用時間帯だけ動かして、夜中は止める。ただし朝一番の利用前に1回は動かす。
- **B. 必要なときだけ切る**：1時間ごとに切るのをやめ、アプリが「リーダーが応答しない」と判断したときだけ USB 電源を入れ直す。同時に Discord に通知すれば、ターン 1 で話した監視と、Discord 改修の両方につながります。
- **C. 本当に不要なら消す**：リーダーの問題と無関係と分かった場合、または根本原因（電源など）を直した後。

おすすめは、今すぐなら A、落ち着いたら B です。確認した設定の中身を見せてもらえれば、A の書き換えはすぐできます。

## ターン 5

直します。ただ、「2回出る」の原因によって直し方がまったく違うので、まずどれなのかを確かめさせてください。ログを表示だけ1回にしても、裏で2回動いているなら問題を隠すだけになります。

### 見せてほしいもの

その再接続ログの前後20行くらいを、そのまま貼ってください（タイムスタンプ、スレッド名、ロガー名が入っている形で）。あわせて次の2点も。

```
ps aux | grep java              # アプリが2つ動いていないか
systemctl status <アプリのサービス名>
```

あと、これは何の再接続ですか？ FeliCa リーダー（USB）か、Discord か、ネットワークか。

### 考えられる原因（ログを見て判断します）

1. **アプリが2つ動いている**：今日はデプロイと切り戻しをしたので、古いプロセスが残っている可能性があります。ログの PID やスレッドが違えばこれです。これだと、GPIO やリーダーを2つのプロセスが取り合うので「実害なし」とは言えません。最優先で確認したいのはこれです。
2. **ウォッチドッグとアプリの両方が再接続している**：ターン 4 のウォッチドッグが USB の電源を切る → アプリが切断を検知して再接続、という流れで、検知元が2つ（切断イベント + 読み取りエラーなど）あると2回出ます。ログの時刻が毎時ちょうどならこれが濃厚です。
3. **再接続処理・リスナーが二重に登録されている**：初期化が2回呼ばれている、など。pi4j に戻して切り戻した過程でコードが混ざっていないかも気になります。
4. **ログ出力の設定の問題**：処理は1回で、ログだけ2回出ている（logback などでアペンダーが二重に設定されている、など）。ログの中身がまったく同じで時刻も同じならこれです。この場合は設定を1行直すだけです。

### 直し方の見通し

- 1 → 余計なプロセスを止めて、systemd で二重起動しないようにする
- 2 → ウォッチドッグの扱い（ターン 4 の話）と一緒に整理する
- 3 → 該当コードを直す（ソースを見る必要があります）
- 4 → ログ設定を直す

ターン 4 の「何で直ったか」と「ウォッチドッグの中身」もまだ聞けていないので、分かれば一緒に教えてください。2 と関係しているかもしれません。
