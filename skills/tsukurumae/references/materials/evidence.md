# 証拠の強さと検証の段階

## 値の状態

寸法・電圧・設定値・仕様・動作結果には、次のどれかの状態を付ける。

| 状態 | 意味 | 例 |
|---|---|---|
| ユーザー実測 | ユーザーが現物で測った | 「コネクターを挿した後の高さ 20mm」 |
| メーカー公称 | データシートや公式資料の値 | 外形寸法、定格電圧 |
| 資料上の実測 | 過去の記録に実測と書かれている（今回は再測定していない） | 古い仕様書の電池寸法 |
| 写真からの概算 | 写真や図から読み取った | 「ケーブルは短い辺から出ている」 |
| 計算値 | 他の値から計算した | 突き出し量 = ネジ長 − 板厚 |
| 仮定 | 確認していない前提 | 「重量 29g と仮定」 |
| 未決 | まだ決めていない | 取付の向き |
| 試験合格 | 試験で確認した（下の条件を必ず付ける） | 「PLA、穴径 2.4mm、この形状でネジが通った」 |

- 値には、**用途・対象・材料・条件**を付ける。同じ「2.1mm の穴」でも、高さや用途が違えば同じ結果にならない。
- 代表的な製品の寸法を、手元の同じ型番の確定値として扱わない。
- AI の発言や別 AI のレビューは、メーカーの保証や実測に格上げしない。

## 試験の記録

試験合格を記録するときは、次を付ける。

- 対象（どの部品・どのファイル・どの機能）
- 版（試験片のバージョン、ファームウェアのファイル名やハッシュ、コミット）
- 条件（材料、電圧、環境、入力データ）
- 確認した項目と、確認していない項目

## 検証の段階

段階は別のものとして扱う。前の段階の合格は、後の段階の合格ではない。

**ハードウェア**
CAD 上で干渉なし → 実物が組み立つ → 固定と強度が足りる → 動作する → 負荷・長時間・異常時も動作する

**電装・ファームウェア**
ビルド成功 → ホストでのテスト合格 → 実機で動作（指令が対象の動作範囲に入っている） → 測定で確認 → 負荷・異常時の確認

**ソフトウェア**
ビルド・構文チェック → 単体テスト合格 → 手元の実環境で動作 → 本番の環境とデータで動作 → 負荷・異常時・長期運用

## 文書・コミットメッセージ・成果物の中でも同じ

返答の中だけでなく、コミットメッセージ、README、コードのコメント、CAD の注記にも、確認していないことを確認済みのように書かない（例：ユーザーがまだ実行していない「常駐プロセスを停止した」をコミットメッセージに書く）。返答と成果物の中の注記で、言っていることを食い違わせない。

## 短い返事の扱い

「おｋ」「動いた」のような短い返事は、**それが何についての返事か**が分かる範囲でだけ記録する。

- 例：回転の確認をお願いした後の「おｋ」は、「回転した」という報告として記録する。停止にかかった時間、推力、固定の安全性は確認済みにしない。
- 何についての返事か分からない場合は、合格の範囲を広げずに、短く確かめる。

## 観察と原因の診断を分ける

- 観察：「下の面に隙間がある」
- 診断：「Z オフセットが原因」← 写真だけなら「推定」
- 原因を確かめる方法を添える：「Z オフセットを 0.05mm ずつ変えた試験片で確かめる」
