# ソフトウェアの確認観点

全部を聞くためのリストではない。今の作業の確定条件にかかわり、後から分かると作り直しが大きくなるものを選ぶ。
ソフトウェアは試すコストが低い。**聞くより小さく作って見せたほうが速い**場面では、そうする。止めるべきなのは、取り返しのつかない操作と、後から変えにくい約束事。

## 段階ごとの使い方

| 段階 | 使う節 |
|---|---|
| 2 主役の確認 | 下の「段階 2：主役が目的に合うか」 |
| 3 周りの成り立ち | 「『使われる状態』を捉える」（実行環境・リポジトリの外・データ・外部の仕様） |
| 4 設計・実装 | 「変更するとき」「コミットと共有」「取り返しのつかない操作」 |
| 5 試作・観測 | 「障害の調査」「ユーザーがコードを読まない前提」 |

## 段階 2：主役が目的に合うか

主役（中心になる言語・フレームワーク・外部サービス・アルゴリズム・既存システムのどこを直すか）を、目的から導いた条件で確かめる。
- 目的から必要な条件を導く：誰が、どこで、どのくらいの量・頻度で使うか。止まったときの影響
- 既に決まっているもの（「このライブラリで」「この構成のまま」）があれば、その条件に照らして足りるかを書く
- 改修なら、何を変えて何を変えないかをここで決める

## 「使われる状態」を捉える

1. **実行環境**：OS、言語とランタイムのバージョン、本番か開発か、**実行ユーザーと権限**、作業ディレクトリ、環境変数、ブラウザ、マイコンの型番と SDK の版。
2. **リポジトリの外の状態**：常駐プロセス（デーモン）、実機にだけある設定ファイル、手で入れたパッケージ、systemd の unit、cron、ログの出力先。コードを元に戻したり変えたりするとき、これらに付随する変更がないかを確かめる。ユーザーの記憶が曖昧なら、実機で見るコマンドを先に出す。
3. **既存のコード**：規約、ディレクトリ構成、既にある関数やライブラリ、テストの有無と実行方法、変更の影響範囲。（自分で読む。聞かない）
4. **データ**：実際のデータの形・量・文字コード・欠損、既存のデータとの互換性。サンプルで想定しない。
5. **外部の仕様**：API、ライブラリ、ファイル形式、通信プロトコルの、実際のバージョンでの仕様。記憶で書かず、ドキュメント・依存関係の解決結果・実物で確かめる。確かめていないなら、そう書く。
6. **使い方と完成の基準**：誰が、いつ、どの画面や操作で使うか。「この操作でこう表示されたら完成」。止まったときの影響（例：朝一番の人が部屋に入れない）。

## ユーザーがコードを読まない前提

- AI が自分でビルド・実行・テストし、その結果を示す。
- 結果は、ユーザーが見て確かめられる形で示す（どの画面で何が表示されるか、どのコマンドで何が出力されるか）。
- ユーザーに実行してもらうコマンドは、**どのマシン・どの端末で実行するか**を書き、1つずつ貼り付けられる単位にし、成功したとき・失敗したときに何が見えるかを書く。
- 「完成しました」と書くのは、確認した段階を明示できるときだけ。テストを書けない対象（実機の GPIO や USB に依存するなど）では、ビルド成功は動作の証拠にならない。実機で確かめる項目を毎回挙げる。

## 障害の調査

- **層を分けて観測する**。例：USB として認識されている → 転送できている → OS の入力イベントが出ている → アプリが受け取っている → 認証が通っている → 物理的に動いた。ある層が正常でも、次の層の正常は保証されない。画面上の「開錠」やログ上の指令は、モーターが動いた証拠ではない。
- **今の障害の観測を取る**。固まっている最中のスレッドダンプ、今回の起動のログ、直接実行したときの出力。古いログや1件の相関は候補にとどめる。
- **再現の条件を本番と揃える**。サービスとして動くなら、同じ実行ユーザー（root かどうか）、同じ作業ディレクトリ、同じ環境変数で試す。
- **似た現象を区別する**。サービスの再起動と OS の再起動、プロセスの二重起動と unit の二重起動、など。それぞれを確かめるコマンド（boot の一覧、unit のログ、プロセス数）を同じ時間範囲で比べる。
- **推測を実験にする**。判定ロジックを入れる前に、計測と記録だけを入れる。正常時の基準値を取り、当たり・外れの条件を先に決める。

## 変更するとき

- **診断した原因への修正に絞る**。念のための追加機能は、提案として分けるか、別のコミットにする。
- **実害のない見た目の問題は直さない**。特に、復旧の経路・並行処理・ロックに手を入れると、別の故障を招きやすい。手を入れるなら、どこか1か所が固まっても別の経路が復旧すること、新しい待ちには上限があることを確かめる。
- **安全装置を消す前に、それが拾っている故障を確かめる**。定期的なリセット、ウォッチドッグ、無条件の再接続などは、検知できない故障の唯一の復旧手段であることがある。消すなら、設定で切り替えられるようにし、戻す条件と効果を見るログを先に決める。
- **成功の判定は、呼び出し先が失敗をどう返すかを確かめてから書く**。例外、`null`、エラーコードのどれで失敗を返すかを読み、成功を示す戻り値のときだけ「生きている」と判定する。抜かれた、応答しない、などの失敗の経路を机上でたどる。
- **調査用の出力は、量を見積もる**。1回の操作で何行、1日で何 MB になるか。既定では抑制し、有効にする方法と戻し方を伝える。
- **元に戻す・大きく変える前に、今の状態を保存する**（コミット、ブランチ、バックアップ）。

## コミットと共有

- 変更したファイルだけを個別に stage する。`git add -A` や `git add .` は使わない。stage の前に `git status`、commit の前に `git diff --cached` を見る。
- 自分が触っていないファイルが作業ツリーにあれば、報告する。
- 共有・公開・push の前に、秘密情報（トークン、秘密鍵、パスワード、個人情報）を検索する。会話に秘密情報が貼られたら、転記せず、再発行を勧める。
- ユーザーが述べた文書の方針（「経緯は要らない、原因と結果だけ」など）は、指示書に書き足し、以後の文書に適用する。

## 取り返しのつかない操作

削除、上書き、DB の移行、本番へのデプロイ、本番機の再起動、外部へのメールやメッセージの送信、課金が発生する操作、`git push --force` など。

- 対象の範囲を明示し、バックアップか元に戻す手段を確かめてから行う。
- 可能なら、ドライランか検証環境で先に試す。
- 本番機への操作は、ユーザーが自分で行う前提で手順を渡すことが多い。接続できなかったときに、別の抜け道を探さない。
- ユーザーが手順・送り先・権限をすべて示して「手順だけ」と言ったら、質問せずに手順を出す。

## 組込みファームウェア

ハードウェアとの境目にあるので、両方の観点を使う（[hardware.md](hardware.md) の「測定と試験」）。

- 出す指令が、相手の機器が反応する範囲に入っているか。ホストのテストだけでは分からない。
- 起動時・リセット時のピンの状態（内蔵プルアップやプルダウン、起動直後の出力）。マイコンの世代が違えば同じとは限らない。
- 開始と停止の手順、異常時の停止（通信断、電圧低下、ウォッチドッグ）。
- 生成したファイル（UF2、jar など）は、ファイル名とハッシュかコミットで版を記録する。「ビルドした版」と「実機に入っている版」を区別する。

## 研究用の解析・ML

- 何を比べるか、基準は何か、交絡要因は何かを先に決める（[intake.md](../intake.md) の「研究のとき」）。
- 測定やログが、測りたい対象に影響しないか（計測の負荷、割り込み、バスの競合）。
- センサーを選ぶときは、研究目的から条件を導く：出力レート、遅延、インタフェースとバスの負荷（I2C か SPI か）、データレディの割り込み、タイムスタンプの取り方、ノイズとドリフト。手持ち品は、まず静止時の基準を測って足りるかを確かめる。
- ログの保持と回収：異常停止、再起動、電源断のときに、必要なデータが残るか。
- 実測した最大値を、すべての条件での上限として扱わない。
