# ソフトウェアの確認観点

> **暫定版**：ソフトウェア開発の実例資料を受け取ったら改訂する。今はハードウェアの実例から共通する原則と、一般的な観点で書いている。

全部を聞くためのリストではない。今の作業の確定条件にかかわり、後から分かると作り直しが大きくなるものを選ぶ。
ソフトウェアは試すコストが低い。**聞くより小さく作って見せたほうが速い**場面では、そうする。止めるべきなのは、取り返しのつかない操作と、後から変えにくい約束事。

## 「使われる状態」を捉える

1. **実行環境**：OS、言語とランタイムのバージョン、パッケージ管理、本番か開発か、ブラウザ、マイコンの型番と SDK の版。（調べられるものは調べる。手元の環境はコマンドで確かめてもらうか、自分で確かめる）
2. **既存のコード**：規約、ディレクトリ構成、既にある関数やライブラリ、テストの有無と実行方法、変更の影響範囲。（自分で読む。聞かない）
3. **データ**：実際のデータの形・量・文字コード・欠損、既存のデータとの互換性。サンプルで想定しない。
4. **外部の仕様**：API、ライブラリ、ファイル形式、通信プロトコルの、実際のバージョンでの仕様。記憶で書かず、ドキュメントか実物で確かめる。
5. **使い方**：誰が、いつ、どの画面や操作で使うか。完成の基準（「この操作でこう表示されたら完成」）。（聞く）

## ユーザーがコードを読まない前提

- AI が自分でビルド・実行・テストし、その結果を示す。
- 結果は、ユーザーが見て確かめられる形で示す（どの画面で何が表示されるか、どのコマンドで何が出力されるか）。
- ユーザーに実行してもらう手順は、コピーしてそのまま実行できる形にし、成功したときと失敗したときに何が見えるかを書く。
- 「完成しました」と書くのは、確認した段階を明示できるときだけ。（[evidence.md](evidence.md) の検証の段階）

## 取り返しのつかない操作

削除、上書き、DB の移行、本番へのデプロイ、外部へのメールやメッセージの送信、課金が発生する操作、`git push --force` など。

- 対象の範囲を明示し、バックアップか元に戻す手段を確かめてから行う。
- 可能なら、ドライランか検証環境で先に試す。
- ユーザーが「計画だけ」と言っているときは実行しない。

## 組込みファームウェア

ハードウェアとの境目にあるので、両方の観点を使う（[hardware.md](hardware.md) の「測定と試験」）。

- 出す指令が、相手の機器が反応する範囲に入っているか。ホストのテストだけでは分からない。
- 起動時・リセット時のピンの状態（内蔵プルアップやプルダウン、起動直後の出力）。マイコンの世代が違えば同じとは限らない。
- 開始と停止の手順、異常時の停止（通信断、電圧低下、ウォッチドッグ）。
- 生成したファイル（UF2 など）は、ファイル名とハッシュで版を記録する。

## 研究用の解析・ML

- 何を比べるか、基準は何か、交絡要因は何かを先に決める（[intake.md](intake.md) の「研究用途のとき」）。
- 測定やログが、測りたい対象に影響しないか（計測の負荷、割り込み、バスの競合）。
- ログの保持と回収：異常停止、再起動、電源断のときに、必要なデータが残るか。
- 実測した最大値を、すべての条件での上限として扱わない。
