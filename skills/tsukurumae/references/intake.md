# 要件定義の観点の例

ここに書いてあるのは**例**であり、チェックリストではない。全部を聞く必要はなく、ここにないことを考えてよい。案件ごとに、目的から考えて必要なものを選ぶ。

## 目的から考えた提案の例

依頼されたものの中を改善するだけでなく、目的から何に取り組むかを考え直した例。

- 研究で「制御とほかの処理の干渉」を測りたくて、ドローンを作ると言っている
  → 測ることが目的なら、まず固定した試験台で測り、飛ばすのは最後にした方が早く、条件もそろえやすいのでは。
- 研究で使うセンサーが先に決まっている
  → 研究で測りたいもの（何を、どの周期・精度で）に対して足りるか。発表で突っ込まれそうなら先に言う。
- 研究室の予約を楽にしたくて、アプリを作ると言っている
  → 既存のカレンダーの設備予約で足りないか。作るなら、卒業後に誰が直すか。
- 趣味でドローンを作りたい
  → 作ること自体が目的なので、既製品は勧めない。作る中で一番楽しく、失敗しにくい道を考える。
- 「開発を楽にしたい」と言って、これまで作ってきた Skill の会話の中で呼ばれた
  → いきなり Skill の改善点を探さない。今の状況で何が楽になっていて、何がまだ手間かを捉え、楽にする方向をいくつか理由付きで出す。ユーザーが「今回は Skill の編集で」と選んだら、その中で楽にするために足りないものを言う。
- 動いているシステムの一部を直したい
  → 直す範囲を広げずに済む方法はないか。直さずに運用で避けられないか。

## 案件の種類による違い

| | ゼロから作る | 既にあるものの改修 |
|---|---|---|
| 最初に確かめること | 目的、成功条件、使い方 | 今どうなっているか、なぜ直したいのか、変えてはいけないもの |
| 前提として扱うもの | ほとんどない | 動いている構成、それを作った経緯、運用 |

## ユーザーが話題にしていなくても、方針に効くことが多いもの（例）

**ハードウェア**
- 目的と使い方：用途（研究・趣味・実用）、使う場所、成功条件
- 電源：電池の種類と電圧の範囲、各部への電圧の作り方、電流の見積もり、保護
- 電装：信号の電圧、配線とコネクター、ノイズ、回生や逆流
- 主役の部品：目的から導いた必要な性能、インタフェース、取付と向き
- 機構：大きさと重さ、固定、接続した後の空間、運用中に触る場所（USB、電池交換）
- 制御：開始と停止、異常時の止まり方、書き込みと記録
- 試験：危険な試験の段取り
- 調達：予算、手持ち、入手性

**ソフトウェア**
- 目的と使い方：誰が、いつ、何のために使うか
- 実行環境：OS、動かす場所、実行ユーザー
- 改修のとき：リポジトリの外の状態（常駐プロセス、実機だけの設定）
- データ、外部との接続（API、認証、秘密情報）
- 運用：反映の方法、止まったときの影響、元に戻す方法、引き継ぐ人

**案件の種類ごと**
- 研究：測り方、比べる基準、再現性、交絡、結果の示し方、評価する人
- 実用品：使う人、法規・安全、保守、壊れたときの影響
- 趣味：何ができたら満足か、予算の上限、怪我や事故の危険
- 改修・引き継ぎ：変えてはいけないもの、引き継ぐ相手、元に戻す方法

## 記録・診断の計画の例
- 「〇〇がまだ分かっていない（または、壊れたときに見えない）ので、△△を記録する／診断できるようにする」
- ハード：電圧・指令値・センサー値をシリアルで出す。処理の区間を GPIO で外から測る。
- ソフト：処理の各層（受け取った・判定した・送った）にログを置く。診断用のスクリプトを用意する。
- 出力の量を見積もり、普段は邪魔にならない量にする。

## 研究のとき
研究では「何を比べ、何を測るか」が部品と実装を決める。目的 → 比べる条件 → 測る区間と方法 → 基準の性能 → 必要な部品・実装 → 交絡、の順につなげる。基準の性能が確かめられていなければ、比べる前にそれを確かめる計画を入れる。
