# Step 4：試作・実機確認・フィードバック

## 目的
実物を作らないと分からない問題を、速く見つけて直す。

```
Plan → Build → Observe → Diagnose → Modify → Build …
```

## 手順

### 4-1. 試作前に確認項目を渡す
Step 3 で仮定した値・不確かな箇所を「試作で確認すること」として渡す。例:
- ジャンパ線を挿した状態で蓋が閉まるか（仮定高さ 15mm）
- ネジ穴の径が合うか（PLA で穴が小さくなる場合）
- 総重量（実測値）
- 通電時に各電圧が想定範囲か（テスタで 5V / 3.3V を測る）

### 4-2. フィードバックを受けたら
ユーザーの報告（「ここが干渉した」「思ったより重い」「IMU に振動が乗る」など）を、次の形で整理する:

1. **現象**：何が起きたか（可能なら数値・写真・ログ）
2. **原因の仮説**：複数挙げ、確からしさの順に
3. **切り分け方法**：仮説を区別するための簡単な確認・測定
4. **戻り先**：どのステップの判断が原因か
   - 要求の誤り → Step 1
   - 部品・構成の不足（推力不足、容量不足）→ Step 2
   - 実装条件の見落とし（干渉、ケーブル方向、高さ）→ Step 3
   - 製作・組立・調整の問題 → Step 4 内で修正
5. **修正案**：最小の変更から
6. **うまくいったこと**も記録する（次の設計で維持するため）

### 4-3. 「Step 3 で防げたか」を振り返る
問題ごとに分類する:
- **事前に防げた**（例：Pico 2 WH のヘッダーを考慮していなかった）→ 同じ種類の見落としを防ぐため、該当部品の確認項目を台帳の「教訓」に記録する。繰り返し出るなら [component-checklists.md](component-checklists.md) に追加することを提案する。
- **実機でしか分からなかった**（例：実際に飛ばしたら想定以上に IMU に振動が伝わった）→ 想定内。速く直すことを優先する。

### 4-4. 台帳を更新する
仮定が実測で確認されたら Known に、変更した決定は Decided を更新し、変更理由を残す。

## やらないこと
- フィードバックの症状だけを見て、原因を確かめずに大きく作り直す
- 一度に多くの変更を入れて、何が効いたか分からなくする
- 安全に関わる症状（発熱、発煙、電圧降下による制御喪失、プロペラ回転中の作業）を後回しにする
